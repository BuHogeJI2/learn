## Какую проблему решает

Тест — это способ купить **уверенность в том, что изменение безопасно выпускать**, и у каждого теста есть цена: время на написание, время на запуск и работа по поддержке, когда код меняется. Без стратегии команды платят много, а получают мало: тысячи тестов, которые ломаются при каждом рефакторинге, а ошибка, дошедшая до продакшена, сидит в зазоре между двумя компонентами, каждый из которых был «полностью протестирован».

Вопросы, на которые отвечает стратегия, не о синтаксисе:

- Что может сломаться и чего это будет стоить?
- Какой самый дешёвый тест это поймает?
- Что на самом деле доказывает зелёный результат?

## Ментальная модель: тест проводит границу

Каждый тест обводит линией какую-то часть системы. Внутри линии работает настоящий код. Снаружи что-то заменено или просто не участвует. **Тест доказывает что-либо только о том, что находится внутри его границы.**

```
                    what runs for real                     proves
unit           ┌ function ┐                               this logic is correct
component      ┌ component + its children ┐               this UI behaves for a user
integration    ┌ your code + real database ┐              the parts work together
contract       ┌ consumer's expectation ↔ provider ┐      two sides still agree
end-to-end     ┌ browser → frontend → API → database ┐    a user journey works
```

Более широкая граница доказывает больше о настоящей системе, но стоит дороже: такой тест медленнее, его труднее настроить, а когда он падает, он хуже показывает, где проблема. Узкая граница быстра и точна, но тест может оставаться зелёным, когда продукт сломан.

Вид теста определяет не инструмент. Тест в настоящем браузере с поддельным API — не end-to-end: о настоящем API и базе данных он ничего не доказывает.

Поэтому вопрос никогда не звучит как «юнит или end-to-end?». Вопрос в том, **какая граница ловит этот риск с наименьшими затратами**.

## Виды тестов и что они доказывают

| Вид | Граница | Ловит | Пропускает | Скорость |
| --- | --- | --- | --- | --- |
| **Статические проверки** (типы, линт) | Код как текст | Неверные формы данных, опечатки, опасные паттерны | Неверное поведение | Секунды |
| **Юнит** | Одна функция или модуль | Логику с множеством случаев: цены, даты, парсеры, конечные автоматы | Всё, что между модулями | Миллисекунды |
| **Компонентный** | UI-компонент в смоделированном или настоящем браузере | Поведение для пользователя: что появляется после нажатия | Остальное приложение и бэкенд; в смоделированном браузере ещё и настоящую раскладку | Миллисекунды или секунды |
| **Интеграционный** | Ваш код плюс настоящие зависимости, например база данных | Неверные запросы, [транзакции](/ru/data/consistency/#транзакции-и-acid) (группы записей по принципу «всё или ничего»), [миграции](/ru/data/schema-evolution/), связку с фреймворком | Другие сервисы, настоящий браузер | Секунды |
| **Контрактный** | Каждая сторона API проверяется по записанным ожиданиям другой | Изменение, которое ломает другую команду ([развитие API](/ru/architecture/api-styles/#развитие-долгосрочная-цена)) | Полезна ли функция | Секунды |
| **End-to-end** (E2E, сквозной) | Настоящий браузер и запущенная система | Сломанный сценарий: вход, оформление заказа | Редкие случаи, потому что каждый стоит дорого | Минуты |
| **Визуальная регрессия** | Скриншоты сравниваются с эталоном | Непреднамеренные изменения раскладки и стилей | Поведение | Секунды или минуты |

У контрактного теста две половины: потребитель записывает, чего ожидает, а тесты провайдера проверяют эти ожидания. Проверка только того, что ответ соответствует описанию OpenAPI (машиночитаемому описанию API), уже: она показывает, что форма корректна, а не что реальные примеры потребителя работают.

Типы — это тоже проверки. В типизированном коде тесты, которые только подтверждают «функция получила строку» от вашего же кода, добавляют затраты и не дают информации. С данными снаружи (ответами API, вводом пользователя) иначе: во время выполнения типов нет, поэтому их проверку тестировать стоит.

Ещё несколько проверок отвечают на вопросы, которых эти виды не покрывают: **нагрузочные тесты** ([масштабирование](/ru/architecture/scaling/)), **проверки доступности** ([доступность](/ru/web-platform/accessibility/#что-могут-и-чего-не-могут-проверить-инструменты)) и **внесение сбоев** (fault injection, [надёжность](/ru/architecture/reliability/#как-применять)).

## Настоящие зависимости или тестовые двойники

**Тестовый двойник** (test double) — замена настоящей зависимости. Обычно их все называют моками, хотя строго говоря **стаб** (stub) возвращает заготовленные ответы, а **мок** (mock) ещё и проверяет, как его вызвали.

Каждый двойник меняет реалистичность на скорость и контроль и приносит допущение: *настоящая штука ведёт себя вот так*. Когда допущение перестаёт быть верным, тест остаётся зелёным, а продакшен падает. Классический случай — замоканный API, который всё ещё возвращает старое имя поля.

| Зависимость | Обычный выбор | Почему |
| --- | --- | --- |
| Ваш собственный код | Настоящий | Моки собственных модулей привязывают тесты к структуре кода |
| Ваша база данных | Настоящая, в [контейнере](/ru/delivery/containers/) или in-memory-вариант того же движка | SQLite ведёт себя не как PostgreSQL; проверять нужно именно запросы, ограничения и транзакции |
| Ваш собственный API со стороны фронтенда | Подделка на уровне сети (Mock Service Worker), те же ожидания которой проверяются на провайдере | Тесты видят настоящие вызовы `fetch`, а проверка не даёт подделке врать |
| Сторонний сервис (платежи, почта) | Подделка или песочница поставщика | Вы его не контролируете, он стоит денег и падает по причинам, не связанным с вашим кодом |
| Время и случайность | Под контролем | Иначе результаты меняются от запуска к запуску |

**Заменяйте на самой внешней границе, на какой можно.** Подделка на уровне сети оставляет в тесте вашу обёртку над `fetch`, код повторов и обработку ошибок. Подделка вашего хука `useOrders` их убирает.

## Проверяйте поведение, а не реализацию

Хороший тест падает, когда ломается продукт, и остаётся зелёным, когда код реорганизуют. Тест, который делает наоборот, хуже, чем его отсутствие: он мешает рефакторингу и приучает людей обновлять тесты, не читая их.

- **Проверяйте то, что видит пользователь или вызывающий код**: текст на экране, ответ, строку в базе данных. А не то, какая внутренняя функция вызвана или что лежит в состоянии компонента.
- **Ищите элементы так, как это делают пользователи**: по роли и доступному имени, а не по CSS-классу. Это главная идея Testing Library, и заодно такие тесты немного проверяют [доступность](/ru/web-platform/accessibility/).
- **Избегайте больших снапшотов.** Снапшот, который меняется при каждой правке, принимают не читая. Маленькие подходят для стабильного конкретного результата, например сгенерированного файла.
- **Держите тесты независимыми.** Каждый тест создаёт свои данные. Общие данные и обязательный порядок приводят к случайным падениям ([нестабильные тесты](/ru/delivery/ci-cd/#типичные-проблемы)).
- **Ждите условий, а не времени.** `sleep(2000)` — это либо слишком долго, либо слишком мало.

## Формы: пирамида, трофей и ваши собственные риски

Часто приводят две картинки:

```
Test pyramid                  Testing trophy
     ▲  few E2E                    ▲  few E2E
    ▲▲▲  some integration        ▲▲▲▲▲  most integration
  ▲▲▲▲▲▲▲  many unit              ▲▲▲  some unit
                                ▔▔▔▔▔▔▔  static checks
```

- **Пирамида тестов** (Майк Кон) говорит: много быстрых тестов внизу и мало медленных наверху — из-за стоимости.
- **Трофей тестирования** (Кент Доддс) переносит вес на интеграционные тесты, потому что во фронтенде большинство ошибок — в том, как части работают вместе, а современные инструменты сделали такие тесты быстрыми.

В главном они сходятся: E2E-тестов мало и только для самого важного. Дальше правильная форма зависит от того, где живёт риск. Движок расчёта цен заслуживает множества юнит-тестов. CRUD-админка (экраны, которые создают, читают, обновляют и удаляют записи) получает больше всего пользы от интеграционных тестов. Приложению, которое только собирает другие сервисы, нужны контрактные тесты. Используйте формы как отправной аргумент, а не как правило.

## Выбор покрытия для пользовательского сценария

Возьмите один сценарий, например оформление заказа, и пройдите его:

1. **Перечислите, что может пойти не так**, и сколько стоит каждый сбой: неверная сумма, двойное списание, сломанная кнопка, некрасивая раскладка.
2. **Дайте каждому риску самый узкий тест, который его ловит.** Суммы и скидки — юнит-тесты с множеством случаев. Заказ, записанный одной транзакцией, — интеграционный тест. Контракт с платёжным провайдером — контрактный тест или песочница. Состояния UI корзины — компонентные тесты.
3. **Добавьте один E2E-тест для основного пути** и один-два сбоя, с которыми пользователи реально сталкиваются.
4. **Решите, что намеренно остаётся без тестов** и как вы заметите проблему на продакшене: [мониторинг](/ru/observability/logs-metrics-traces/), [canary](/ru/delivery/deployment-models/#релизы-от-коммита-до-пользователей)-релиз, [фича-флаг](/ru/delivery/deployment-models/#релизы-от-коммита-до-пользователей).

**Процент покрытия** (сколько строк выполнилось во время тестов) показывает, что *не* протестировано. Он не показывает, что что-то протестировано хорошо: тест может выполнить строку и ничего не проверить. Считайте фиксированную цель тревожным признаком, потому что она вознаграждает лёгкие тесты неважного кода. **Мутационное тестирование** (инструмент меняет ваш код и проверяет, что какой-то тест упал) честнее измеряет качество тестов, но сильно увеличивает время запуска.

Когда ошибка доходит до продакшена, добавьте тест на самой узкой границе, которая поймала бы её. Со временем тесты окажутся там, где случаются настоящие сбои.

## Типичные проблемы

- **Рожок мороженого** (ice cream cone): много медленных E2E-тестов и мало быстрых. Набор идёт час, и люди перестают его ждать ([скорость пайплайна](/ru/delivery/ci-cd/#решения-при-проектировании-пайплайна)).
- **Моки везде.** Все тесты проходят, а приложение не запускается, потому что ни один тест не соединял настоящие части.
- **Тесты, повторяющие код**: они проверяют, что `save` вызвал `repository.insert`, поэтому их ломает любой рефакторинг и не ломает ни одна ошибка.
- **E2E-тесты для каждого крайнего случая**, хотя юнит-тест покрыл бы то же правило за миллисекунды.
- **Нестабильные тесты**, которые перезапускают до зелёного, пока никто не перестанет верить красному результату.
- **Подделка базы данных, которая ведёт себя иначе**, чем настоящая, поэтому миграции и ограничения никогда не проверяются.
- **Общие тестовые данные**, из-за которых результат зависит от порядка.
- **Погоня за процентом покрытия** с тестами, которые ничего не проверяют.
- **Проверка только основного пути**: нет тестов для таймаутов, пустых состояний или `500` от API.

## Когда вкладываться, а когда нет

- **Всегда:** статические проверки плюс тесты для логики с множеством случаев и для всего, что работает с деньгами или правами.
- **Недолговечные прототипы:** часто хватает нескольких E2E smoke-тестов (коротких проверок, что главный сценарий работает). Удаляйте их вместе с прототипом.
- **Код, который меняется каждую неделю:** тестируйте на более широкой границе, чтобы тесты переживали изменения.
- **Стабильный, активно переиспользуемый код** (дизайн-система, общая библиотека): много узких тестов окупается, потому что от него зависят все потребители.
- **Старая система без тестов:** начните с нескольких широких тестов вокруг поведения, которое нужно сохранить, затем рефакторьте под их защитой.

## Ландшафт

- **Запуск юнит- и компонентных тестов:** Vitest, Jest, встроенный тест-раннер Node.js; Testing Library для поиска элементов UI.
- **End-to-end и браузер:** Playwright, Cypress, WebdriverIO; режим браузера в Vitest для компонентных тестов в настоящем браузере.
- **Подделки и настоящие зависимости:** Mock Service Worker (подделки на уровне сети), Testcontainers (настоящие базы данных и сервисы в контейнерах).
- **Контракты:** Pact (контракты, управляемые потребителем), инструменты сравнения OpenAPI, проверки схем GraphQL.
- **Визуальные:** Storybook, Chromatic, Percy, скриншоты Playwright.
- **Качество тестов:** Stryker (мутационное тестирование), отчёты о покрытии, встроенные в тест-раннеры.
