## Какую проблему решает

Нагрузка растёт: больше пользователей, больше данных, больше запросов на пользователя. Запуски и распродажи могут за минуты принести в десять раз больше обычного трафика. В какой-то момент ответы замедляются и появляются ошибки.

**Масштабирование** — это удержание задержки и ошибок в пределах ваших целей при росте нагрузки, за разумные деньги, и уменьшение мощностей, когда нагрузка падает, чтобы не платить за простаивающие машины.

Два слова, которые часто путают:

- **Производительность**: насколько система быстрая для **одного** пользователя.
- **Масштабируемость**: **остаётся** ли она такой же быстрой для многих пользователей.

Страница может быть быстрой на тестах и рухнуть под реальным трафиком, а может быть медленной для всех даже без нагрузки.

## Ментальная модель: найти узкое место

Запрос проходит через цепочку ресурсов: CPU, память, сеть, диск, соединения с базой данных, блокировки, квоту внешнего API. **Пропускная способность ограничена самым узким из них.** Добавление мощности в любом другом месте ничего не меняет.

Ресурсы замедляются не постепенно. Когда ресурс приближается к полной загрузке, запросы начинают ждать в очередях, и время ожидания резко растёт:

```
latency
   │                                      │
   │                                     ╱
   │                                   ╱
   │                               _ ─
   │ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─
   └────────────────────────────────────── utilization
   0%                        ~70%      100%
```

Поэтому системам нужен **запас мощности**: у сервера, который в обычный день загружен на 90%, на пик ничего не остаётся.

Полезная формула — **закон Литтла**: в среднем число запросов в обработке = частота поступления × среднее время обработки одного запроса. При стабильных 200 запросах в секунду и 0,5 секунды на запрос в среднем обрабатывается около 100 запросов. Применяйте формулу к каждому ресурсу отдельно, с тем временем, на которое занят *именно этот ресурс*: если запрос держит соединение с базой только 50 мс из своих 0,5 секунды, при 200 запросах в секунду нужно около 10 соединений, а не 100. А асинхронный сервер (например, Node.js) может держать много запросов на очень небольшом числе потоков.

**Измеряйте, прежде чем масштабировать.** Метрики насыщения показывают, где узкое место ([что измерять](/ru/observability/logs-metrics-traces/#что-измерять)), а нагрузочные тесты — где оно будет. В типичных веб-приложениях первой в предел упирается база данных, затем CPU приложения, затем внешние API.

## Стратегии масштабирования

### Делать меньше работы

Часто самый дешёвый и эффективный шаг:

- [кэширование](/ru/architecture/caching/) и [CDN](/ru/web-platform/cdn/) (серверы рядом с пользователями, которые хранят копии) для всего, что можно разделить между пользователями;
- выполнение работы один раз при сборке вместо каждого запроса ([стратегии рендеринга](/ru/architecture/rendering/));
- более удачные запросы и [индексы](/ru/data/database-types/#ментальная-модель-структура-данных-на-диске-плюс-гарантии);
- вынос медленной работы из запроса в [фоновые задачи](/ru/architecture/background-jobs/). Строго говоря, это переносит работу, а не убирает её: запросы становятся быстрыми, пики сглаживаются, но обработчикам всё равно нужно достаточно мощности, иначе backlog (накопившаяся работа) продолжит расти;
- пагинация и лимиты, чтобы ни один запрос не мог попросить «всё».

### Вертикальное: машина побольше

Больше CPU и памяти для того же сервера (масштабирование **вверх**). Это требует немногих изменений в архитектуре и работает дольше, чем ожидает большинство. Но больше ядер помогает, только если программа умеет их использовать: один процесс Node.js выполняет JavaScript на одном ядре, поэтому нужны несколько процессов или воркеров. Масштабируйте тот ресурс, который действительно насыщен. Пределы: есть самая большая машина, цены у верхней границы растут быстро, это всё ещё одна машина, которая может отказать, а изменение размера может потребовать перезапуска.

### Горизонтальное: больше машин

Несколько копий приложения за **балансировщиком нагрузки** (масштабирование **вширь**). Для частей без состояния мощность растёт почти линейно, и вы заодно получаете резервирование: одна копия может упасть, пока остальные продолжают работать. Для этого нужны серверы, которые не хранят собственного состояния (см. ниже).

### Автомасштабирование

Платформа добавляет и удаляет инстансы по метрике: CPU, частоте запросов, длине очереди. Serverless-платформы делают это автоматически ([модели деплоя](/ru/delivery/deployment-models/)). Учитывайте:

- оно реагирует за секунды или минуты, поэтому резкий пик может прийти раньше новой мощности; к известным событиям масштабируйтесь заранее;
- задайте минимум и максимум;
- масштабирование одного слоя переносит давление на следующий: в десять раз больше серверов приложения — в десять раз больше соединений с той же базой.

## Балансировка нагрузки

**Балансировщик нагрузки** принимает все запросы и распределяет их по инстансам:

- **Health checks** (проверки здоровья) убирают сломанные инстансы из ротации.
- Он часто завершает TLS и может маршрутизировать по пути или заголовку, когда работает на уровне HTTP (layer 7, седьмой уровень), или только пересылать соединения, когда работает на уровне TCP (layer 4, четвёртый уровень).
- **Алгоритмы**: round robin (по очереди), least connections (наименьшее число соединений), взвешенный и хэширование (один и тот же ключ всегда попадает на один инстанс, что полезно для кэшей).

**Sticky sessions** («липкие» сессии: каждый раз отправлять пользователя на тот же инстанс) — обходной путь для состояния в памяти. Они делают нагрузку неравномерной, а состояние пользователя теряется, когда этот инстанс умирает. Предпочитайте серверы без состояния.

Балансировка происходит на нескольких уровнях: DNS или anycast (один IP-адрес, анонсированный из многих мест) распределяют пользователей по регионам ([как пользователи попадают в PoP](/ru/web-platform/cdn/#ментальная-модель-reverse-proxy-перед-всем-остальным)), балансировщик распределяет запросы внутри региона, а сервисы балансируют вызовы друг к другу.

## Серверы без состояния, состояние — в другом месте

Горизонтальное масштабирование работает, когда **любой инстанс может обработать любой запрос**. Поэтому состояние уходит с серверов приложения:

- сессии — в базу данных, Redis или подписанные cookies ([сессии](/ru/security/auth/#сессии-на-практике-жизненный-цикл));
- файлы — в объектное хранилище;
- общий кэш — в Redis или похожее хранилище;
- работа по расписанию и долгая работа — в очередь.

См. [что переживает перезапуск](/ru/delivery/deployment-models/#состояние-что-переживает-перезапуск). Состояние не исчезает: оно переезжает в слой данных, и масштабировать становится трудно именно его.

## Масштабирование слоя данных

Сначала самые дешёвые шаги:

1. **Исправить запросы**: индексы, никаких [N+1](/ru/architecture/api-styles/#как-они-сравниваются) (загрузки связанных строк по одному запросу), никаких неограниченных запросов; пул соединений.
2. **Кэшировать чтения**: в Redis рядом с приложением и в CDN для публичных ответов.
3. **Реплики для чтения**: копии, которые обслуживают чтение. Цена — отставание репликации и устаревшие чтения ([согласованность](/ru/data/consistency/#копии-и-модели-согласованности)).
4. **Основная база помощнее**: вертикальное масштабирование очень далеко вытягивает запись.
5. **Разделение по нагрузке**: аналитика — в хранилище для аналитики, поиск — в поисковый движок, данные каждого сервиса — в его собственную базу.
6. **Шардинг**: разделение данных по ключу (tenant — компания-клиент — или пользователь) между несколькими основными базами. Выбирайте ключ так, чтобы большинство запросов оставалось внутри одного шарда. Перешардировать потом трудно, и многим приложениям это никогда не понадобится.

**Запись масштабировать труднее, чем чтение.** Чтение можно обслуживать с копий, но конфликтующие записи в одни и те же данные нужно выстроить в один порядок: через одного лидера, который владеет этими данными, через координацию между копиями (что стоит задержки) или приняв конфликты и разрешая их позже ([согласованность](/ru/data/consistency/)).

Следите за **горячими точками**: один товар на распродаже, один аккаунт знаменитости, один популярный ключ кэша. Вся нагрузка ложится на один шард или один ключ, сколько бы ни было машин. Для горячего **чтения** помогают репликация горячих данных и объединение одинаковых запросов в один ([request coalescing](/ru/architecture/caching/), объединение запросов). С горячей **записью** сложнее: реплики не помогают, потому что запись всё равно принадлежит одному месту. Распределяйте запись по нескольким ключам, когда смысл это позволяет (счётчик, разбитый на десять частей, которые складываются при чтении), или ставьте записи в очередь и обрабатывайте по порядку, с лимитами.

## Выход на весь мир

Для пользователей по всему миру масштабируйтесь в таком порядке:

1. Статические файлы и кэшируемые страницы на CDN: бо́льшая часть выигрыша по задержке при небольшой сложности.
2. Серверы приложения в нескольких регионах с **репликами для чтения** в каждом регионе. Запись по-прежнему идёт в один основной регион.
3. Данные, **разделённые по регионам** (данные пользователей из ЕС — в ЕС), что ещё и помогает с законами о размещении данных.
4. **Запись в каждом регионе.** Либо **скоординированная** (регионы договариваются до подтверждения записи: данные остаются строго согласованными, но каждая запись ждёт round trip между регионами), либо **независимая** (каждый регион подтверждает сразу, а конфликтующие записи разрешаются позже). В любом случае это самый сложный вариант.

Каждый шаг добавляет стоимость и проблемы с согласованностью. Большинству приложений хорошо служит один регион плюс CDN.

## Типичные проблемы

- **Масштабирование не того слоя.** Больше серверов приложения, когда узкое место — база данных: больше соединений, результат хуже.
- **Состояние в памяти**, которое ломается, как только появляется второй инстанс.
- **Исчерпание пула соединений.** 50 инстансов × 20 соединений = 1000 соединений с базой.
- **Автомасштабирование без лимитов**, которое перегружает базу или приносит огромный счёт; или масштабирование, слишком медленное для известного пика.
- **[Retry storms](/ru/architecture/reliability/#повторы-ограниченные-разнесённые-и-безопасные)** (шторм повторов): клиенты одновременно повторяют неудачные запросы и умножают нагрузку на систему, которой и так тяжело.
- **Горячие ключи и горячие шарды.**
- **Неограниченные запросы и выгрузки** без пагинации.
- **Шардинг или [микросервисы](/ru/architecture/application-boundaries/) «ради масштаба»** задолго до того, как этого потребуют цифры.
- **Нет нагрузочного тестирования.** Первым настоящим тестом становится самый большой день распродаж.

## Как выбирать

1. **Измерьте**: где узкое место и какую нагрузку вы ожидаете в пик и через год?
2. **Делайте меньше работы**: кэш, CDN, предварительные вычисления, исправленные запросы.
3. **Сделайте слой приложения без состояния** и масштабируйте его горизонтально за балансировщиком или используйте платформу, которая сделает это за вас.
4. **Масштабируйте базу вверх**, используйте пул соединений и добавьте реплики для чтения при нагрузке, где много чтения.
5. **Разделите нагрузки**: поиск, аналитика и фоновая работа уходят в свои системы.
6. **Шардируйте или выходите в несколько регионов**, только когда этого требуют цифры.

Закладывайте запас на пики и проводите нагрузочное тестирование перед большими событиями.

## Ландшафт

- **Балансировщики нагрузки:** Nginx, HAProxy, Envoy, Traefik; облачные балансировщики (AWS ALB и NLB, Google Cloud Load Balancing, Azure Front Door), Cloudflare Load Balancing.
- **Автомасштабирование:** Kubernetes Horizontal Pod Autoscaler, KEDA (масштабирование по длине очереди и другим событиям), облачные группы автомасштабирования; serverless-платформы масштабируются сами.
- **Данные:** Redis и Valkey, Memcached, реплики для чтения в управляемых базах, пулеры соединений (PgBouncer, Amazon RDS Proxy, Supavisor), слои шардинга (Vitess для MySQL, Citus для PostgreSQL).
- **Нагрузочное тестирование:** k6, Gatling, Locust, Apache JMeter, Artillery.
- **Для изучения:** System Design Primer.
