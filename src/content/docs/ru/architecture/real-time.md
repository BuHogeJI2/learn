## Какую проблему решает

HTTP — это запрос и ответ: сервер может ответить, только когда клиент спрашивает ([HTTP](/ru/web-platform/http/)). Но многим функциям нужно, чтобы сервер сам сообщал что-то новое:

- сообщения чата, уведомления, счёт матчей и цены в реальном времени;
- «ваша выгрузка готова» после [фоновой задачи](/ru/architecture/background-jobs/);
- дашборды, совместное редактирование, мультиплеер;
- ответы AI, которые приходят слово за словом.

Вопросы такие: насколько свежими должны быть данные, какая сторона говорит и сколько стоит держать данные свежими для каждой открытой вкладки?

Не путайте это с фоновой работой. Доставка в реальном времени **уведомляет клиентов**; работе, которую нельзя потерять, место в очередях.

## Ментальная модель: кто начинает и сколько живёт соединение

```
Polling        client: "anything new?"   server: "no."            …again every N seconds
Long polling   client: "anything new?"   server waits … "yes, here it is"  → client asks again
SSE            client opens one HTTP response; the server keeps writing events into it
WebSocket      one upgraded connection; both sides send messages at any time
```

Это отдельные компромиссы, а не лестница. Только у polling есть встроенная задержка; остальные три доставляют почти сразу. Они различаются **направлением** (кто может отправлять), **накладными расходами на запрос** для каждого обновления и тем, сколько долгоживущих **потоков** сервер держит открытыми. Поток — не всегда отдельное сетевое соединение: в HTTP/2 и HTTP/3 много потоков делят одно соединение, хотя серверы всё равно ограничивают, сколько потоков может нести одно соединение.

## Варианты

| | Polling (опрос) | Long polling (долгий опрос) | SSE (Server-Sent Events) | WebSocket |
| --- | --- | --- | --- | --- |
| **Направление** | Клиент забирает сам | От сервера к клиенту, один ответ на запрос | От сервера к клиенту | В обе стороны |
| **Задержка обновления** | До длины интервала | Почти нет | Почти нет | Почти нет |
| **Соединение** | Новый запрос каждый раз | Держится открытым до события или таймаута | Один долгий HTTP-ответ | Одно долгоживущее соединение |
| **Протокол** | Обычный HTTP | Обычный HTTP | Обычный HTTP, `text/event-stream` | Собственный протокол после HTTP «upgrade» (`wss://`, WebSocket поверх TLS) |
| **Переподключение и пропущенные события** | Каждый опрос получает текущее состояние; чтобы получить *каждое* событие, нужен курсор | Ваш код | `EventSource` переподключается и отправляет `Last-Event-ID`, если у событий есть ID; досылать пропущенное — задача сервера | Ваш код |
| **Работа с существующей HTTP-инфраструктурой** (cookies, прокси, [CDN](/ru/web-platform/cdn/)) | Да | В основном | В основном; прокси, которые буферизуют ответы, его ломают | Нужна отдельная настройка; некоторые прокси и файрволы его блокируют |
| **Нагрузка на сервер** | Много запросов | Много удерживаемых запросов | Один открытый поток на клиента | Одно открытое соединение на клиента |
| **Подходит для** | Редких обновлений, небольшого числа пользователей, простоты | Запасного варианта, когда ничего другого не работает | Уведомлений, лент, прогресса, стриминга ответов AI | Чата, совместной работы, игр, частых сообщений в обе стороны |

Важные детали:

- **SSE в браузере.** Встроенный `EventSource` делает только `GET`-запросы и не может задавать свои заголовки, поэтому аутентификация идёт через cookies. Многие приложения читают тот же формат потока событий через `fetch`, который позволяет `POST` и заголовки; так стримят ответы большинство AI-чатов. С `fetch` переподключение и отправка последнего ID события — задача вашего кода.
- **SSE и HTTP/1.1.** Каждый поток SSE занимает соединение, а по HTTP/1.1 браузеры разрешают около шести соединений на один origin (схема + хост + порт). Несколько открытых вкладок могут заблокировать все остальные запросы. В [HTTP/2 и HTTP/3](/ru/web-platform/http/#версии-http-смысл-тот-же-транспорт-разный) потоки делят одно соединение, и этот лимит исчезает (серверы всё равно ограничивают число потоков на соединение).
- **WebSocket — голая труба.** В протоколе есть кадры ping и pong, но браузерный API не позволяет вашему коду их отправлять, и в нём нет встроенных переподключения, расписания heartbeats (периодических сигналов «я жив»), подтверждений сообщений или каналов (именованных тем, на которые подписывается клиент). Библиотеки вроде Socket.IO добавляют их со своим протоколом поверх.
- **Более новые и другие инструменты:** WebTransport (поверх HTTP/3, несколько потоков и ненадёжные сообщения — для игр и медиа), WebRTC (прямые peer-to-peer аудио, видео и данные) и Web Push (уведомления, когда страница вообще не открыта).

## Соединение оборвётся

Мобильные сети переключаются, ноутбуки засыпают, [деплои](/ru/delivery/deployment-models/#релизы-от-коммита-до-пользователей) перезапускают серверы. Проектируйте переподключения с самого начала:

- **Переподключайтесь с backoff и jitter** (растущими и случайными паузами между попытками; [повторы](/ru/architecture/reliability/#повторы-ограниченные-разнесённые-и-безопасные)). Иначе, когда сервер перезапускается, все его клиенты переподключаются в одну и ту же секунду.
- **Возобновляйте, а не просто переподключайтесь.** Дайте каждому событию ID или порядковый номер. При переподключении клиент отправляет последний увиденный ID, и сервер досылает пропущенное из своей истории. Если этот ID старше истории, которую хранит сервер, клиент загружает текущее состояние. Такая загрузка не должна оставлять разрыв: снимок должен приходить с позицией последнего события, которое в него вошло, чтобы поток продолжился ровно оттуда (или сначала подпишитесь и буферизуйте события, затем загрузите снимок и примените более новые события из буфера).
- **Считайте сообщения подсказками.** Простой подход: сообщение «заказ 42 изменился» заставляет клиент инвалидировать и перезапросить эти данные ([чтение серверного состояния](/ru/architecture/state/#чтение)), а источником истины остаётся сервер. Он самовосстанавливается, только если перезапросы запускает ещё что-то, потому что за потерянным *последним* сообщением другое уже не придёт: перезапрашивайте при переподключении и при фокусе окна, а там, где это важно, — периодически.
- **Heartbeats.** Отправляйте небольшое сообщение каждые несколько десятков секунд, чтобы прокси не закрыли соединение как простаивающее. Чтобы обнаружить мёртвое соединение, ожидайте ответа или какой-то активности в пределах дедлайна: сама отправка может успешно уйти в буфер, даже когда другой стороны уже нет.
- **Дубликаты и нарушение порядка** могут появиться вокруг переподключений. ID событий позволяют клиенту отбрасывать дубликаты. Номер версии позволяет игнорировать более старое **полное состояние** той же записи; но отдельные сообщения и правки (два сообщения чата, два изменения) нужны все, поэтому пропущенные нужно получить или дослать, а не пропустить.

## Fan-out: одно событие, много соединений

Каждый сервер держит соединения своих клиентов. Событие, произошедшее на сервере A, должно дойти до пользователей, подключённых к серверам B и C:

```
event ──► pub/sub (Redis, NATS, a broker) ──┬─► server A ──► its open connections
                                            ├─► server B ──► its open connections
                                            └─► server C ──► its open connections
```

- Серверам нужна **pub/sub-шина** между ними ([формы обмена сообщениями](/ru/architecture/background-jobs/#три-формы-обмена-сообщениями)).
- **Каждое открытое соединение стоит памяти** и сетевого сокета на сервере, даже когда ничего не отправляется.
- **Медленные клиенты.** Вкладка в плохой сети получает сообщения медленнее, чем они создаются, и буфер сервера для неё растёт. Ограничьте буфер на клиента, объединяйте обновления, которые заменяют друг друга, и отключайте клиентов, которые слишком отстали, чтобы они пересинхронизировались.
- **[Балансировка нагрузки](/ru/architecture/scaling/#балансировка-нагрузки) неравномерная**: соединения остаются на сервере, где они начались. После масштабирования новые серверы простаивают, пока клиенты не переподключатся; во время деплоя старые серверы должны закрывать соединения постепенно, чтобы клиенты переехали без шторма.
- **Serverless-функции** обычно не могут держать соединения ([что переживает перезапуск](/ru/delivery/deployment-models/#состояние-что-переживает-перезапуск)). Используйте постоянно работающие серверы, управляемый сервис реального времени или платформу, созданную для соединений.
- **Безопасность живёт столько же, сколько соединение.** Handshake WebSocket не защищён CORS, а handshake с cookies можно начать с другого сайта, поэтому проверяйте заголовок `Origin` по списку доверенных origin ([границы браузера](/ru/security/browser-boundaries/)). Это дополняет аутентификацию, а не заменяет её: клиенты вне браузера могут подделать заголовок. Проверяйте права при подключении, при каждой подписке на канал и для каждого действия, которое отправляет клиент ([авторизация](/ru/security/auth/#авторизация-проверка-того-что-разрешено)). Токены и права могут измениться за время соединения, которое длится часами; проверяйте заново или закрывайте соединение. Никогда не отправляйте приватные данные в общий канал с фильтрацией в браузере.

## Типичные проблемы

- **Каждая вкладка опрашивает сервер каждую секунду.** Поток запросов, который вы устроили сами себе. Опрашивайте реже, ставьте опрос на паузу в фоновых вкладках (Page Visibility API) и делайте опросы дешёвыми с помощью `ETag` и `304` ([HTTP-кэширование](/ru/architecture/caching/#http-кэширование-общий-язык)).
- **Предположение, что соединение останется открытым.** Без возобновления UI после переключения сети молча показывает старые данные.
- **Штормы переподключений** после деплоя или аварии.
- **Прокси и CDN, которые буферизуют** ответ SSE или закрывают простаивающие соединения.
- **Много потоков SSE по HTTP/1.1**, которые исчерпывают лимит соединений.
- **Проверка прав только при подключении.**
- **Рассылка всего всем с фильтрацией на клиенте**, из-за которой утекают данные.
- **WebSockets для данных, которые меняются раз в несколько минут**, где polling или SSE были бы проще.
- **Отношение к сообщениям реального времени как к надёжным.** Пользователь, который офлайн, их пропустит. Всё, что должно дойти до пользователя, попадает в сохраняемый inbox (входящие) — источник истины; push-уведомление может указывать на него, но сама доставка push не гарантирована.

## Как выбирать

- **Обновления раз в несколько минут или небольшое устаревание допустимо:** polling или перезапрос, когда окно получает фокус.
- **Сервер стримит клиенту** (уведомления, прогресс, ленты, ответы AI): SSE.
- **Частые сообщения в обе стороны с малой задержкой** (чат с индикатором набора, совместное редактирование, мультиплеер): WebSocket.
- **Не хотите держать серверы соединений:** управляемый сервис реального времени.
- **Пользователь должен получить сообщение даже при закрытой странице:** сохраняемый inbox плюс Web Push или мобильные push-уведомления как способ сообщить о нём без гарантии доставки.
- **Совместное редактирование:** WebSocket плюс CRDT-библиотека, которая сливает одновременные правки ([одновременные изменения](/ru/architecture/state/#одновременные-изменения)).

## Ландшафт

- **API браузера:** `EventSource`, `WebSocket`, `fetch` с потоковыми ответами, WebTransport, Web Push, Page Visibility API.
- **Серверы и библиотеки:** Socket.IO, `ws` и uWebSockets.js (Node.js), Phoenix Channels (Elixir), SignalR (.NET), Centrifugo; подписки GraphQL.
- **Управляемые сервисы:** Pusher, Ably, PubNub, Supabase Realtime, слушатели Firebase, AWS AppSync, Cloudflare Durable Objects; Liveblocks и PartyKit для совместной работы.
- **Sync engines (движки синхронизации), скрывающие транспорт:** Zero, Replicache, ElectricSQL, Convex.
- **Данные для совместной работы:** Yjs, Automerge.
