## Какую проблему решает

API — это **контракт** между частями, которые создаются, деплоятся и меняются отдельно: фронтендом и бэкендом, двумя сервисами, вашей системой и системой партнёра. Контракт говорит, что клиент может запросить, что он получит в ответ и как выглядят ошибки.

Стиль API определяет форму этого контракта, а через неё:

- сколько запросов нужно экрану,
- что кэши, прокси и инструменты могут понять без специальной работы,
- как сообщается об ошибках и как их повторять,
- насколько сложно потом менять API, не ломая клиентов.

## Ментальная модель: три способа задать форму контракта

| Стиль | Клиент мыслит в терминах | Пример | Контракт задаётся |
| --- | --- | --- | --- |
| **Ресурсы** (REST) | Существительных и стандартных глаголов | `GET /orders/42`, `POST /orders` | URL, [HTTP-методами и статус-кодами](/ru/web-platform/http/#методы-что-обещает-запрос); часто описывается в OpenAPI |
| **Запросы** (GraphQL) | Графа типов; запрашивает точные поля | `{ order(id: 42) { total items { name } } }` | Типизированной схемой |
| **Процедуры** (RPC, remote procedure call — удалённый вызов процедур) | Вызовов функций | `orders.get({ id: 42 })`, `CreateOrder(request)` | Сигнатурами функций: Protocol Buffers (gRPC), типами TypeScript (tRPC) |

Одни и те же данные можно отдавать во всех трёх стилях. Разница в том, **кто решает, какой формы будет ответ**:

- В **REST** форму каждого ресурса решает сервер.
- В **GraphQL** клиент выбирает нужные поля в пределах того, что разрешает схема.
- В **RPC** сервер определяет операции, и API выглядит как код, который за ним стоит.

## Как они сравниваются

| | REST | GraphQL | RPC |
| --- | --- | --- | --- |
| Форма ответа | Фиксирована для ресурса | Выбирается клиентом | Фиксирована для процедуры |
| Over- и under-fetching (слишком много данных или слишком много вызовов) | Часто: экрану нужны части нескольких ресурсов | Решено by design: один запрос, точные поля | Зависит от того, как спроектированы процедуры |
| HTTP-кэширование | Нативное: URL с `GET` работают с [кэшами браузера и CDN](/ru/architecture/caching/) | Слабое по умолчанию: обычно `POST` на один URL. Запросы можно отправлять через `GET` и кэшировать как любой URL (persisted queries — запросы, заранее сохранённые на сервере и отправляемые по ID, — делают URL короткими и стабильными); иначе работу делает клиентский кэш | Слабое: обычно `POST` |
| Ошибки | HTTP статус-коды плюс тело, в идеале в стандартном формате вроде RFC 9457 | Обычно `200 OK` со списком `errors`; возможны частичные данные | Собственные коды (у gRPC фиксированный набор) |
| Типы и инструменты | OpenAPI, затем кодогенерация | Схема типизирована by design; кодогенерация из неё | gRPC: сгенерированный код для многих языков; tRPC: общие типы TypeScript, без генерации |
| Поддержка в браузере | Да | Да | tRPC и JSON-RPC: да; gRPC нужен gRPC-Web или Connect |
| Типичные риски | Много эндпоинтов, которые нужно защищать и держать согласованными | Дорогие или злонамеренные запросы; медленная загрузка вложенных данных (N+1); проверки доступа для каждого поля | Сильная связанность кода клиента и сервера |

**Проблема N+1** в GraphQL: запрос на 50 заказов с их покупателями может выполнить 1 запрос за заказами плюс 50 запросов за покупателями. Слой батчинга (DataLoader) собирает их в один.

**Server actions** (серверные функции, которые генерирует фреймворк, как в Next.js) — это замаскированный RPC: фреймворк создаёт `POST`-эндпоинт для каждой функции. Это всё равно публичные эндпоинты. Их может вызвать напрямую кто угодно, поэтому им нужны валидация входных данных и проверка прав, как любому API.

## Развитие: долгосрочная цена

Написать API быстро; дорого обходится изменение его без поломки клиентов. Важнее всего это тогда, когда вы не контролируете, когда клиенты обновляются: мобильные приложения, которые пользователи никогда не обновляют, партнёры, другие команды.

**Обычно безопасно (добавление):**

- добавить новый эндпоинт, поле или необязательный параметр;
- добавить новое значение, которое клиенты готовы игнорировать.

**Breaking changes (ломающие изменения):**

- удалить или переименовать поле;
- изменить тип или смысл значения;
- сделать необязательный параметр обязательным;
- изменить коды ошибок, на которые реагируют клиенты.

Стратегии:

- **Expand and contract** (расширить, затем сузить): добавить новую форму, перевести клиентов, следить за использованием и удалить старую форму, только когда ею никто не пользуется.
- **Версионирование**: `/v2/` в URL или заголовок с версией. Это обычно для публичных REST API. GraphQL обычно обходится без версий: схема развивается, а старые поля помечаются `@deprecated` и отслеживаются, пока не перестанут использоваться.
- **Tolerant reader** (терпимый читатель): клиенты игнорируют неизвестные им поля, поэтому серверы могут свободно добавлять поля.
- **Проверки контракта в CI**: инструменты сравнивают новую схему со старой и падают на ломающих изменениях (инструменты diff для OpenAPI, реестры схем GraphQL, `buf breaking` для Protocol Buffers).

## Границы ошибок

Не все ошибки одинаковы, и контракт должен делать разницу явной:

| Вид | Пример | Что делает клиент |
| --- | --- | --- |
| Транспортные | Нет сети, таймаут | Возможно, повторить |
| Протокольные | `401`, `404`, `429`, `503` | Реагирует на класс: войти, показать «не найдено», подождать и повторить |
| Доменные | «Недостаточно товара на складе», «Email уже используется» | Показать конкретное сообщение; повтор не поможет |

Хорошие доменные ошибки **читаются машиной** (стабильный код), **читаются человеком** (сообщение) и указывают на **поле**, в котором ошибка.

Повторять `POST` опасно: если первый запрос на самом деле выполнился и потерялся только ответ, повтор создаст второй заказ. Обычное решение — **idempotency key** (ключ идемпотентности): клиент отправляет с запросом уникальный ID, и сервер игнорирует повторы с тем же ID.

## Для кого API

- **Публичный API для неизвестных клиентов:** важнее всего стабильность и документация. REST с OpenAPI — общий знаменатель, который понимают все языки и инструменты.
- **Ваш собственный фронтенд:** API меняется вместе с UI. GraphQL, tRPC или серверные функции фреймворка держат их в согласии.
- **Сервис-сервис внутри вашей системы:** важны производительность, строгие типы и стриминг. Частый выбор — gRPC.
- **BFF** (backend for frontend — бэкенд для фронтенда) — тонкий серверный слой для одного клиента: он вызывает внутренние API и возвращает ровно то, что нужно одному экрану или приложению.

## Типичные проблемы

- **RPC, переодетый в REST.** `POST /getUser` и `POST /deleteUser` не дают ни кэширования, ни семантики REST. Это нормально, если это осознанный выбор, и запутывает, если нет.
- **GraphQL без ограничений.** Клиент может отправить глубоко вложенный запрос, который положит сервер. Добавьте ограничения глубины и стоимости или разрешите только известные (persisted) запросы.
- **Запросы N+1** за резолверами GraphQL или REST-эндпоинтами, которые загружают связанные данные по одной строке.
- **Выкатка ломающего изменения до того, как обновились клиенты.**
- **`200 OK` с ошибкой внутри** для REST API: мониторинг видит успех, а кэши сохраняют ошибку.
- **«Болтливые» API.** Экрану нужно 15 вызовов цепочкой; каждый добавляет round trip (путь до сервера и обратно). Объединяйте их на сервере (BFF, GraphQL).
- **Модель базы данных наружу.** Когда клиенты зависят от структуры ваших таблиц, вы не можете менять базу данных.

## Как выбирать

- **Публичный API со множеством неизвестных клиентов:** REST с OpenAPI.
- **Много разных клиентов, которым нужны разные формы богатых связанных данных** (веб и мобильные приложения, несколько команд): GraphQL.
- **Full-stack TypeScript, одна команда, фронтенд и бэкенд в одном репозитории:** tRPC или серверные функции фреймворка.
- **Внутренние сервисы на разных языках, высокая нагрузка, стриминг:** gRPC.

Стили хорошо сочетаются: gRPC между внутренними сервисами, GraphQL или REST на границе для клиентов.

## Ландшафт

- **REST:** OpenAPI (Swagger) для описания и кодогенерации; JSON:API как соглашение о формате ответов; фреймворки Express, Fastify, Hono, NestJS.
- **GraphQL:** Apollo Server и Client, GraphQL Yoga, Relay, Hasura; Apollo Federation для объединения схем нескольких сервисов.
- **RPC:** gRPC и Connect, tRPC, oRPC, JSON-RPC; серверные функции в Next.js и других фреймворках.
- **Инструменты:** Postman, Bruno, Insomnia, GraphiQL. AsyncAPI описывает API на событиях (сообщениях) так же, как OpenAPI описывает HTTP API.
