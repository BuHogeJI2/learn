## Какую проблему решает

Запрос проходит долгий путь: браузер → сеть → [CDN](/ru/web-platform/cdn/) (сеть серверов рядом с пользователями, которые хранят копии вашего контента) → сервер приложения → база данных, и обратно. Каждый шаг стоит времени, а последние шаги (рендеринг, запросы к базе) стоят ещё и денег, и ресурсов.

Кэш хранит копию результата **ближе к месту, где она нужна**, поэтому повторная работа пропускается. Он даёт две вещи:

- **Скорость**: пользователь получает ответ из более близкого и быстрого места.
- **Защиту origin** (сервера, где лежат исходные данные): сервер и база данных делают меньше работы, поэтому система выдерживает больше трафика за меньшие деньги.

Цена всегда одна и та же: **копия может устареть**, и теперь вам нужно решать, когда её выбросить. Большинство ошибок кэширования — именно об этом решении.

## Ментальная модель: четыре вопроса к любому кэшу

Любой кэш, от браузера до Redis (хранилища ключ-значение в памяти), описывается одними и теми же четырьмя вопросами. Если вы можете на них ответить, вы понимаете этот кэш.

| Вопрос | Смысл | Примеры |
| --- | --- | --- |
| **Ключ** | Что идентифицирует запись? Два запроса с одинаковым ключом получают одинаковый ответ. | URL + заголовки `Vary`; аргументы функции; GraphQL-запрос + переменные |
| **Scope** (кто видит данные) | Кто делит запись между собой? | Один пользователь (браузер), все (CDN, серверный кэш) |
| **Свежесть** | Как долго запись годится без проверки? | `max-age=60`, TTL (время жизни записи) в Redis, `cacheLife('hours')` |
| **Инвалидация** | Как удалить или обновить запись раньше срока? | Purge (принудительный сброс) по URL, purge по тегу, новое имя файла |

**Опаснее всего scope.** Персональный ответ (корзина, имя пользователя), сохранённый в общем кэше, будет показан другим пользователям. Это частый реальный инцидент, а не теория.

## Слои

```
 Browser (one user)              Edge (shared)        Your servers (shared)        Data
┌──────────────────────────┐    ┌─────────────┐     ┌──────────────────────────┐   ┌──────────┐
│ 1. App memory            │    │ 4. CDN      │     │ 5. Application cache     │   │ 6. DB    │
│    (Apollo, TanStack     │───►│    cache    │────►│    (in-process LRU,      │──►│  buffers,│
│    Query, router cache)  │    │             │     │    Redis, framework      │   │  views   │
│ 2. HTTP cache            │    │             │     │    data cache)           │   │          │
│ 3. Service Worker cache  │    └─────────────┘     └──────────────────────────┘   └──────────┘
└──────────────────────────┘
```

| Слой | Scope | Чем управляется | Типичное содержимое |
| --- | --- | --- | --- |
| 1. Память приложения | Одна вкладка | Ваш JS-код / клиентская библиотека | Ответы API, нормализованные сущности |
| 2. HTTP-кэш браузера | Один пользователь | Заголовки ответа `Cache-Control`, `ETag` | JS/CSS/картинки, некоторые ответы API |
| 3. Service Worker (скрипт, который браузер запускает между страницей и сетью) | Один пользователь | Код вашего service worker | Офлайн-страницы, оболочка приложения |
| 4. CDN / edge (серверы на краю сети, рядом с пользователями) | Все пользователи | Заголовки (`s-maxage`), правила CDN, purge API | Статические файлы, публичный HTML и ответы API |
| 5. Кэш приложения | Все пользователи (на инстанс или общий) | Код вашего сервера | Результаты запросов, отрендеренные фрагменты, сессии |
| 6. База данных | Все пользователи | Сама БД, материализованные представления | «Горячие» страницы в памяти, предвычисленные результаты |

Чем ближе слой к пользователю, тем он быстрее и тем сложнее его инвалидировать. Можно сделать purge в CDN или Redis, но **нельзя** залезть в браузер пользователя и удалить запись. Поэтому кэширование в браузере полагается на время и на имена файлов, а не на purge.

## HTTP-кэширование: общий язык

Слоями 2 и 4 управляют [HTTP-заголовки](/ru/web-platform/http/#заголовки-метаданные-которые-управляют-поведением), и большинство фреймворков переводят свои настройки в эти заголовки. Поэтому основные из них стоит знать.

**Директивы `Cache-Control`:**

- `max-age=N`: запись свежая N секунд в любом кэше.
- `s-maxage=N`: то же самое, но только для общих кэшей (CDN). Позволяет задать браузеру и CDN разное время жизни.
- `no-cache`: сохранять можно, но перед каждым использованием нужно проверить у сервера. Название вводит в заблуждение: оно **не** означает «не кэшировать».
- `no-store`: нигде не сохранять. Для чувствительных данных.
- `private`: сохранять может только браузер, никогда не CDN. Для персонализированных ответов.
- `public`: общие кэши могут сохранить ответ, даже когда обычно бы не стали (например, ответ на запрос с заголовком `Authorization`).
- `stale-while-revalidate=N`: после истечения срока ещё до N секунд отдавать старую копию, параллельно получая новую в фоне.
- `immutable`: содержимое по этому URL никогда не изменится; даже не перепроверять.

**Ревалидация.** Когда сохранённая копия устарела, кэшу не обязательно скачивать всё заново. Он спрашивает: «У меня версия X, она ещё актуальна?» через `If-None-Match` (с `ETag`) или `If-Modified-Since`. Если ничего не изменилось, сервер отвечает `304 Not Modified` без тела. Это экономит трафик, но не сам сетевой запрос туда и обратно.

**`Vary`** добавляет заголовки запроса в ключ кэша. `Vary: Accept-Language` хранит отдельную копию для каждого языка. `Vary: Cookie` обычно убивает hit rate (долю попаданий в кэш), потому что у каждого пользователя свои cookies.

**Классическая схема для веб-приложения:**

- Статические файлы с хэшем в имени (`app.3f9a1c.js`): `max-age=31536000, immutable`. Когда содержимое меняется, меняется имя файла, поэтому инвалидация не нужна вообще.
- HTML: `no-cache` (всегда перепроверять) или короткий `s-maxage` со `stale-while-revalidate` в CDN. HTML ссылается на файлы с хэшами, поэтому свежий HTML означает свежий код.

## Стратегии свежести

1. **По времени (TTL).** Запись истекает через N секунд. Просто и предсказуемо, но вы принимаете до N секунд устаревших данных и платите за обновления, даже когда ничего не изменилось.
2. **Stale-while-revalidate** (отдавать устаревшее, пока обновляется). После истечения срока кэш сразу отвечает старой копией и обновляет её в фоне. Пользователи почти никогда не ждут, но кто-то один раз видит немного устаревшие данные.
3. **Инвалидация по событию.** Когда данные меняются, вы явно удаляете связанные записи: по ключу, по URL или по **тегу** (например, все записи с тегом `product:42`). Данные становятся свежими почти сразу, но нужно знать, какие записи от каких данных зависят. Теги делают это управляемым.
4. **Версионированные ключи.** Никогда не инвалидировать, а менять ключ (хэш в имени файла, номер версии в ключе). Самый надёжный способ, но работает только там, где вы управляете ссылкой на ключ.

На практике их комбинируют: длинный TTL как страховка плюс инвалидация по событию при изменении. Например, контент из CMS кэшируется «навсегда» с тегами, а webhook при публикации делает purge по тегу.

**Паттерны для серверных кэшей:**

- **Cache-aside** (самый распространённый): приложение проверяет кэш; при промахе читает БД и записывает результат в кэш.
- **Write-through**: каждая запись идёт в кэш и в БД одновременно, поэтому при чтении кэш всегда «прогрет».
- **Write-behind**: запись сначала идёт в кэш, а в БД попадает позже. Быстро, но можно потерять данные, поэтому в веб-приложениях встречается редко.

## Типичные проблемы

- **Приватные данные в общем кэше.** Персонализированный ответ без `private` или `no-store` попадает в кэш CDN. Решение: явно помечать персонализированные ответы и разносить публичные и персональные данные по разным запросам.
- **Cache stampede (thundering herd, «набег» на источник).** Популярная запись истекает, и тысячи запросов одновременно промахиваются и вместе идут в базу данных. Решения: stale-while-revalidate, request coalescing (объединение запросов: обновляет только один запрос, остальные ждут), случайный jitter (разброс) для TTL или обновление по событиям вместо обновления по времени.
- **Низкий hit rate.** Ключи слишком специфичные, поэтому записи редко переиспользуются. Типичные причины: параметры трекинга (`?utm_source=…`) в URL, `Vary: Cookie`, метки времени в ключах. Нормализуйте ключи и измеряйте hit rate, прежде чем доверять кэшу.
- **Накопленное устаревание.** У кэшей браузера, CDN и сервера свой TTL, поэтому в худшем случае данные устарели на их сумму. Для отладки смотрите заголовки ответа: `Age` (сколько секунд копия лежит в общем кэше) и заголовок статуса CDN (`x-vercel-cache`, `cf-cache-status`, `x-cache`) показывают, какой слой ответил.
- **Холодный кэш после деплоя.** Многие кэши привязаны к деплою или к памяти процесса. После деплоя или перезапуска первые запросы медленные, а origin получает всплеск нагрузки.

## Когда кэшировать, а когда нет

Кэширование окупается, когда данные:

- **Читаются гораздо чаще, чем пишутся**,
- **Дорогие** в вычислении или получении,
- **Общие** для многих пользователей,
- **Допускают устаревание** на какое-то время.

Избегайте кэширования (или делайте его персональным и коротким), когда данные:

- **Должны быть точно актуальными**: балансы, остатки товара при оформлении заказа, права доступа.
- **Дешёвые и персональные**: кэш добавляет сложность и почти ничего не даёт взамен.
- **Редко переиспользуются**: hit rate будет близок к нулю.

Хороший порядок рассуждений: сначала сделать ответ кэшируемым средствами HTTP (бесплатно и стандартно), затем добавить CDN, и только потом добавлять кэши на уровне приложения там, где замеры показывают необходимость.

## Ландшафт

- **Браузер:** HTTP-кэш (встроенный), Cache API вместе с Service Workers, клиентские библиотеки данных (Apollo Client, TanStack Query, SWR, RTK Query).
- **CDN / edge:** Cloudflare, Fastly, Akamai, Amazon CloudFront, edge-сети Vercel и Netlify.
- **Reverse proxy:** Varnish, Nginx `proxy_cache`.
- **Кэши приложения:** Redis и Valkey, Memcached, LRU-кэши внутри процесса (первыми удаляют записи, которые дольше всех не использовались); кэши фреймворков, например [директива `use cache` в Next.js](/ru/tools/nextjs/caching/).
- **Уровень базы данных:** buffer pools (автоматически), материализованные представления, read replicas (реплики для чтения). Реплика — не кэш, но она решает похожую проблему «слишком много чтений».
