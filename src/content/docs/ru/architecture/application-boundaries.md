## Какую проблему решает

Когда продукт растёт, всё больше людей работает со всё большим количеством кода. Появляются вопросы, на которые стиль кода не отвечает:

- Кто может что-то менять, не дожидаясь других команд?
- Что должно деплоиться вместе?
- Что падает вместе?
- Кто владеет какими данными?

**Границы** — это линии между частями системы. Если их слишком мало, всё превращается в один клубок, и каждое изменение задевает всё. Если слишком много, простые фичи требуют сетевых вызовов между сервисами, а сбои распространяются неожиданными путями.

## Ментальная модель: три вида границ

Граница может существовать на трёх уровнях, и их можно выбирать отдельно:

1. **Граница кода** (модуль): какой код может вызывать какой. Обеспечивается языком и инструментами. Переносится дёшево.
2. **Граница деплоя** (единица деплоя): что выпускается, масштабируется и падает вместе. У каждой единицы свой пайплайн, своя версия и своя среда выполнения.
3. **Граница данных**: кто владеет какими таблицами. Остальные части используют API владельца, а не его базу данных.

Над ними стоит **владение**: какая команда отвечает за часть. **Закон Конвея** говорит, что системы в итоге повторяют структуру коммуникаций организации, которая их строит, поэтому границы команд и границы системы тянутся друг к другу.

| | Монолит | Модульный монолит | Сервисы (микросервисы) |
| --- | --- | --- | --- |
| Границы кода | Часто слабые | Сильные, проверяются инструментами | Сильные: отдельные кодовые базы или пакеты |
| Единиц деплоя | Одна | Одна | Много |
| Данные | Одна база, общая для всего кода | Одна база, таблицами владеют модули | Каждый сервис владеет своими данными; другие никогда не читают его таблицы напрямую (отдельные базы или отдельные схемы на общем сервере) |
| Вызовы между частями | Вызовы функций | Вызовы функций через API модулей | Сетевые вызовы |
| Радиус поражения при сбое | Баг или перегрузка может задеть всё приложение | Как у монолита, но владение яснее | Может остаться внутри одного сервиса, если остальные не зависят от него синхронно и обрабатывают его сбои |
| Транзакции между частями | Легко | Легко | Трудно: [саги и идемпотентность](/ru/data/consistency/#между-сервисами-общей-транзакции-нет) |
| Подходит для | Одной или нескольких команд | Нескольких команд, одного продукта | Многих команд, которым нужны независимые релизы |
| Стоимость эксплуатации | Низкая | Низкая | Высокая: деплой, мониторинг, трейсинг, версионирование |

## Варианты разделения

### Монолит

Одно приложение, которое деплоится целиком. Его легко разрабатывать, тестировать, деплоить и отлаживать; рефакторинг по всей кодовой базе — обычное изменение; одна транзакция базы данных покрывает всё. Монолит также масштабируется дальше, чем думают: запустите несколько копий за балансировщиком нагрузки.

Монолиты получают плохую репутацию, когда у них нет **внутренних** границ (big ball of mud — «большой ком грязи»), а не потому, что они деплоятся одной единицей.

### Модульный монолит

Один деплой, но разделение на модули с явными публичными API и своими данными. Правила вроде «модуль биллинга не может импортировать внутренности каталога» проверяются инструментами.

Он даёт большую часть командных преимуществ сервисов (ясное владение, независимая работа внутри модуля) без сетевых вызовов, распределённых сбоев и транзакций между сервисами. Если модулю позже понадобится стать сервисом, линия разреза уже есть. Известный пример — основное приложение Shopify.

### Сервисы и микросервисы

Независимо деплоящиеся сервисы, каждый построен вокруг бизнес-возможности (заказы, платежи, каталог) и владеет своими данными.

Преимущества:

- команды выпускают релизы по своему графику;
- каждый сервис масштабируется отдельно, а его сбои *могут* оставаться внутри него, если вызывающие его сервисы используют таймауты и fallback (запасной вариант);
- каждый может выбрать подходящую ему технологию.

Цена:

- любой вызов может быть медленным или упасть, поэтому нужны таймауты, повторы и идемпотентность;
- нет join и нет транзакций между сервисами;
- изменения API между сервисами должны оставаться совместимыми: добавление вместо изменения, периоды устаревания и, когда нужно, версии ([развитие API](/ru/architecture/api-styles/#развитие-долгосрочная-цена));
- отладка одного запроса пользователя означает следить за ним через много сервисов, а для этого нужен распределённый трейсинг;
- запустить всё локально становится трудно.

Худший случай — **распределённый монолит**: сервисы, которые нужно деплоить вместе или которые читают и пишут таблицы друг друга. Вы платите цену обоих стилей и не получаете преимуществ ни одного.

Заметьте: **serverless-функции** (код, который платформа запускает по запросу, без постоянно работающего сервера) **— это модель деплоя, а не архитектура**: монолит можно запускать как функции, а сервис — в контейнере.

## Где здесь фронтенд: BFF, gateway, микрофронтенды

```
                       ┌──► Orders service
Browser ──► BFF (web) ─┼──► Catalog service
Mobile  ──► BFF (app) ─┼──► Users service
                       └──► …
```

- **API gateway** (шлюз API): одна общая точка входа перед всеми сервисами. Он маршрутизирует запросы и берёт на себя общие задачи: проверку учётных данных, rate limiting (ограничение частоты запросов) и логирование. Он универсальный, и обычно им владеет платформенная команда.
- **BFF** (backend for frontend — бэкенд для фронтенда): серверный слой **для одного вида клиента** (веб, мобильное приложение), которым обычно владеет команда, делающая этот клиент. Он вызывает несколько сервисов и возвращает ровно то, что нужно экрану, хранит токены на сервере ([где живут учётные данные](/ru/security/auth/#где-браузер-хранит-учётные-данные)) и часто рендерит HTML. На практике сервер full-stack фреймворка вроде Next.js часто *и есть* BFF. Слой GraphQL, объединяющий несколько сервисов, — ещё один способ собрать API для клиентов ([Стили API](/ru/architecture/api-styles/)).
- **Микрофронтенды**: UI, разделённый на части, которые разные команды разрабатывают и деплоят независимо, а собираются они при сборке, на сервере или в браузере. Самый дешёвый вариант — разделение **по маршрутам** (каждая команда владеет целыми страницами); разделить одну страницу на части из разных деплоев гораздо сложнее. Они решают организационную проблему: много команд работают над одним UI. Цена — дублирующиеся зависимости, менее единый UX, более сложные общее состояние и маршрутизация и часто худшая производительность. При одной-двух фронтенд-командах они обычно стоят больше, чем дают.

## Типичные проблемы

- **Микросервисы слишком рано.** Небольшая команда с неясной предметной областью проводит границы не там, и переносить их теперь дорого, потому что это сетевые API.
- **Разделение по техническим слоям** («фронтенд-сервис», «сервис базы данных») вместо бизнес-возможностей. Тогда каждая фича задевает каждый сервис.
- **Сервисы читают таблицы друг друга.** Скрытая связанность: изменение схемы одной командой ломает сервис другой. Общий *сервер* базы данных — нормально; проблема в общих *таблицах*.
- **«Болтливые» сервисы.** Один запрос пользователя вызывает двадцать синхронных вызовов. Задержки складываются, а доступность перемножается: если все двадцать обязательны и падают независимо, двадцать сервисов по 99,9% каждый дают около 98% на весь запрос.
- **Монолит без внутренних границ**, который потом «чинят» разделением на сервисы по тем же запутанным линиям.
- **Общая библиотека «common»**, от которой зависят все сервисы, так что выпускать их приходится вместе.
- **Микрофронтенды для одной команды.**
- **Каждый сервис проверяет права по-своему.**

## Как выбирать

- **Начинайте с монолита, лучше модульного.** Мартин Фаулер называет это «monolith first»: вы узнаёте, где настоящие границы, до того как сделать их дорогими для переноса.
- **Выносите сервис по конкретной причине:**
  - часть с сильно отличающимися требованиями к масштабу или надёжности (обработка видео, поиск);
  - команда, которой нужен свой график релизов;
  - изоляция ради безопасности или требований регуляторов (платежи);
  - другая технология, которую основное приложение использовать не может.
- **Проводите границы по бизнес-возможностям и владению данными.** В Domain-Driven Design такая область называется **bounded context** (ограниченный контекст): часть бизнеса, где у каждого термина один смысл («товар» в каталоге и «товар» на складе — разные вещи). Стремитесь к тому, чтобы вызовов внутри границы было много, а через неё — мало.
- **Для фронтенда:** по умолчанию одно приложение с хорошими границами модулей. Добавляйте BFF, когда клиентам нужны данные разной формы или токены должны оставаться на сервере. Используйте микрофронтенды, только когда нескольким командам действительно нужны независимые релизы одного UI.

## Ландшафт

- **Границы модулей в одной кодовой базе:** правила границ модулей в Nx, dependency-cruiser, ESLint-плагины для границ, Spring Modulith (Java), Packwerk (Ruby, от Shopify).
- **Общение между сервисами:** REST, gRPC и GraphQL ([Стили API](/ru/architecture/api-styles/)), брокеры сообщений, service mesh (Istio, Linkerd), которые управляют трафиком, повторами и шифрованием между сервисами.
- **API gateways:** Kong, Amazon API Gateway, Apigee, gateways на основе Envoy, Cloudflare.
- **BFF и композиция API:** серверы full-stack фреймворков (Next.js, React Router, Nuxt, SvelteKit), Apollo Federation, Hive Gateway.
- **Микрофронтенды:** Module Federation (webpack, Rspack), single-spa, Native Federation, iframe, web components.
