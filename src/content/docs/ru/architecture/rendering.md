## Какую проблему решает

Любая страница в итоге оказывается в браузере в виде HTML плюс JavaScript, который делает её интерактивной. Кто-то должен создать этот HTML в какой-то момент, а JavaScript должен прийти и подключиться к нему. Где и когда это происходит, определяет:

- как быстро появляется первый контент ([TTFB, FCP, LCP](/ru/web-platform/page-loading/#как-шаги-соотносятся-с-метриками)),
- как быстро страница реагирует на ввод,
- насколько свежим и персональным может быть контент,
- что видят поисковики и превью ссылок,
- сколько серверной работы стоит каждый визит.

## Ментальная модель: три измерения, а не список вариантов

CSR, SSR, SSG, ISR и остальные обычно подают как конкурирующие варианты. Полезнее видеть в них **точки в пространстве из трёх независимых вопросов**:

1. **Где создаётся HTML?** На сервере или в браузере с помощью JavaScript.
2. **Когда?** Во время сборки, на каждый запрос, в фоне через какое-то время или в браузере после загрузки JavaScript.
3. **Как приходит интерактивность?** Гидратируется вся страница, только отдельные части, или JavaScript странице не нужен вообще.

Поверх них есть ещё вопрос доставки: HTML отправляется **целиком** или **стримится** частями по мере готовности каждой?

Знакомые названия — это комбинации ответов:

| Название | Где создаётся HTML | Когда | Интерактивность |
| --- | --- | --- | --- |
| **CSR** (client-side rendering, рендеринг на клиенте) | Браузер | После загрузки JS и получения данных | Всё приложение — JavaScript |
| **SSR** (server-side rendering, рендеринг на сервере) | Сервер | На каждый запрос | Обычно гидратируется вся страница |
| **SSG** (static site generation, статическая генерация) | Сервер, при сборке | Один раз, во время сборки | Гидратируется или не нужна |
| **ISR** (incremental static regeneration, инкрементальная регенерация) | Сервер | При сборке, затем перегенерируется в фоне через время или по запросу | Гидратируется |
| **Стриминг SSR** | Сервер | На каждый запрос, отправляется частями | Части гидратируются по мере прихода |
| **Islands** (острова) | Сервер или сборка | Сборка или запрос | JavaScript получают только интерактивные «острова» |
| **Server Components** (серверные компоненты React) | Сервер или сборка | Сборка или запрос | JavaScript отправляют только клиентские компоненты и код, который они импортируют |

Они **комбинируются**. Одна страница может быть static shell (части, одинаковые для всех, пререндеренные один раз) из сборки с персональным блоком, который стримится на каждый запрос, и только поле поиска на ней гидратируется. Современные фреймворки решают это **для каждого маршрута** или даже **для каждого компонента**, а не для приложения целиком.

## Цена каждого выбора

```
CSR     [empty shell][──── download JS ────][run][── fetch data ──][render]▶ content + interactive

SSR     [──── server renders ────][HTML ▶ content visible][── download JS ──][hydrate]▶ interactive

SSG     [HTML from CDN ▶ content visible][── download JS ──][hydrate]▶ interactive

Stream  [shell + placeholders ▶ visible][ slow parts stream in … ][hydrate parts]▶ interactive
```

| | CSR | SSR | SSG | ISR |
| --- | --- | --- | --- | --- |
| Время до первого байта | Быстро (static shell) | Медленнее: рендеринг на каждый запрос | Быстрее всего: из [CDN](/ru/web-platform/cdn/) | Быстрее всего: из CDN |
| Первый контент | Поздно: после JS и данных | Рано | Рано | Рано |
| Когда читаются данные | В браузере, при каждом визите | На сервере, на каждый запрос | При сборке; устаревают до следующей сборки | При сборке, затем при каждой регенерации; в промежутке устаревают, и дольше, если регенерация падает |
| Персональный контент | Легко | Легко | Не в HTML: получать в браузере или на edge | Как у SSG |
| Работа сервера по рендерингу HTML на визит (без учёта API и данных) | Нет | На каждый запрос | Нет | Только при регенерации |
| Поисковики, превью ссылок | Рискованно: контент виден только с JS | Полный HTML | Полный HTML | Полный HTML |

О поисковиках: Google выполняет JavaScript, но позже и с ограничениями. Многие другие краулеры и почти все боты превью ссылок (мессенджеры, соцсети) читают только HTML. Если контент должны находить или им должны делиться, кладите его в HTML.

## Гидратация: цена HTML, который выглядит готовым

При SSR и SSG HTML приходит уже отрендеренным. Ссылки и нативные формы работают, но всё, чему нужны обработчики на JavaScript, пока не работает: кнопка, открывающая меню, ничего не делает. **Гидратация** (hydration) — шаг, на котором фреймворк загружает JavaScript страницы, заново строит дерево компонентов в памяти, сопоставляет его с уже существующим HTML и подключает обработчики событий.

Её цена:

- **Вы платите дважды.** Страница рендерится на сервере, а её компоненты снова выполняются в браузере, включая части, которые никогда не меняются.
- **«Зловещая долина».** Страница выглядит готовой, но клики ничего не делают, пока гидратация не закончится. На медленных телефонах это может длиться секунды и ухудшает INP (насколько быстро страница реагирует на ввод).
- **Несовпадения.** Если браузер отрендерит что-то иное, чем сервер (дату, случайное значение, проверку `window`), фреймворк предупреждает, исправляет или перерендеривает, и это может мерцать.

Все новые подходы стараются гидратировать меньше:

- **Islands**: страница — статический HTML; JavaScript получают и независимо гидратируются только помеченные интерактивные части.
- **Server Components**: компоненты, которые только рендерят (без состояния и обработчиков), выполняются на сервере или при сборке, и их код никогда не отправляется в браузер.
- **Селективная гидратация**: React гидратирует каждую границу `<Suspense>` отдельно и первой — ту часть, с которой взаимодействует пользователь.
- **Resumability** (возобновляемость, Qwik): сервер сохраняет в HTML достаточно состояния, чтобы браузеру не нужно было заново выполнять компоненты; код загружается только тогда, когда он нужен для взаимодействия.

## Стриминг

При стриминге сервер отправляет HTML частями, а не ждёт всю страницу:

1. **Оболочка** (макет, навигация, заглушки для медленных частей) уходит сразу.
2. Каждая медленная часть (блок рекомендаций, виджет пользователя) отправляется позже в том же ответе, и небольшой скрипт ставит её на место заглушки.

Почему это помогает: медленный запрос к базе данных больше не задерживает всю страницу. TTFB и первый контент приходят рано, а быстрые части не ждут медленные. В React места, где страницу можно разделить, определяют границы `<Suspense>`.

Оговорки:

- **Статус-код и заголовки уходят с первой частью.** После начала стриминга сервер уже не может сменить ответ на `404` или редирект. Фреймворки обходят это специальными механизмами, но это реальное ограничение на то, где проверять «существует ли этот товар?».
- **Буферизация посередине.** Прокси или CDN, который буферизует весь ответ перед отправкой дальше, убивает стриминг.
- **Метаданные должны быть в первой части.** Краулеры, которым нужны `<title>` и meta-теги в `<head>`, могут получить рендер без стриминга.

## Публичный и персональный контент

Самая важная граница для рендеринга и кэширования: **одинаков ли этот HTML для каждого посетителя?**

- **Одинаков для всех** (страница товара, статья): его можно собрать один раз и отдавать всем пользователям из CDN. SSG, ISR или закэшированный static shell.
- **Персональный** (имя пользователя, его корзина, цены для его региона): он никогда не должен попасть в общий кэш, иначе его увидят другие пользователи. Либо рендерьте его на каждый запрос без общего кэширования, либо отдавайте публичную оболочку, а персональные части получайте или стримьте отдельно.

Правила scope (кто видит данные) объяснены в [Кэшировании](/ru/architecture/caching/#ментальная-модель-четыре-вопроса-к-любому-кэшу). Кому что разрешено видеть — в [Аутентификации и авторизации](/ru/security/auth/#авторизация-проверка-того-что-разрешено).

## Типичные проблемы

- **Чистое SPA для контентного сайта.** Медленный LCP, слабая видимость в поиске, пустые превью ссылок.
- **SSR для всего при медленном бэкенде.** Каждый визит ждёт самого медленного запроса. Static shell плюс стриминг медленных частей обычно лучше.
- **Персональные данные в статически сгенерированной или закэшированной странице.** Данные первого посетителя отдаются всем.
- **«SSR делает быстро».** SSR ускоряет первый контент, но отправляет тот же JavaScript. Если гидратация тяжёлая, страница всё равно медленно реагирует.
- **Несовпадения при гидратации** из-за рендеринга на сервере значений, зависящих от времени или доступных только в браузере.
- **Waterfall на клиенте** (цепочка запросов, где каждый ждёт предыдущий). Компонент получает данные после своего рендера, затем его дочерний компонент — после *своего*. Каждый уровень добавляет round trip (путь до сервера и обратно). Получение данных на сервере или запуск всех запросов на уровне маршрута убирает цепочку.

## Как выбирать

Для каждого маршрута спросите:

1. Контент **одинаков для всех пользователей** или персональный?
2. Как часто он **меняется** и насколько может устаревать?
3. Должны ли его видеть **поисковики или превью ссылок**?
4. Это **документ** (в основном чтение) или **приложение** (в основном взаимодействие)?
5. Где **данные** и как далеко от них сервер?

Практические правила:

- **Документация, блоги, маркетинг:** статика, islands для немногих интерактивных частей; регенерация по запросу, когда CMS публикует изменения.
- **E-commerce:** статический или ISR-каталог, а корзина и персональные цены получаются или стримятся отдельно.
- **Дашборды за логином:** SSR со стримингом или CSR. Поисковики не важны, и почти всё персональное.
- **Сильно интерактивные инструменты** (редакторы, инструменты дизайна): CSR, а сервер предоставляет API.

## Ландшафт

- **Next.js**: SSG, SSR, ISR, стриминг, Server Components; Partial Prerendering сочетает static shell со стримингом частей. См. [Кэширование в Next.js](/ru/tools/nextjs/caching/).
- **React Server Components**: возможность React, которую реализуют фреймворки. Server Components могут выполняться во время сборки или на каждый запрос, и в браузер попадает только результат их рендеринга.
- **React Router (бывший Remix)**: SSR со стримингом плюс пререндеринг выбранных маршрутов.
- **Astro**: статика в первую очередь, islands; server islands для персональных частей. На нём построена эта книга.
- **Nuxt** (Vue), **SvelteKit**, **SolidStart**: режим рендеринга выбирается для каждого маршрута.
- **Qwik**: resumability вместо гидратации.
- **Чистое SPA**: Vite с React, Vue или Svelte, отдаётся как статические файлы.
