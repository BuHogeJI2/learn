## Какую проблему решает

Компании с веб-приложением, админкой, API, дизайн-системой и несколькими общими утилитами нужно решить, **где живёт код**: в одном репозитории или в отдельном для каждого проекта. Этот выбор влияет на то, как код переиспользуется, как делается изменение, затрагивающее несколько проектов, как работают версии, сколько длится [CI](/ru/delivery/ci-cd/) и кто чем владеет.

Это решение отличается от того, как система работает. **Monorepo** (монорепозиторий — один репозиторий на много проектов) может содержать независимо деплоящиеся микросервисы, а один монолит можно разделить на несколько репозиториев. Границы во время работы описаны в [Границах приложения](/ru/architecture/application-boundaries/).

## Ментальная модель: из исходников или из опубликованных версий

```
Monorepo                                   Polyrepo
repo/                                      web-app repo ───┐
  apps/web      ─┐                         admin repo ─────┤ depend on published
  apps/admin     ├─ import shared code     ui-kit repo ────┤ versions: ui-kit@3.2.0,
  apps/api       │  directly from source   utils repo ─────┘ utils@1.8.1
  packages/ui   ─┘
  packages/utils
one commit can change everything           one change = a PR and a release per repo
```

Обычная схема и разница, которая действительно важна:

- В **монорепозитории** проекты обычно используют код друг друга **из исходников**: все собираются на последней версии, а изменение и все его последствия помещаются в один коммит и одно ревью.
- В **polyrepo** (по репозиторию на проект) проекты обычно используют друг друга **через опубликованные версии**: каждый потребитель сам решает, когда обновляться, а изменение проходит через релизы.

Ничто из этого не обязательно: монорепозиторий может публиковать независимо версионируемые пакеты, а отдельные репозитории могут закреплять исходники друг друга. На самом деле устройство репозиториев решает одно: одна общая история или несколько. И один коммит атомарен в Git, но не в production: приложения из одного коммита всё равно деплоятся по отдельности, поэтому изменения между ними должны оставаться обратно совместимыми.

## Сравнение monorepo и polyrepo

| | Monorepo | Polyrepo |
| --- | --- | --- |
| **Общий код** | Импортируется напрямую; публиковать нечего | Опубликовать пакет, присвоить версию, обновить каждого потребителя |
| **Изменение в нескольких проектах** (переименовать общий API) | Один коммит и одно ревью, проверяются вместе | Согласованные pull request в нескольких репозиториях, выпущенные в правильном порядке |
| **Версии** | Обычно всё работает на последнем коммите; пакеты всё равно можно версионировать и публиковать | У каждого репозитория своя версия и свой график релизов |
| **Сторонние зависимости** | Возможна единая политика версий (один React для всех приложений) | Каждый репозиторий может уехать на свои версии |
| **CI** | Должен быть умным: собирать и тестировать только затронутое изменением, с [кэшированием](/ru/architecture/caching/) результатов | Простой в каждом репозитории; тестировать проекты вместе сложнее |
| **Владение и доступ** | Владельцы по папкам (`CODEOWNERS`); обычно все могут читать всё | Права на каждый репозиторий, естественное разделение |
| **Инструменты** | Workspaces плюс система сборки; особые меры для очень больших репозиториев | Стандартные инструменты, но общая конфигурация постепенно расходится |
| **Подходит для** | Одной организации или продукта, общей дизайн-системы и типов, частых сквозных изменений | Независимых команд или продуктов, open-source библиотек, разных циклов релизов, строгого разделения доступа |

Многие компании оказываются посередине: несколько монорепозиториев, по одному на домен или группу команд.

## Как работает JavaScript-монорепозиторий

- **Workspaces** (рабочие пространства в npm, pnpm, Yarn или Bun): несколько пакетов в одном репозитории. Каждый пакет объявляет свои зависимости, а пакетный менеджер связывает локальные пакеты по своим правилам workspaces (например, ссылки `workspace:` в pnpm гарантируют, что используется локальная копия, а не версия из реестра).
- **Запускатель задач или система сборки** (Turborepo, Nx), которая знает граф зависимостей между пакетами и между задачами (`test` нужен `build` пакетов, которые он использует). В CI она сравнивает изменение с базовым коммитом и запускает задачи **затронутых** проектов (изменённые пакеты плюс всё, что от них зависит) вместе с их предварительными задачами, в правильном порядке и параллельно. Граф и базу нужно настроить правильно: пропущенная зависимость или неверная база молча пропускают проверки.
- **Кэширование, локальное и удалённое** ([скорость пайплайна](/ru/delivery/ci-cd/#решения-при-проектировании-пайплайна)): инструмент вычисляет отпечаток входных данных задачи (исходники, конфигурация, версии инструментов и зависимостей, нужные переменные окружения) и сохраняет под этим отпечатком результаты и логи задачи. **Удалённый кэш** делится ими, так что коллега или чистая машина CI восстанавливают результат вместо пересборки. Это корректно, только если каждый важный вход учтён в отпечатке, а результаты объявлены; иначе попадание в кэш восстановит неправильную сборку. Закэшированные логи — общие данные, поэтому никогда не выводите в них секреты.
- **Правила границ модулей**: какой пакет может импортировать какой, с проверкой инструментами, чтобы монорепозиторий не превратился в один большой клубок ([модульные границы](/ru/architecture/application-boundaries/#модульный-монолит)).
- **Общая конфигурация**: настройки TypeScript, линтера и форматирования задаются один раз.
- **Владельцы кода**: файл `CODEOWNERS` называет владельцев каждой папки и запрашивает их ревью; сделать это ревью обязательным — отдельная настройка защиты веток. Код он не скрывает: каждый, у кого есть доступ к репозиторию, может читать любую папку.
- **Публикация, когда нужна**: пакеты, которые используются и вне репозитория, получают версии и changelog с помощью инструмента вроде Changesets.

Внутренние пакеты бывают двух видов: приложения используют их **прямо из исходников на TypeScript** (просто, без отдельной сборки пакета, но инструменты каждого приложения-потребителя должны уметь компилировать эти исходники) или они **сначала собираются** и используются как скомпилированный результат (больше настройки, но пакет собирается один раз и кэшируется отдельно).

## Polyrepo, сделанный хорошо

- **Общие библиотеки** живут в приватном реестре с семантическим версионированием (`major.minor.patch`, где новая major-версия означает ломающие изменения), а автоматические pull request (Renovate, Dependabot) поддерживают потребителей в актуальном состоянии.
- **Шаблоны и переиспользуемые CI-workflow** не дают конфигурации расходиться между репозиториями.
- **Контрактные тесты** (проверки того, что поставщик всё ещё соответствует ожиданиям своих потребителей) и правила совместимости защищают API между проектами ([развитие API](/ru/architecture/api-styles/#развитие-долгосрочная-цена)).
- Побочный плюс: отдельные репозитории заставляют проводить ясные версионированные границы.

## Типичные проблемы

- **Монорепозиторий без инструментов**: каждый pull request запускает все тесты, и CI идёт час.
- **Монорепозиторий, где всё импортирует всё**: проекты срастаются в клубок, который уже никто не может разделить.
- **Уверенность, что монорепозиторий означает деплой всего вместе.** Каждое приложение в нём по-прежнему может собираться и деплоиться отдельно.
- **Один сломанный общий пакет ломает сборку каждого приложения, которое его использует.** Уже задеплоенные приложения продолжают работать, но ничего не выпускается, пока его не починят. Хорошие тесты и CI по затронутым проектам ловят это до слияния.
- **Неполные входные данные кэша**: переменная окружения или файл конфигурации не учтены в отпечатке, поэтому CI восстанавливает устаревшую сборку и сообщает об успехе.
- **Polyrepo с общей библиотекой, которая меняется каждую неделю**: постоянная работа по обновлению и несколько версий одной библиотеки в одном приложении (с React две копии вызывают ошибки, в которых трудно разобраться).
- **Конфликты версий**: двум библиотекам нужны разные версии третьей.
- **Код или конфигурация, видимые всем**, хотя им нужна была своя граница доступа, например отдельный репозиторий. Секретам вообще не место ни в каком репозитории: они живут в хранилищах секретов CI и среды выполнения ([секреты](/ru/delivery/ci-cd/#секреты-и-безопасность)).
- **Выбор по моде**, а не по тому, как на самом деле происходят изменения.

## Как выбирать

Оптимизируйте под самый частый вид изменений:

- **Изменения часто затрагивают несколько проектов** (фронтенд, бэкенд и общие типы меняются вместе): монорепозиторий с workspaces и системой сборки вроде Turborepo или Nx. Это обычный выбор для небольшой или средней продуктовой команды.
- **Проекты редко меняются вместе**, принадлежат независимым командам, используют разные языки или требуют строгого разделения доступа: отдельные репозитории или по монорепозиторию на домен.
- **Очень большие организации** держат огромные монорепозитории (Google, Meta) только с тяжёлыми собственными инструментами.

Что бы вы ни выбрали, границы во время работы решайте отдельно: устройство репозиториев не определяет, что деплоится вместе.

## Ландшафт

- **Workspaces:** workspaces в pnpm, npm, Yarn и Bun.
- **Системы сборки для монорепозиториев:** Turborepo, Nx, Bazel, Pants, Rush, moon; Lerna (теперь её поддерживает команда Nx).
- **Версии и релизы:** Changesets, semantic-release, release-please.
- **Обновление зависимостей:** Renovate, Dependabot.
- **Очень большие репозитории:** sparse checkout в Git (в рабочей копии только некоторые папки) и partial clone (объекты Git скачиваются только по необходимости).
- **Владение:** `CODEOWNERS` в GitHub и GitLab.
