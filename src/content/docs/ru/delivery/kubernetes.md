## Какую проблему решает

Запустить один [контейнер](/ru/delivery/containers/) легко. Запуск сотен контейнеров на десятках машин поднимает вопросы, с которыми скрипты справляются плохо:

- На какой машине должен работать каждый контейнер?
- Кто перезапустит упавший контейнер или заменит умершую машину?
- Как выкатить новую версию без простоя и откатить её?
- Как сервисам находить друг друга, когда контейнеры появляются и исчезают?
- Как до них доходят конфигурация и секреты?

На эти вопросы отвечает **оркестратор**. **Kubernetes** (часто пишут K8s) — доминирующий оркестратор: open source, доступен как управляемый сервис у всех крупных облаков, с огромной экосистемой инструментов.

## Ментальная модель: желаемое состояние и циклы управления

Вы не говорите Kubernetes «запусти три контейнера». Вы **объявляете**: «я хочу, чтобы работали три копии этого образа», — и Kubernetes постоянно приводит реальность в соответствие с этим объявлением.

```
you ── kubectl apply / GitOps ──► API server ──► desired state stored (etcd)
                                       ▲
     controllers watch it ─────────────┘  compare desired with actual → act
     scheduler: chooses a node for each new Pod
     kubelet (on every node): starts and watches the containers
```

- **Кластер** — это **control plane** (управляющий слой: API-сервер, его база данных etcd, планировщик и контроллеры) плюс **ноды** (nodes) — рабочие машины, на которых выполняются контейнеры.
- Всё — **объекты** в API, обычно описанные YAML-манифестами. Инструменты вроде `kubectl`, Helm и Argo CD только создают и обновляют объекты.
- **Контроллеры** крутят бесконечные циклы: сравнивают объявленное с существующим и исправляют разницу. Если нода умирает, поды, которыми управляет контроллер (например, поды Deployment), пересоздаются на других нодах — после того как сбой обнаружен, если есть свободная мощность и доступно нужное им хранилище. Замена самой машины — задача облачного провайдера или автомасштабирования нод. Этот цикл называется **reconciliation** (согласование).

## Прослеживаем один деплой

1. Вы меняете версию образа в **Deployment** (объекте, который говорит «N одинаковых копий этого шаблона пода»).
2. Контроллер Deployment начинает **[rolling update](/ru/delivery/deployment-models/#релизы-от-коммита-до-пользователей)** (постепенное обновление): создаёт новые **поды** (Pod — минимальная единица: один или несколько контейнеров с общим сетевым адресом) и шаг за шагом удаляет старые.
3. **Планировщик** (scheduler) размещает каждый новый под на ноде, где хватает CPU и памяти, которые под **запрашивает**.
4. Под получает конфигурацию из **ConfigMaps**, а чувствительные значения — из **Secrets**, в виде переменных окружения или файлов.
5. В веб-сервисе с настроенной **readiness probe** (проверкой готовности) новый под получает трафик, только когда проверка проходит. **Liveness probe** (проверка «жив ли») перезапускает зависший контейнер, поэтому используйте её только для сбоев, которые лечит перезапуск; **startup probe** (проверка запуска) откладывает проверки liveness, пока медленное приложение стартует ([health checks](/ru/architecture/reliability/#типичные-проблемы)).
6. Старые поды убираются из ротации трафика и получают `SIGTERM` примерно одновременно. Изменениям маршрутизации нужно время, чтобы распространиться, поэтому запросы могут приходить и сразу после сигнала. Отведённое время (по умолчанию 30 секунд, включая pre-stop hook, если он есть) — это всё время на завершение работы, после которого под убивают ([остановка](/ru/delivery/containers/#конфигурация-секреты-и-данные)).

Если новые поды так и не становятся готовыми, выкатка застревает: Kubernetes продолжает пытаться и после дедлайна помечает Deployment как неудавшийся, но сам ничего не откатывает. Откат — это решение. С [GitOps](/ru/delivery/ci-cd/#ландшафт) (кластер следует за Git-репозиторием) откатите изменение в Git; `kubectl rollout undo` — вариант для экстренных случаев. `rollout undo` восстанавливает только шаблон пода в Deployment; откат в Git восстанавливает и другие объекты, описанные в репозитории, например ConfigMap или Service. Ни то ни другое не отменяет изменений в базе данных.

## Прослеживаем один запрос

```
user ─► cloud load balancer ─► Ingress / Gateway ─► Service ─► one of the ready Pods
                               (host, path, TLS)    (stable name,
                                                     balances between Pods)
```

Это концептуальный маршрут. Перечисленное — объекты конфигурации, которые реализуют контроллеры и сеть, а ingress-контроллер часто отправляет трафик прямо в поды.

- **Поды одноразовые.** Пересозданный под получает новый IP-адрес, поэтому обычные клиенты используют имя сервиса, а не адреса подов.
- **Service** (сервис) даёт группе подов стабильное [DNS](/ru/web-platform/dns/)-имя и адрес и распределяет новые соединения между готовыми подами. Он балансирует соединения, а не отдельные HTTP-запросы: keep-alive-, HTTP/2- или WebSocket-соединение остаётся на одном поде.
- **Ingress** и его более новый и выразительный преемник **Gateway API** направляют HTTP-трафик извне кластера к сервисам по имени хоста и пути и завершают TLS. Им нужен контроллер, который их реализует (на основе NGINX или Envoy либо [балансировщик](/ru/architecture/scaling/#балансировка-нагрузки) облака).

## Остальные повседневные объекты

| Объект или настройка | Что делает |
| --- | --- |
| **Requests и limits** | **Requests** (запросы ресурсов) контейнера определяют, где его можно разместить; **limits** (лимиты) ограничивают потребление. При превышении лимита памяти контейнер убивают; при превышении лимита CPU — замедляют. |
| **HorizontalPodAutoscaler** | Меняет число подов по метрике, например CPU ([автомасштабирование](/ru/architecture/scaling/#автомасштабирование)). Cluster autoscaler добавляет или убирает ноды под эту нагрузку. |
| **Namespace** | Группирует объекты, например по командам или окружениям, со своими правами и квотами. |
| **RBAC** (role-based access control — доступ на основе ролей) | Кто может читать или менять какие объекты ([авторизация](/ru/security/auth/#авторизация-проверка-того-что-разрешено)). |
| **Job** и **CronJob** | Работа, которая выполняется до завершения, один раз или по расписанию ([фоновые задачи](/ru/architecture/background-jobs/#работа-по-расписанию-и-долгие-процессы)). |

## Хранилище: поды одноразовые, данные — нет

Собственная файловая система пода теряется, когда под заменяют. Данные, которые должны сохраниться, используют **PersistentVolumeClaim** (запрос на хранилище), который Kubernetes связывает с **PersistentVolume** — обычно диском облачного провайдера. Том переживает перезапуски пода и может переехать вслед за ним на другую ноду — в пределах того, куда этот диск можно подключить (часто это одна зона доступности; локальные диски не переезжают вообще). Что произойдёт при очистке, решают его storage class и **reclaim policy** (политика освобождения): при распространённой политике `Delete` удаление запроса удаляет и диск. Постоянный том — это не [бэкап](/ru/delivery/disaster-recovery/#репликация--не-бэкап).

Запускать базы данных внутри Kubernetes можно (**StatefulSet** даёт подам стабильные имена и собственные тома), но это серьёзная эксплуатационная работа: бэкапы, обновления, переключение при сбоях. Многие команды держат в Kubernetes приложения без состояния, а управляемую базу данных — вне кластера ([что переживает перезапуск](/ru/delivery/deployment-models/#состояние-что-переживает-перезапуск)).

## Сколько Kubernetes вы обслуживаете сами?

| Вариант | Вы обслуживаете | Примеры |
| --- | --- | --- |
| **Свой кластер** | Всё: control plane, обновления, бэкапы etcd, ноды | kubeadm, дистрибутивы для своих серверов |
| **Управляемый control plane** | Ноды и всё внутри кластера | Amazon EKS, Google GKE, Azure AKS |
| **Управляемые ещё и ноды** | Свои нагрузки; вы платите за поды, или провайдер управляет пулами нод | GKE Autopilot, EKS Auto Mode, AWS Fargate |
| **Без Kubernetes** | Только свои контейнеры | Google Cloud Run, Amazon ECS на Fargate, Fly.io, Render (ECS на своих машинах EC2 оставляет машины на вас) |

Поверх кластера команды описывают и выкатывают нагрузки с помощью **Helm** (пакеты-шаблоны, которые называются charts), **Kustomize** (наложения под конкретные окружения) и **GitOps**-инструментов вроде Argo CD и Flux, которые держат кластер в соответствии с Git-репозиторием.

## Типичные проблемы

- **Kubernetes для небольшой команды с двумя сервисами.** Цена эксплуатации больше пользы.
- **Нет requests и limits**: непредсказуемое размещение, «шумные соседи», контейнеры, убитые из-за памяти.
- **Нет readiness probe**, поэтому трафик приходит в поды, которые ещё запускаются, и каждый деплой вызывает ошибки. Или **liveness probe, которая проверяет базу данных**, из-за чего короткая проблема с базой перезапускает все поды.
- **Игнорирование `SIGTERM`**, из-за которого выкатки обрывают текущие запросы.
- **Секреты в виде обычных манифестов в Git.** Secrets в Kubernetes только закодированы в base64, а это не шифрование, поэтому никогда не коммитьте их значения. Сочетайте минимальные права доступа с шифрованием при хранении в кластере. Внешний менеджер секретов, который синхронизирует значения в кластер, — частое дополнение, и синхронизированным Secrets нужна та же защита.
- **Тег образа `latest`**: поды работают на разных версиях, а откат неясен.
- **Данные в файловой системе пода**, которые теряются при следующем перемещении.
- **Скопированный YAML** для каждого окружения, который постепенно расходится.
- **Отложенные обновления кластера.** Каждая минорная версия Kubernetes поддерживается всего около года, поэтому обновления — рутинная работа, а не редкий проект.
- **У всех права администратора кластера.**

## Когда использовать

- **Стоит того:** много сервисов и несколько команд; платформенная команда, которая будет его обслуживать; переносимость между облаками или на свои серверы; особые требования к размещению (GPU, большие пакетные задачи); экосистема инструментов.
- **Пока не стоит:** несколько сервисов и небольшая команда. Управляемая контейнерная платформа (Google Cloud Run, Amazon ECS, Fly.io, Render) или фронтенд-платформа даст большую часть пользы. Контейнеры переносимы, поэтому перейти на Kubernetes позже вполне реально.
- **Если всё-таки внедряете:** используйте управляемый сервис, деплойте через GitOps, задавайте requests и limits для каждой нагрузки, readiness probes (плюс liveness и startup probes, где они уместны) для каждого сервиса, который принимает трафик, и держите базы данных управляемыми вне кластера, если нет веских причин поступить иначе.

## Ландшафт

- **Управляемый Kubernetes:** Amazon EKS, Google GKE (включая Autopilot), Azure AKS, DigitalOcean Kubernetes.
- **Дистрибутивы:** Red Hat OpenShift, Rancher (RKE2), k3s (облегчённый), Talos Linux.
- **Локальные кластеры:** kind, minikube, k3d, Docker Desktop, OrbStack.
- **Упаковка и деплой:** Helm, Kustomize, Argo CD, Flux.
- **Сеть:** контроллеры Ingress (Traefik, HAProxy, на основе NGINX), реализации Gateway API (Envoy Gateway, Istio, Cilium), service mesh (Istio, Linkerd), сетевые плагины (Cilium, Calico).
- **Масштабирование и эксплуатация:** Horizontal Pod Autoscaler, KEDA, Cluster Autoscaler, Karpenter; k9s и Lens для просмотра кластеров; Backstage для порталов разработчиков поверх них.
