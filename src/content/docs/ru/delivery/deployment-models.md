## Какую проблему решает

После сборки у вас есть статические файлы и часто ещё серверный код. Им нужно где-то работать: отвечать на запросы, расти вместе с трафиком, переживать сбои и обновляться, не ломая пользователям работу.

**Модель деплоя** определяет:

- сколько вы платите, когда приложением никто не пользуется;
- как быстро стартует новый инстанс (работающая копия приложения) и как долго может выполняться один запрос;
- где может жить состояние и что теряется при перезапуске;
- что значат «задеплоить» и «откатить».

Фронтенд-разработчики сталкиваются с этим каждый день: хостинг-платформы вроде Vercel и Netlify незаметно превращают возможности фреймворка (рендеринг на сервере, регенерацию, серверные функции) в одну из моделей ниже.

## Ментальная модель: результат сборки определяет среду выполнения

```
source ──build──► static files ─────────────► object storage + CDN       (no server)
              └──► server code ──┬──► long-running process (VM or container)
                                 ├──► functions (started on demand, scale to zero)
                                 └──► edge functions (in every CDN location)
```

Важны два момента:

- **Время сборки** наступает один раз на деплой: компиляция, бандлинг, пререндеринг страниц.
- **Время запроса** наступает при каждом визите: рендеринг на сервере, обработчики API, серверные функции.

[Стратегии рендеринга](/ru/architecture/rendering/) определяют, сколько работы выполняется при сборке, а сколько — во время запроса. Модель деплоя определяет, **где** выполняется код времени запроса.

Деплой обычно состоит из двух частей: **неизменяемого артефакта** (результат сборки или образ контейнера, который после сборки никогда не меняется) и **конфигурации** (переменные окружения, секреты). Twelve-Factor App называет это отделением конфигурации от кода: один и тот же артефакт проходит через staging и production, а отличается только конфигурация.

Одна ловушка для фронтенда: конфигурация, которая попадает в браузерный бандл, читается во время **сборки**. Переменная `NEXT_PUBLIC_` или `VITE_` копируется в JavaScript, и если потом поменять её на сервере, ничего не изменится. Чтобы провести один артефакт через все окружения, загружайте такие значения во время выполнения (например, с небольшого эндпоинта конфигурации или из скрипта, который сервер вставляет в страницу) либо смиритесь с отдельной сборкой для каждого окружения.

## Модели деплоя

| Модель | Что выполняется | Масштабирование | Стоимость в простое | Главные ограничения | Подходит для |
| --- | --- | --- | --- | --- | --- |
| **Статический хостинг** | Файлы на [CDN](/ru/web-platform/cdn/) (серверах рядом с пользователями, которые хранят копии) | Практически без ограничений | Почти ноль | Нет кода во время запроса (если не сочетать с функциями) | Документации, блогов, маркетинговых сайтов, SPA, которые вызывают внешние API |
| **Постоянно работающие серверы** (VM — виртуальные машины; контейнеры; PaaS — платформы, которые запускают приложение за вас) | Процесс, который не останавливается и обрабатывает много запросов | Добавить инстансы; [автомасштабирование](/ru/architecture/scaling/#автомасштабирование) реагирует за секунды или минуты | Вы всё время платите минимум за один инстанс | Вы планируете ёмкость; на вас больше эксплуатации | Ровного трафика, [WebSockets](/ru/architecture/real-time/), долгих запросов, [фоновых обработчиков](/ru/architecture/background-jobs/) |
| **Serverless-функции** | Код, который платформа запускает по запросу; инстансы создаются и удаляются автоматически | Автоматическое, быстрое, до нуля | Почти ноль | Cold starts, максимальная длительность, нет постоянного локального диска, много соединений с базой | Пикового трафика, рендеринга на сервере на хостинг-платформах, webhooks |
| **Edge-функции** | Лёгкие изоляты (небольшие песочницы внутри одной общей среды выполнения) в каждой локации CDN | Автоматическое | Почти ноль | Ограниченные API, короткое время CPU, обычно далеко от данных ([edge compute](/ru/web-platform/cdn/#edge-compute-где-должен-выполняться-код)) | Редиректов, проверки токенов, A/B-маршрутизации, лёгкой персонализации |

Некоторые детали за таблицей:

- **Cold start** (холодный старт) — задержка, когда платформе приходится создавать новый инстанс: загружать среду выполнения и ваш код до первого запроса. Он длится от миллисекунд (edge-изоляты) до секунды и больше (большие функции в медленных средах выполнения). «Тёплые» инстансы переиспользуются для следующих запросов.
- **Максимальная длительность** функции зависит от провайдера, триггера и тарифа: AWS Lambda останавливает вызов через 15 минут, другие платформы разрешают час и больше, а у HTTP-ответа часто есть свой, более короткий лимит. Долгой работе, которую пользователь ждал бы, в любом случае место в [фоновой задаче](/ru/architecture/background-jobs/).
- **Serverless-контейнеры** находятся посередине: вы поставляете образ контейнера, а платформа запускает и останавливает инстансы по трафику, вплоть до нуля (Google Cloud Run, Azure Container Apps).
- Платформы размывают границы: некоторые позволяют одному инстансу функции обрабатывать несколько запросов одновременно, а приложение на full-stack фреймворке на Vercel или Netlify становится смесью статических файлов, функций и edge-функций.

## Контейнеры коротко

**Контейнер** упаковывает приложение вместе с зависимостями и системными библиотеками в **образ** (image), который одинаково запускается на ноутбуке, в CI и в production, если у хоста совместимое ядро операционной системы и архитектура процессора (образы можно собирать под несколько архитектур, например x86 и ARM). Он легче виртуальной машины, потому что контейнеры делят ядро операционной системы хоста. Docker — распространённый инструмент для сборки и запуска образов.

Чтобы запускать много контейнеров на многих машинах, нужен **оркестратор**: он решает, где запускать каждый контейнер, перезапускает упавшие, масштабирует их, выкатывает новые версии и направляет трафик между сервисами. **Kubernetes** — доминирующий оркестратор. Он мощный и сложный: платформа для построения платформ. Он окупается, когда организация запускает много сервисов и у неё есть люди для его эксплуатации; небольшой команде обычно лучше подходит управляемая платформа.

## Состояние: что переживает перезапуск

Главное правило: **считайте каждый инстанс одноразовым.** Любой инстанс может быть остановлен, перезапущен или заменён во время деплоя, уменьшения масштаба или сбоя. Его память теряется при любом перезапуске. Его локальный диск может пережить простой перезапуск, но не замену, и он никогда не общий с другими инстансами. Данные сохраняют только подключённый постоянный том или внешний сервис — по своим собственным правилам хранения.

| Состояние | Неправильное место | Правильное место |
| --- | --- | --- |
| Загруженные файлы | Локальный диск сервера | Объектное хранилище (сервис для файлов, например S3 или R2) |
| Сессии пользователей | Память процесса (пользователи разлогиниваются, попадая на другой инстанс) | База данных, Redis или подписанная cookie ([сессии](/ru/security/auth/#сессии-на-практике-жизненный-цикл)) |
| Кэш | Только в процессе, когда все инстансы должны видеть одно и то же закэшированное значение | В процессе — нормально как ускорение для одного инстанса; общий кэш — когда инстансы должны делить записи, с ясным планом свежести и инвалидации ([кэширование](/ru/architecture/caching/)). Данным, которые должны быть корректными, место в базе данных ([согласованность](/ru/data/consistency/)) |
| Работа по расписанию и долгая работа | `setTimeout` или таймер в веб-процессе | [Очередь задач](/ru/architecture/background-jobs/) или сервис-планировщик |
| WebSocket-соединения | Среда выполнения функций, которая не поддерживает долгоживущие соединения (проверьте лимиты платформы) | Постоянно работающие серверы, управляемый сервис [реального времени](/ru/architecture/real-time/) или serverless-среда, созданная для соединений (например, Cloudflare Durable Objects) |
| Файл базы SQLite | Временный диск функции или контейнера | Сервис базы данных или платформа с постоянными томами |

## Релизы: от коммита до пользователей

**CI/CD** — автоматизированный путь от коммита до production:

- **CI** (continuous integration — непрерывная интеграция): каждое изменение автоматически собирается и тестируется, и изменения часто вливаются в общую ветку.
- **CD** означает либо **continuous delivery** (непрерывную поставку: каждое изменение *может* уйти в production; кнопку нажимает человек), либо **continuous deployment** (непрерывное развёртывание: каждое изменение, прошедшее проверки, уходит в production автоматически).

Типичный пайплайн: сборка → тесты → упаковка артефакта → деплой на staging → деплой в production. GitHub Actions, GitLab CI, Jenkins и Bamboo — движки, которые выполняют такие пайплайны.

Как новая версия доходит до пользователей:

| Стратегия | Как работает | Откат |
| --- | --- | --- |
| **Recreate** (пересоздание) | Остановить старую версию, запустить новую | Медленный; есть простой |
| **Rolling** (постепенная замена) | Заменять инстансы по несколько за раз | Постепенно вперёд или назад |
| **Blue-green** | Запустить новую версию рядом со старой, затем переключить весь трафик разом | Мгновенный для кода: переключить обратно |
| **Canary** (канареечный релиз) | Отправить небольшую долю трафика на новую версию, следить за ошибками и задержками ([мониторинг](/ru/observability/logs-metrics-traces/)), затем увеличивать | Остановить canary |
| **Фича-флаги** (feature flags) | Задеплоить код выключенным, затем включить его для выбранных пользователей | Выключить флаг, без деплоя; то, что фича уже сделала, остаётся |

Откат переключает **код**, а не **данные**. Изменения в базе, отправленные сообщения и списанные с карт деньги остаются. Держите схему и данные совместимыми с предыдущей версией всё время, пока может понадобиться откат.

При любой стратегии два правила предотвращают ошибки во время выкатки:

- отправляйте трафик на новый инстанс, только когда он сообщает, что **готов** (readiness check, проверка готовности);
- **выводите из работы** (drain) старый инстанс перед остановкой: перестаньте отправлять ему новые запросы, дайте текущим завершиться за ограниченное время и ожидайте, что долгоживущие соединения переподключатся.

Фронтенд-платформы добавили две привычки, которые стоит перенять где угодно:

- **Неизменяемые деплои со своими URL.** Каждый деплой хранится ровно таким, каким его собрали, под своим URL — столько, сколько его держит политика хранения платформы. Откат направляет домен обратно на более старый деплой. Это работает, если деплой ещё хранится, а его конфигурация и данные всё ещё совместимы.
- **Preview deployments** (превью-деплои). Каждый pull request получает свой живой URL для ревью.

Две проблемы характерны именно для релизов веб-приложений:

- **Version skew** (рассинхрон версий). После деплоя пользователи с открытыми вкладками всё ещё выполняют старый JavaScript. Он вызывает новый сервер или запрашивает старые чанки кода, которые были удалены, и это падает с ошибками вроде `ChunkLoadError`. Держите старые файлы доступными какое-то время, сохраняйте обратную совместимость API ([развитие API](/ru/architecture/api-styles/#развитие-долгосрочная-цена)) и перезагружайте страницу, когда чанк не загрузился. Некоторые платформы направляют старых клиентов на старый деплой (Vercel называет это skew protection).
- **Миграции базы данных.** Во время постепенного деплоя старый и новый код работают одновременно с одной и той же базой. Меняйте схему совместимыми шагами (расширить, перенести данные, затем сузить), чтобы работали обе версии.

## Типичные проблемы

- **Файлы или сессии на инстансе.** Локально работает и ломается при двух инстансах или после первого деплоя.
- **Долгая работа в функции** (обработка видео, большие выгрузки), которая упирается в лимит времени.
- **Исчерпанные соединения с базой данных** из-за множества инстансов функций ([масштабирование базы](/ru/data/database-types/#масштабирование-коротко)).
- **Секреты в клиентском бандле.** Переменные окружения с публичным префиксом (`NEXT_PUBLIC_`, `VITE_`) копируются в JavaScript, и их может прочитать кто угодно.
- **Конфигурация, вшитая в сборку непреднамеренно**: тогда staging и production запускают разные артефакты, и тестирование на staging доказывает меньше.
- **Удаление старых статических файлов при деплое**, которое ломает каждую открытую вкладку.
- **Функции в одном регионе, база данных в другом.** Каждый запрос пересекает океан.
- **Cold starts на критичном к задержке пути**, усиленные большими бандлами функций.
- **Неожиданные счета.** Функции дёшевы при небольшом или пиковом трафике и могут быть дорогими при высоком ровном трафике; трафик тоже оплачивается.
- **Нет плана отката** или миграция, которую нельзя отменить.

## Как выбирать

Спросите:

1. Какая форма трафика: пиковая или ровная, маленькая или большая?
2. Какой самый долгий запрос? Держит ли что-то соединение открытым?
3. Где данные и может ли код работать рядом с ними?
4. Кто будет это эксплуатировать и сколько контроля нужно?
5. Сколько это стоит при ожидаемом объёме, а не только при нулевом?

Практические правила:

- **Контентные сайты, документация, SPA с внешним API:** статический хостинг на CDN.
- **Приложение на full-stack фреймворке с умеренным или пиковым трафиком:** платформа, которая раскладывает его на статические файлы и функции, или один контейнерный сервис, если нужно больше контроля.
- **Ровный высокий трафик, WebSockets, долгие запросы, фоновые обработчики:** постоянно работающие контейнеры.
- **Чувствительная к задержке логика, которой не нужны данные:** edge-функции.
- **Много сервисов и платформенная команда:** оркестрация контейнеров, например управляемый Kubernetes.

## Ландшафт

- **Статические и фронтенд-платформы:** Vercel, Netlify, Cloudflare Pages, GitHub Pages, AWS Amplify, Amazon S3 с CloudFront.
- **Платформы приложений (PaaS) и serverless-контейнеры:** Render, Railway, Fly.io, Heroku, Google Cloud Run, Azure Container Apps.
- **Функции:** AWS Lambda, Vercel Functions, Netlify Functions, Azure Functions, Google Cloud Run functions. Edge: Cloudflare Workers, Deno Deploy, edge-функции Vercel и Netlify.
- **Контейнеры и оркестрация:** Docker, Podman; Kubernetes (управляемый: EKS, GKE, AKS), Amazon ECS, HashiCorp Nomad.
- **CI/CD:** GitHub Actions, GitLab CI/CD, Jenkins, Atlassian Bamboo, CircleCI, Buildkite; GitOps-инструменты деплоя Argo CD и Flux.
- **Infrastructure as code** (инфраструктура как код: серверы и сервисы описаны в файлах и создаются инструментом): Terraform и OpenTofu, Pulumi, AWS CDK, SST.
- **Фича-флаги:** LaunchDarkly, Unleash, Flagsmith, GrowthBook, Statsig.
