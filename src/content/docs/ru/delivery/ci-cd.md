## Какую проблему решает

Много людей каждый день меняют один и тот же код. Без автоматизации проблемы копятся:

- «у меня работает», а больше ни у кого;
- сломанная основная ветка, которую кто-то обнаруживает через несколько дней;
- релизы вручную, с шагами, которые кто-то забывает;
- никто точно не знает, какая версия сейчас в production.

**CI/CD** автоматизирует путь от коммита до production. [Модели деплоя](/ru/delivery/deployment-models/#релизы-от-коммита-до-пользователей) объясняют, где выполняется код и как новая версия доходит до пользователей; эта страница — о механизме между ними: о **пайплайне**.

- **CI** (continuous integration — непрерывная интеграция): каждое изменение автоматически собирается и тестируется, и изменения часто вливаются в основную ветку.
- **CD** — либо **continuous delivery** (непрерывная поставка: каждое изменение *можно* выпустить; когда — решает человек), либо **continuous deployment** (непрерывное развёртывание: каждое изменение, прошедшее проверки, выпускается автоматически).

## Ментальная модель: коммит становится артефактом, артефакт продвигается

```
push / pull request
      │ trigger
      ▼
 [ build ] ─► [ lint │ type check │ unit tests ] ─► [ package artifact ] ─► staging ─► approval ─► production
                  jobs in parallel                   stored and versioned    the same artifact, promoted
```

Словарь, который в той или иной форме используют все инструменты:

- **Пайплайн**: весь автоматический процесс для одного изменения.
- **Стадия** (stage): фаза пайплайна. Стадии обычно идут по порядку, и стадия начинается, только когда предыдущая прошла успешно.
- **Джоб** (job): единица работы, которая выполняется на одной машине. Джобы одной стадии могут выполняться параллельно.
- **Шаг** (step, или task): одна команда внутри джоба, например `npm ci` или `npm test`.
- **Раннер** (runner, или agent — агент): машина или [контейнер](/ru/delivery/containers/), на которых выполняются джобы.
- **Триггер**: то, что запускает пайплайн: push, pull request, расписание, другой пайплайн, человек.
- **Артефакт**: то, что пайплайн создаёт и сохраняет: папка сборки, образ контейнера, отчёт о тестах.
- **Окружение** (environment): место, куда деплоится артефакт: development, staging, production.

Четыре принципа делают пайплайны надёжными:

1. **Собирайте один раз и продвигайте тот же артефакт.** В production попадает ровно то, что тестировали; между окружениями отличается только конфигурация. Это работает, только если эти различия действительно читаются во время выполнения: публичные переменные во фронтенд-бандлах вшиваются при сборке ([конфигурация](/ru/delivery/deployment-models/#ментальная-модель-результат-сборки-определяет-среду-выполнения)). Если фреймворку нужна отдельная сборка для каждого окружения, тестируйте именно эту сборку.
2. **Пайплайн как код.** Описание пайплайна лежит в репозитории, проходит ревью как код и версионируется вместе с ним.
3. **Сначала быстрая обратная связь.** Дешёвые проверки (линтер, типы, юнит-тесты) идут первыми и падают рано; медленные (end-to-end тесты) — позже или параллельно.
4. **Воспроизводимые сборки.** Закреплённые версии инструментов, lock-файлы (файлы, где записана точная версия каждой зависимости), чистые машины для каждого запуска.

## Одни и те же идеи в разных инструментах

| Понятие | GitHub Actions | GitLab CI/CD | Bamboo |
| --- | --- | --- | --- |
| Конфигурация | `.github/workflows/*.yml` | `.gitlab-ci.yml` | Bamboo Specs (YAML или Java) или веб-интерфейс |
| Пайплайн | Запуск workflow | Pipeline | Plan плюс deployment project для релизов |
| Стадия | Отдельного понятия нет; джобы объявляют зависимости через `needs` | Stage | Stage |
| Джоб | Job | Job | Job |
| Шаг | Step | Строка в `script` | Task |
| Машина | Runner | Runner | Agent |
| Цель деплоя | Environment | Environment | Environment в deployment project |

## Bamboo как разобранный пример

Bamboo — self-hosted CI/CD-сервер от Atlassian, который часто встречается в компаниях, использующих Jira и Bitbucket Data Center. (Облачный CI-сервис Atlassian — Bitbucket Pipelines.) Его модель хорошо ложится на понятия выше:

```
Project
 └─ Plan                      triggers, repository, variables
     ├─ Stage 1               stages run one after another
     │   ├─ Job A             jobs of a stage run in parallel, on different agents
     │   │   └─ Task, Task    tasks of a job run in order, on the same agent
     │   └─ Job B
     └─ Stage 2               starts only when every job of stage 1 succeeded

Deployment project            takes the plan's artifacts
 ├─ Release 1.4.2             a snapshot of tested artifacts
 └─ Environments, for example QA → Staging → Production
```

- **Plan** собирает и тестирует. Его джобы описывают **артефакты**; джоб может использовать артефакты, созданные на более ранней стадии, а артефакты, помеченные как общие (shared), могут использовать деплои.
- **Агенты** выполняют джобы. Джоб указывает свои **требования** (requirements, например Node.js 22), и Bamboo отправляет его агенту с подходящими **возможностями** (capabilities).
- **Plan branches** переиспользуют конфигурацию plan для других веток; в зависимости от настроек они создаются автоматически или вручную, с необязательными переопределениями.
- **Deployment project** превращает результат сборки в **релизы**: снимки проверенных артефактов с их коммитами и задачами Jira. Один и тот же релиз деплоится в **окружения**, и каждое окружение показывает, какой релиз в нём работает, кто его задеплоил и когда. Это «собирайте один раз и продвигайте тот же артефакт», встроенное в инструмент. Порядок (QA, затем staging, затем production) не автоматический: у каждого окружения свои триггеры и права, и именно вы настраиваете их так, чтобы получился этот путь.

## Решения при проектировании пайплайна

- **Триггеры.** Pull request получает быстрые проверки; слияние в main — полный набор и деплой; запуски по расписанию ловят медленные проблемы (ночные end-to-end тесты, обновления зависимостей).
- **Ветвление.** CI означает частую интеграцию. При **trunk-based development** (разработке в основной ветке) ветки живут часы или дни, а незаконченные фичи прячутся за [фича-флагами](/ru/delivery/deployment-models/#релизы-от-коммита-до-пользователей). Долгоживущие ветки превращают каждое слияние в большое рискованное событие и делают результаты CI менее осмысленными.
- **Что и когда запускать.** На pull request: линтер, типы, юнит-тесты, сборка, часто превью-деплой. На main: более медленные тесты, публикация артефакта, деплой на staging. На релиз: production, при необходимости с подтверждением.
- **Скорость.** [Кэшируйте](/ru/architecture/caching/) то, что дорого создавать заново. Ключ **кэша зависимостей** — lock-файл плюс версии среды выполнения и инструментов. Ключ **кэша результатов сборки** должен учитывать всё, что влияет на результат: исходные файлы, конфигурацию и инструменты; инструменты сборки вроде Turborepo или Nx вычисляют его за вас. Считайте кэши одноразовым ускорением, а не артефактами релиза, и не позволяйте недоверенным джобам записывать кэши, которые читают доверенные. А ещё запускайте джобы параллельно, делите длинные наборы тестов между машинами, а в [монорепозитории](/ru/architecture/repository-layout/) (несколько проектов в одном репозитории) собирайте и тестируйте только проекты, которые затронуло изменение.
- **Merge queues** (очереди слияния). Когда много pull request сливаются одновременно, каждый проходил тесты на более старом main. Очередь слияния тестирует каждое изменение поверх текущего main перед слиянием, поэтому main остаётся зелёным.
- **Окружения.** Защищайте production: обязательные подтверждения, ограниченный круг тех, кто может деплоить, и видимая история того, что и когда было задеплоено.
- **Один деплой за раз на окружение.** Два пайплайна из main могут завершиться не по порядку: более новый задеплоит, а потом более старый его перезапишет. Выполняйте деплои в одно окружение друг за другом и пропускайте уже устаревшие запуски; осторожнее с отменой деплоя на середине — он может остаться выполненным наполовину.

## Секреты и безопасность

Пайплайн держит ключи от production, поэтому он — главная цель для атаки.

- **Храните секреты в хранилище секретов CI-системы**, ограничив их окружениями, которым они нужны. Никогда не коммитьте их и не полагайтесь только на маскирование в логах.
- **Предпочитайте короткоживущие учётные данные.** С **OIDC federation** (федерацией через OIDC) пайплайн доказывает свою личность облачному провайдеру и получает временный токен, так что долгоживущего облачного ключа, который можно украсть, просто нет ([OpenID Connect](/ru/security/auth/#oauth-2-и-openid-connect)). Облачная сторона должна проверять, кто спрашивает: разрешайте роль только вашему репозиторию, нужной ветке или защищённому окружению и ожидаемой аудитории и давайте роли минимальные права.
- **Держите недоверенный код подальше от доверенных джобов.** Pull request из форков запускают код, написанный кем угодно. Они не должны получать ваши секреты, но этого мало: на переиспользуемом self-hosted раннере они могут оставить изменённые файлы или добраться до приватных сетей. Запускайте их на чистых короткоживущих раннерах с ограниченным доступом к сети и никогда не запускайте их код или артефакты позже внутри привилегированного джоба.
- **Закрепляйте сторонние actions и плагины на точной проверенной версии**: полный SHA коммита для GitHub Actions, точные версии или контрольные суммы для плагинов и образов, но никогда не подвижный тег. Поддерживайте эти закрепления в актуальном состоянии. В 2025 году скомпрометированный популярный GitHub Action (`tj-actions/changed-files`) раскрыл секреты в логах многих репозиториев, которые использовали его по тегу.
- **Минимальные права** для собственного токена пайплайна: только чтение, если джобу не нужно больше.
- **[Supply chain](/ru/security/web-attacks/#supply-chain-код-который-писали-не-вы)** (цепочка поставки): устанавливайте ровно то, что указано в lock-файле (`npm ci`), проверяйте обновления зависимостей и подписывайте публикуемое или прикладывайте к нему provenance (подписанную запись о том, как и где это было собрано).

## Типичные проблемы

- **Медленные пайплайны.** При 30 минутах и больше люди копят изменения, перестают ждать и всё равно сливают.
- **Нестабильные тесты** (flaky — падающие случайно). Люди перезапускают до зелёного и начинают игнорировать настоящие сбои. Отслеживайте нестабильные тесты, изолируйте и чините их.
- **Случайная отдельная сборка для каждого окружения**, из-за чего production запускает артефакт, который никогда не тестировали.
- **Пересекающиеся деплои**, когда более старый пайплайн завершается последним и возвращает старую версию.
- **Разные версии инструментов** в CI и на ноутбуках: «в CI работает, локально падает» или наоборот. Закрепляйте версии; используйте одни и те же [образы контейнеров](/ru/delivery/containers/).
- **Секреты в логах** или доступные pull request из форков.
- **Ручные шаги** в релизе («а потом подключиться к серверу и выполнить…»).
- **Main красный несколько дней**, потому что исправлять его не отвечает никто.
- **Скопированные файлы пайплайнов** во множестве репозиториев; используйте общие шаблоны или переиспользуемые workflow.
- **Устаревшие или «отравленные» кэши**: кэш результатов с ключом только по lock-файлу восстанавливает старый код, а кэш, записанный недоверенным джобом, может подбросить код доверенному.

## Как выбирать

- **Большую часть решает место, где лежит код:** GitHub → GitHub Actions; GitLab → GitLab CI/CD; Bitbucket Cloud → Bitbucket Pipelines; self-hosted окружение Atlassian → часто Bamboo. Очень большие или необычные схемы используют Jenkins или Buildkite со своими агентами.
- **Хостинговые или self-hosted раннеры:** хостинговые не требуют обслуживания; self-hosted дают доступ к приватным сетям, особому железу или более низкую стоимость на большом масштабе, но их безопасность и обновления становятся вашей задачей; не запускайте на них недоверенные pull request.
- **Хороший первый пайплайн:** на каждый pull request — установка → линтер и типы → юнит-тесты → сборка; main автоматически деплоится на staging; в production — с подтверждением или автоматически, когда тестам и [мониторингу](/ru/observability/logs-metrics-traces/) уже доверяют.
- **Измеряйте результат** **метриками DORA**, которых сейчас пять: частота деплоев, время прохождения изменения (от коммита до production), доля неудачных изменений (как часто деплой требует исправления), время восстановления после неудачного деплоя и доля переделок (rework rate — доля деплоев, которые были незапланированными исправлениями инцидента в production). Сам пайплайн измеряйте отдельно: время обратной связи, время в очереди и долю нестабильных тестов.

## Ландшафт

- **Хостинговые CI/CD:** GitHub Actions, GitLab CI/CD, Bitbucket Pipelines, CircleCI, Azure Pipelines, Google Cloud Build, AWS CodeBuild и CodePipeline.
- **Self-hosted или со своими агентами:** Jenkins, Atlassian Bamboo, JetBrains TeamCity, Buildkite, Woodpecker CI.
- **Деплой и GitOps** (инструмент следит за Git-репозиторием, описывающим желаемое состояние production, и применяет его): Argo CD, Flux, Spinnaker, Octopus Deploy.
- **Скорость сборки:** удалённое кэширование в Nx и Turborepo, Bazel, кэш сборки Gradle.
- **Безопасность:** OIDC federation у облачных провайдеров, Dependabot и Renovate, Sigstore, SLSA, OpenSSF Scorecard.
