## Модель коротко

С **Cache Components** (`cacheComponents: true`, включено по умолчанию в новых приложениях) **ничего не кэшируется, пока вы об этом не попросите**. Кэширование включается директивой `'use cache'`.

Во время сборки Next.js рендерит каждый маршрут и относит каждую часть дерева к одному из трёх видов:

- **Статическое**: чистый код, импорты, синхронное чтение. Пререндерится автоматически.
- **Кэшируемое**: асинхронная работа, помеченная `'use cache'`. Тоже пререндерится, если время жизни не слишком короткое.
- **Время запроса**: некэшированные fetch, `cookies()`, `headers()`, `searchParams`, неизвестные `params`. Такие части **обязаны** находиться внутри `<Suspense>`. Их fallback (заглушка) попадает в пререндеренную страницу, а реальное содержимое стримится на каждый запрос.

Статические и кэшируемые части образуют **static shell** (статическую оболочку), которую CDN может отдать мгновенно. Это **Partial Prerendering (PPR)**, частичный пререндеринг: одна страница, частично статическая, частично стримящаяся.

**Предыдущая модель** (Next.js 13–15, она же используется при выключенном флаге) многое кэшировала неявно: результаты `fetch` и целые маршруты, управляемые настройками сегментов маршрута вроде `dynamic` и `revalidate`. Её было сложно предсказать. Новая модель явная.

## Четыре вопроса к кэшу: ответы Next.js

| Вопрос | Ответ Next.js |
| --- | --- |
| **Ключ** | Build ID + ID функции + сериализованные аргументы + значения, захваченные из внешней области видимости. Аргументы и возвращаемые значения должны быть сериализуемыми. |
| **Scope** (кто видит данные) | `'use cache'` общий для всех пользователей. `'use cache: private'` может читать cookies и заголовки; его результаты живут только в браузере пользователя. |
| **Свежесть** | `cacheLife(profile)` с тремя числами: `stale` (клиент использует без запроса к серверу), `revalidate` (сервер обновляет в фоне), `expire` (после этого запросы ждут свежих данных). |
| **Инвалидация** | `cacheTag('x')` на записи, затем `revalidateTag('x', 'max')`, `updateTag('x')` или `revalidatePath('/path')` после изменения. |

Встроенные профили `cacheLife`: `seconds`, `minutes`, `hours`, `days`, `weeks`, `max`. Без явного `cacheLife` применяется профиль `default`: stale 5 мин, revalidate 15 мин, не истекает никогда. Документация рекомендует всегда задавать `cacheLife` явно.

**`revalidateTag` или `updateTag`:**

- `revalidateTag(tag, 'max')` работает как **stale-while-revalidate** (отдавать устаревшее, пока обновляется): следующий посетитель ещё получает старые данные, пока генерируются новые. Подходит для каталогов и постов блога. Работает в Server Actions и Route Handlers.
- `updateTag(tag)` **сразу помечает запись истёкшей**, поэтому пользователь, который внёс изменение, сразу его видит (read-your-own-writes, «вижу свои изменения»). Работает только в Server Actions.

## Где живут кэшированные результаты

1. **Пререндеренный HTML**: на диске или в хранилище платформы за CDN. Это static shell, который пересобирается согласно `revalidate` и `expire`.
2. **Хранилище на сервере**: по умолчанию **в памяти, отдельно для каждого инстанса**. В serverless (бессерверной среде) инстансы живут недолго, поэтому записи, созданные во время работы, часто теряются между запросами. `'use cache: remote'` переносит записи в общий долговременный обработчик кэша (например, Redis или KV платформы) ценой сетевого запроса и платы платформе.
3. **Браузер**: клиентский роутер хранит результаты в течение их времени `stale`, минимум 30 секунд.

Все три привязаны к **одному деплою**: build ID входит в ключ, поэтому каждый деплой начинается с холодного кэша.

## Что удивляет

- **Нельзя читать `cookies()` или `headers()` внутри `'use cache'`.** Прочитайте их снаружи, а значение передайте аргументом; оно станет частью ключа. Это относится и к вспомогательным функциям, вызванным изнутри кэшируемой функции.
- **Короткое время жизни не пререндерится.** Профиль `seconds`, `revalidate: 0` или `expire` меньше 5 минут превращают запись в «дыру», которая заполняется во время запроса, вместо того чтобы стать частью static shell.
- **`Math.random()`, `Date.now()` и `crypto.randomUUID()` требуют решения.** Либо сначала вызвать `await connection()` и обернуть компонент в `<Suspense>` (новое значение на каждый запрос), либо поместить вызов в `'use cache'` (одно общее значение).
- **Сам по себе `<Suspense>` ничего не делает динамическим.** Он только даёт fallback. Часть становится частью времени запроса из-за данных, которые она читает.
- **Боты получают полностью динамический рендер.** Некоторым краулерам нужны полные метаданные в `<head>`, поэтому Next.js распознаёт их и пропускает static shell.
- **Draft Mode обходит все записи `'use cache'`.** Так превью CMS видят неопубликованный контент.

## Как это соотносится с обычным HTTP-кэшированием

- Static shell похож на HTML-страницу в кэше CDN со `stale-while-revalidate`.
- `cacheLife` со `stale`, `revalidate` и `expire` похож на `max-age` плюс `stale-while-revalidate` плюс жёсткий предел.
- Теги — та же идея, что и purge по тегам в CDN (surrogate keys в Fastly, cache tags в Cloudflare).
- `'use cache: private'` похож на `Cache-Control: private`: копию хранит только браузер пользователя.
