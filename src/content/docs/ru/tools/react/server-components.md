## Идея

**Server Components** (серверные компоненты) рендерятся заранее, в окружении отдельно от браузера: один раз при сборке или на каждый запрос на сервере. Их код никогда не отправляется в браузер; отправляется только их **результат** — сериализованное описание UI (его часто называют RSC payload — «полезная нагрузка RSC»). Они могут быть `async` и читать данные напрямую: `await db.notes.get(id)` внутри компонента.

**Client Components** (клиентские компоненты) — привычный вид: их код уходит в браузер, они [гидратируются](/ru/architecture/rendering/#гидратация-цена-html-который-выглядит-готовым) (подключают обработчики событий к HTML с сервера) и могут использовать состояние, эффекты и обработчики событий.

Во фреймворке, который их поддерживает (основной production-вариант — App Router в Next.js; другие поддерживают их на разных стадиях), компоненты по умолчанию **серверные**, а `'use client'` отмечает, где начинается клиентский код.

## Не то же самое, что SSR

| | Классический SSR с гидратацией (рендеринг на сервере, без Server Components) | Server Components |
| --- | --- | --- |
| Что создаёт | HTML для первой загрузки страницы | Сериализованное дерево компонентов, которое SSR затем может превратить в HTML |
| Код компонентов в браузере | Весь; гидратация выполняет его снова | Только код Client Components |
| Где выполняется | На сервере, затем снова в браузере | Только на сервере или при сборке |
| При навигации (с клиентским роутером) | Клиент получает данные и рендерит | Фреймворк получает RSC payload следующего маршрута и встраивает его; Client Components, которые остаются на экране, сохраняют состояние |

Здесь сравнивается распространённая схема React; HTML, отрендеренный на сервере, может быть и полностью статическим. Вместе они работают так: приложение с Server Components обычно использует и SSR, чтобы первая загрузка была готовым HTML ([стратегии рендеринга](/ru/architecture/rendering/)).

## Клиентская граница

```
Page (Server Component)               reads the database, ships no JS
 ├─ Article (Server Component)        ships no JS
 └─ LikeButton.tsx  'use client'      boundary: this module and everything
      │                                it imports become client code
      └─ children passed from the server: still rendered on the server
```

- `'use client'` в начале файла отмечает **этот модуль и всё, что он импортирует**, как клиентский код. Директива работает на графе импортов, а не на дереве рендеринга.
- Server Component может рендерить Client Components и передавать им props. Client Component не может импортировать код только для сервера (например, компонент, который читает базу данных): всё, что импортирует клиентский модуль, становится клиентским кодом. Он может **получить Server Component как `children`** или через другой prop; сервер рендерит его и передаёт результат. Исключение — Server Functions: клиентский код может их импортировать и получает ссылку, которая вызывает сервер, а не код самой функции.
- Props, пересекающие границу, должны быть **сериализуемыми** (значения, которые React умеет закодировать на сервере и восстановить в браузере): примитивы, обычные объекты и массивы, `Date`, `Map`, `Set`, типизированные массивы, JSX, Promise (на клиенте читаются через `use`) и Server Functions. Обычные функции и экземпляры классов пересечь её не могут.
- Server Components не могут использовать состояние, эффекты, обработчики событий или API браузера и не могут создавать context (но могут рендерить provider из Client Component).
- **Всё, что передаётся в Client Component, отправляется в браузер.** Передавайте только нужные ему поля и никогда — секреты или целые записи из базы. Пакет `server-only` делает так, что сборка падает, если клиентский код импортирует такой модуль.

## Server Functions: обратное направление

`async`-функцию, помеченную `'use server'`, можно **вызвать с клиента**: из формы, кнопки или любого Client Component. Вызов — это сетевой запрос: аргументы и результат сериализуются, а фреймворк незаметно превращает функцию в эндпоинт. Server Functions предназначены в основном для мутаций, а не для загрузки данных во время рендеринга. Поэтому каждая Server Function — это **публичный эндпоинт**, форма RPC (remote procedure call — вызов функции на другой машине; [стили API](/ru/architecture/api-styles/#как-они-сравниваются)): проверяйте её входные данные и права внутри неё ([авторизация](/ru/security/auth/#авторизация-проверка-того-что-разрешено)).

Частая путаница: `'use server'` отмечает Server Functions, **а не** Server Components. У Server Components директивы нет.

Держите React и фреймворк обновлёнными. В декабре 2025 года критическая уязвимость (CVE-2025-55182) в том, как среда выполнения Server Components декодировала запросы к Server Functions, позволяла удалённо выполнять код на необновлённых серверах — даже в приложениях, где своих Server Functions не писали. Она была в пакетах `react-server-dom-*`, которые фреймворки включают в себя, поэтому обновить только `react` было недостаточно; первые исправленные версии — 19.0.1, 19.1.2 и 19.2.1. Следите за советами по безопасности своего фреймворка, чтобы знать текущие исправленные версии.

## Где живут данные и кэширование

Server Components определяют, **где выполняется код**, а не **что [кэшируется](/ru/architecture/caching/)**:

- Без кэширования Server Component, который получает данные, делает это при каждом рендере.
- Функция `cache()` из React убирает повторные вызовы в пределах **одного запроса**: несколько компонентов, которые вызывают одну и ту же обёрнутую через `cache` функцию с одинаковыми аргументами (например, ID пользователя), делят один запрос к базе. Каждый вызов `cache(fn)` создаёт свой кэш, а аргументы сравниваются по идентичности, поэтому передавайте простые значения, а не заново созданные объекты.
- Кэширование между запросами и пользователями — задача фреймворка: в Next.js это `'use cache'` и Cache Components ([кэширование в Next.js](/ru/tools/nextjs/caching/)).
- После мутации через Server Function ваш код вызывает API фреймворка, чтобы инвалидировать затронутые записи кэша и обновить UI, который их показывает ([серверное состояние при рендеринге на сервере](/ru/architecture/state/#серверное-состояние-при-рендеринге-на-сервере)). Ничего из этого не происходит автоматически: вернуть результат, обновить маршрут и сбросить закэшированные данные — отдельные шаги.

## Что удивляет

- **`'use client'` не значит «только в браузере».** Client Components обычно сначала рендерятся в HTML на сервере, а потом гидратируются, поэтому API только для браузера по-прежнему место в эффектах.
- **Один `'use client'` в модуле у самого верха** делает клиентским кодом всё, что этот модуль импортирует, и бандл снова большой (Server Components, переданные как `children`, всё равно остаются на сервере).
- **Серверные модули, импортированные клиентским кодом**: клиент базы данных в клиентском файле либо ломает сборку, либо, что хуже, утекает; защищайте серверные модули с помощью `server-only`.
- **Серверные waterfalls**: вложенные Server Components, которые делают `await` один за другим, замедляют запрос. Запускайте независимые запросы параллельно или передавайте Promise вниз и читайте их через `use` внутри границ [Suspense](/ru/tools/react/suspense/).
- **Пересечение при первой загрузке**: контент, отрендеренный из props, есть и в начальном HTML, и в RSC payload, что увеличивает объём передачи. Props, которые компонент вообще не рендерит, всё равно есть в payload, так что спрятанное со страницы значение не становится секретным.
- **API, которые используют сборщики и фреймворки** для реализации Server Components, не следуют semver (правилу, по которому ломать совместимость может только новая major-версия) внутри React 19, поэтому фреймворки закрепляют точные версии React.

## Как это соотносится с концепцией

| Вопрос из [стратегий рендеринга](/ru/architecture/rendering/) | Ответ с Server Components |
| --- | --- |
| Где создаётся HTML? | Server Components создают UI payload на сервере или при сборке; шаг SSR превращает его в HTML для первой загрузки |
| Когда? | При сборке или на каждый запрос — фреймворк решает для каждого маршрута |
| Как приходит интерактивность? | JavaScript отправляют и гидратируются только Client Components. `'use client'` решает, какой код уходит в браузер, — немного похоже на islands; когда гидратируется каждая часть, планирует [Suspense](/ru/tools/react/suspense/) |
| Где читаются данные? | На сервере, рядом с базой данных |
