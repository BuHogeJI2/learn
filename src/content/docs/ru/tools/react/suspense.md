## Идея

Граница `<Suspense>` — это **заглушка загрузки для части дерева**. Пока что-то внутри неё, чего React умеет ждать (см. ниже), не готово, React показывает `fallback` (UI загрузки, который вы передаёте); когда готово всё внутри, React показывает содержимое разом.

Suspense **координирует UI загрузки**. Он не получает данные, не [кэширует](/ru/architecture/caching/) их и не обрабатывает ошибки; это делают другие части, а Suspense на них реагирует.

## Что может заставить границу ждать

По документации React, граница ждёт:

- код компонента, загружаемый через `lazy`;
- Promise, прочитанный через `use`, включая данные, которые стримятся из [Server Components](/ru/tools/react/server-components/) или загружаются через фреймворк или библиотеку с поддержкой Suspense;
- стили, отрендеренные через `<link rel="stylesheet">` с пропом `precedence`;
- при стриминговом рендеринге на сервере — HTML, который ещё не пришёл.

Данные, полученные в `useEffect` или в обработчиках событий, она **не** замечает: такая загрузка никогда не включает fallback, поэтому компонент должен сам управлять своим состоянием загрузки. Обычные картинки и шрифты границу тоже не задерживают.

Библиотеки данных подключаются через эти механизмы: в TanStack Query и Apollo Client есть `useSuspenseQuery`, Relay построен вокруг Suspense, а фреймворки передают Promise из своих загрузчиков или Server Components. Если вы вызываете `use` сами, Promise для одних и тех же данных должен сохранять **ту же идентичность** между рендерами: создавайте его до рендера (в загрузчике или передавайте с сервера) или берите из кэша библиотеки. Новый объект Promise на каждом рендере заставляет React приостанавливаться снова и снова, а если его создание ещё и запускает запрос, данные загружаются заново.

## Границы — это проектное решение

- **Компоненты под одной ближайшей границей появляются вместе.** Вкладывайте границы, чтобы задать последовательность загрузки: оболочка страницы → основной контент → комментарии.
- **Где вы ставите границу, то пользователь и видит во время ожидания.** Слишком высоко — вся страница превращается в один спиннер; слишком мелко — части выскакивают по одной и сдвигают макет ([CLS](/ru/observability/web-vitals/#cls-насколько-стабилен-макет), сдвиг макета). Делайте fallback того же размера, что и контент, который он заменяет.
- React **ограничивает частоту**, с которой показывает приостановленный контент (внутренняя эвристика, сейчас во многих случаях около 300 мс), поэтому границы, которые стали готовы почти одновременно, часто появляются вместе. Не опирайтесь на точное число.

## Обновления: transitions сохраняют то, что уже показано

Когда **уже видимый** контент снова приостанавливается (пользователь переходит на другую страницу или меняет фильтр), React по умолчанию заменил бы его на fallback, а это ощущается как шаг назад. Это предотвращают два инструмента:

- **`startTransition` / `useTransition`**: помечают обновление как несрочное, и React продолжает показывать старый UI. Хук `useTransition` также возвращает флаг `isPending` для небольшого индикатора. Роутеры, построенные под Suspense, сами оборачивают навигацию в transition. (Граница, получившая новый `key`, всё равно сбрасывается — намеренно.)
- **`useDeferredValue`**: позволяет части UI отставать, например результатам поиска, которые продолжают показывать результаты предыдущего запроса, пока загружаются новые.

Срочные обновления, например ввод в поле, сохраняют свой приоритет: держите собственное состояние поля срочным, а дорогой UI, который от него зависит, позвольте отложить. Новые вложенные границы всё равно показывают свои fallback.

## Ошибки — это отдельная граница

Suspense обрабатывает **«ещё не готово»**; **error boundary** (граница ошибок) обрабатывает **«не получилось»**: она перехватывает ошибки, выброшенные при рендеринге её детей, включая отклонённый Promise, прочитанный через `use`, и показывает свой fallback. Ошибки в обработчиках событий и других колбэках не перехватываются; обрабатывайте их в коде. Показ fallback ошибки ничего не повторяет: кнопка «попробовать снова» или фреймворк должны сбросить границу и загрузить данные заново. Ставьте error boundaries вокруг частей UI, которые должны падать независимо; если рядом с виджетом её нет, его ошибка уходит к следующей границе выше — возможно, ко всей странице.

## Suspense на сервере

- **Стриминг SSR** (рендеринга на сервере). Сервер отправляет оболочку страницы с fallback на своих местах, а затем стримит HTML каждой границы, как только он готов; небольшой скрипт подставляет его на место ([стриминг](/ru/architecture/rendering/#стриминг)). Границы — это единицы стриминга.
- **Ошибки внутри границы Suspense во время SSR** не останавливают поток: React отправляет в HTML fallback этой границы, а клиент пробует отрендерить эту часть ещё раз (только клиентский код: код Server Components в браузере никогда не выполняется). Ошибка в самой оболочке, вне всех границ, не оставляет ничего для стриминга; сервер должен ответить страницей ошибки.
- **Селективная гидратация.** Каждая граница гидратируется отдельно, и React первой гидратирует ту часть, с которой взаимодействует пользователь ([гидратация](/ru/architecture/rendering/#гидратация-цена-html-который-выглядит-готовым)).
- **Фреймворки строятся на этом.** В App Router Next.js файл `loading` становится границей Suspense; при включённых Cache Components части страницы, которым нужны данные времени запроса, должны находиться внутри границы, чтобы статическую оболочку можно было пререндерить и отправить первой ([кэширование в Next.js](/ru/tools/nextjs/caching/)).

## Что удивляет

- **Загрузка в `useEffect` не включает fallback.** Это не источник данных для Suspense; такой компонент показывает своё состояние загрузки или ничего.
- **Новый Promise на каждом рендере**, переданный в `use`, приостанавливает рендер снова и снова и перезапрашивает данные, если его создание запускает запрос.
- **Waterfall** (цепочка запросов, где каждый ждёт предыдущий): родитель приостанавливается, и дочерний компонент начинает загружаться, только когда работа родителя завершилась и рендеринг дошёл до него. Начинайте загрузку заранее (в загрузчике роутера или как Promise, переданные с сервера), а не внутри каждого компонента.
- **Видимый контент снова приостанавливается** и заменяется на fallback, если обновление не transition и не использует отложенное значение.
- **Приостановленное поддерево, которое ни разу не появилось, не хранит состояние**; React рендерит его с нуля, когда оно готово.
- **Layout-эффекты скрытого контента очищаются** и запускаются снова, когда он показывается.

## Как это соотносится с концепцией

| Концепция | В React |
| --- | --- |
| [Стриминг](/ru/architecture/rendering/#стриминг) | Каждая граница Suspense — кусок, который стримится, когда готов |
| Селективная гидратация | Каждая граница гидратируется отдельно, самая срочная — первой; это меняет то, когда части становятся интерактивными, а не то, сколько JavaScript отправляется |
| Состояния загрузки [серверного состояния](/ru/architecture/state/#чтение) | Граница с fallback вместо флагов `isLoading` в каждом компоненте |
| Static shell (статическая оболочка) с динамическими «дырами» | «Дыры» — это границы Suspense (Partial Prerendering в Next.js) |
