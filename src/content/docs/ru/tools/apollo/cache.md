## Идея

Apollo Client, [GraphQL](/ru/architecture/api-styles/)-клиент, хранит серверные данные в **нормализованном кэше** — `InMemoryCache`. Это устройство «нормализованного кэша» из [Клиентского и серверного состояния](/ru/architecture/state/#чтение): результаты разбиваются на сущности по типу и ID, каждая хранится один раз, поэтому изменение одного объекта видно в каждом запросе, где он есть.

## Как хранятся данные

Результат запроса разбивается на **плоскую таблицу поиска** из объектов, которые ссылаются друг на друга:

```
query result                             cache
{ order(id: 42) {                        ROOT_QUERY: { order({"id":42}): → Order:42 }
    id                                   Order:42:   { id, total, customer: → Customer:7 }
    total                                Customer:7: { id, name }
    customer { id name } } }
```

- **Cache ID** (ID в кэше): по умолчанию `__typename` плюс `id` (или `_id`): `Order:42`. Типам, которые определяются другими полями, задают `keyFields` в конфигурации кэша (например, `Product`, который определяется по `sku`).
- **Объекты без идентичности** (без `id`, `_id` или настроенных `keyFields`) не нормализуются: они хранятся внутри родителя, и добраться до них можно только через него.
- **Слияние**: когда тот же идентифицированный объект приходит снова, новые значения его полей перезаписывают старые, а поля, которых в нём не было, сохраняются. Объекты без идентичности так не сливаются: новый вложенный объект или массив заменяет старый, поэтому поля, загруженные другим запросом, могут пропасть, если их не объединяет своя функция `merge`.
- **Корневые поля** вроде `order(id: 42)` живут в `ROOT_QUERY` с ключом из имени поля и аргументов.

**Field policies** (политики полей, задаются для каждого типа в `fields` внутри `typePolicies`) настраивают отдельные поля: функция `read` вычисляет или форматирует значение, а функция `merge` решает, как входящие данные объединяются с закэшированными. Главное применение — пагинация (загрузка списка по страницам), и ей нужны две настройки: `merge` склеивает страницы в один список, а `keyArgs` говорит, какие аргументы делают список *другим*. Номер страницы или курсор — не ключевой аргумент, а фильтр или категория — ключевой. Хелперы вроде `offsetLimitPagination` и `relayStylePagination` не используют ключевых аргументов, если их не передать, поэтому списки с разными фильтрами склеятся в один. (Более старая [директива `@connection`](/ru/tools/apollo/directives/#собственные-директивы-apollo-client) делает то же внутри запроса.)

## Когда используется сеть: fetch policies

**Fetch policy** (политика загрузки) — правило, по которому отслеживаемый запрос (например, `useQuery`) выбирает между кэшем и сетью:

| `fetchPolicy` | Поведение |
| --- | --- |
| `cache-first` (по умолчанию) | Ответить из кэша; спросить сервер, только если чего-то из запрошенного нет |
| `cache-and-network` | Сразу ответить из кэша (если там есть всё запрошенное) *и* спросить сервер, затем обновить |
| `network-only` | Всегда спрашивать сервер; сохранять результат в кэш |
| `no-cache` | Всегда спрашивать сервер; не читать из кэша и не писать в него, игнорировать последующие обновления кэша |
| `cache-only` | Никогда не спрашивать сервер |
| `standby` | Как `cache-first`, но не обновляться автоматически, когда меняются закэшированные данные |

`cache-first` означает **отсутствие правила свежести**: однажды закэшированные данные остаются, пока их что-нибудь не изменит. Выбирайте политику для каждого запроса или задайте `nextFetchPolicy`, чтобы после первого запроса поведение менялось (например, `cache-and-network` при первой загрузке и `cache-first` потом); при смене переменных запрос обычно снова начинает с первой политики. Polling (`pollInterval`) и `refetch` дают обновление по времени или вручную.

## Как поддерживать кэш правильным после мутаций

**Мутация** — операция GraphQL, которая меняет данные на сервере. Обычный вопрос из [записи серверного состояния](/ru/architecture/state/#запись) с ответом для Apollo:

- **Мутация возвращает изменённый объект** с полями его идентичности (обычно `id`) и изменёнными полями: кэш сливает его, и каждый активный запрос, который читает этот объект из кэша, обновляется. Дополнительного кода не нужно.
- **Состав и порядок списков**: элементы добавлены или удалены, или элемент изменился так, что должен попасть в отфильтрованный или отсортированный список либо уйти из него. Кэш не может угадать, какие списки затронуты, и не пересчитывает итоги. Обновите их сами функцией `update` (`cache.modify`, `cache.updateQuery`) или перезапросите затронутые запросы (`refetchQueries`).
- **Удаления**: уберите объект через `cache.evict` и почистите недостижимые объекты через `cache.gc`.
- **[Оптимистичные обновления](/ru/architecture/state/#запись)** (показ ожидаемого результата до подтверждения сервера): `optimisticResponse` сразу записывает ожидаемый результат во временный слой кэша; его заменяет настоящий ответ или откат при ошибке.

## Что удивляет

- **Нет полей идентичности в запросе** — и нормализация этого объекта не работает: один и тот же заказ, найденный через двух разных родителей, хранится дважды, и копии не обновляют друг друга. Запрашивайте поля, по которым кэш определяет идентичность (по умолчанию `id`), и в запросах, и в результатах мутаций; `__typename` Apollo добавляет сам.
- **Списки не обновляются после создания или удаления.** Это самая частая жалоба «кэш сломан»; кэш сделал ровно то, что мог.
- **Нет истечения срока.** С `cache-first` данные могут оставаться устаревшими всю сессию, если не выбрать другую политику, не включить polling и не перезапрашивать.
- **Свои ID требуют `keyFields`**, иначе объекты этого типа хранятся внутри родителей.
- **Фрагментам** (переиспользуемым наборам полей) **на интерфейсах и union** (типах, которые могут быть одним из нескольких типов объектов) нужен `possibleTypes` в конфигурации кэша, чтобы правильно сопоставляться.
- **Кэш принадлежит экземпляру клиента, а не пользователю.** После выхода, входа или переключения на другой аккаунт или tenant очистите его (`clearStore`) или сбросьте (`resetStore`, который ещё и перезапрашивает активные запросы), иначе следующий пользователь может увидеть данные предыдущего. Если ID повторяются между tenants, идентичность в кэше должна включать tenant.
- **[Рендеринг на сервере](/ru/architecture/rendering/)**: создавайте новый кэш на каждый запрос на сервере и никогда не делите один кэш между пользователями ([scope](/ru/architecture/caching/#ментальная-модель-четыре-вопроса-к-любому-кэшу), кто видит данные). У Apollo есть пакеты интеграции для Next.js и React Router, которые передают кэш в браузер.
- **В версии 4 React API переехали**: хуки вроде `useQuery` импортируются из `@apollo/client/react`.

## Как это соотносится с концепцией

| Вопрос из [Кэширования](/ru/architecture/caching/) | Ответ Apollo |
| --- | --- |
| Ключ | Cache ID (`__typename:id` или `keyFields`) для объектов; имя поля плюс ключевые аргументы для полей — корневых или любого объекта |
| Scope | Один экземпляр клиента в памяти, а не автоматически один пользователь; на сервере — один запрос |
| Свежесть | По умолчанию нет; решают fetch policy, polling и перезапросы |
| Инвалидация | Результаты мутаций сливаются автоматически; списки и удаления требуют `update`, `evict` или `refetchQueries` |
