## Идея

**Директива** — это аннотация, которая начинается с `@` и меняет то, как выполняется или обрабатывается часть документа [GraphQL](/ru/architecture/api-styles/). В приложении на Apollo бывает три вида директив, и для каждой важен вопрос, **кто её обрабатывает**: сервер, клиент или оба.

| Вид | Примеры | Кто обрабатывает |
| --- | --- | --- |
| **Стандартные GraphQL** | `@include`, `@skip` в запросах; `@deprecated` в схемах | Движок GraphQL на сервере (и инструменты для схемы) |
| **Собственные директивы Apollo Client** | `@client`, `@export`, `@connection`, `@nonreactive`, `@unmask` | Apollo Client, локально; поля с `@client` никогда не отправляются на сервер |
| **Частичная доставка** (incremental delivery) | `@defer`, `@stream` | Оба: сервер должен её поддерживать, а клиент — понимать формат ответа |

Серверы могут также объявлять **свои директивы схемы** (для авторизации, ограничения стоимости или федерации — объединения нескольких сервисов в один граф, например `@key` в Apollo Federation); они живут в схеме, и это забота сервера.

## Стандартные директивы

- **`@include(if: $flag)` и `@skip(if: $flag)`** включают или убирают поле в зависимости от переменной, так что один документ запроса может обслуживать несколько вариантов UI. Их вычисляет сервер при выполнении (Apollo Client тоже учитывает их при чтении кэша); поле остаётся частью операции, а выбирают переменные. Это не механизм контроля доступа.
- **`@deprecated(reason: "…")`** помечает поле схемы как устаревшее. Инструменты предупреждают клиентов, которые всё ещё его используют, — так GraphQL API развиваются без версий ([развитие API](/ru/architecture/api-styles/#развитие-долгосрочная-цена)).

## Собственные директивы Apollo Client

Их понимает Apollo Client, а не сервер:

- **`@client`**: поле вычисляется локально (локальное состояние или вычисляемое значение), а не загружается. В Apollo Client 4 для этого нужен настроенный `LocalState`; значение может браться из кэша, политики поля, локального резолвера или reactive variable. Это позволяет в одном запросе смешивать серверные и клиентские данные.
- **`@export(as: "name")`**: используется вместе с `@client`; кладёт значение локального поля в объявленную переменную запроса до того, как выполнится серверная часть операции.
- **`@connection(key: "…")`**: даёт полю стабильный ключ кэша независимо от аргументов пагинации, чтобы страницы одного списка хранились вместе; его аргумент `filter` оставляет в ключе аргументы, которые делают список другим (категория, пользователь). Политики полей с `keyArgs` (аргументами, которые определяют список) в [конфигурации кэша](/ru/tools/apollo/cache/#как-хранятся-данные) — рекомендуемый способ сделать то же самое в одном месте.
- **`@nonreactive`**: изменения внутри этого поля или фрагмента (переиспользуемого набора полей) не запускают обновление запроса, который его содержит. Он нужен для больших списков: родительский запрос игнорирует изменения каждого элемента, а компонент каждого элемента читает свой фрагмент (через `useFragment`), поэтому перерендеривается только изменившийся элемент. Без этой второй части UI устаревает.
- **`@unmask`**: при включённом **data masking** (маскировании данных) результат запроса показывает только поля, выбранные в нём напрямую; поля из spread фрагмента читаются через этот фрагмент (например, через `useFragment`). `@unmask` делает поля spread видимыми в объемлющем результате — в основном на время миграции существующего приложения. Маскирование упорядочивает зависимости по данным, но ничего не скрывает от браузера: все загруженные поля всё равно есть в клиенте и его кэше.

## Частичная доставка: @defer и @stream

```
query ProductPage {
  product(id: 7) {
    name price                        ← arrives in the first part
    ... @defer { recommendations { … } }  ← arrives later, in the same response
  }
}
```

- **`@defer`** на фрагменте позволяет серверу отправлять ответ **частями**: сначала быстрые поля, а отложенный фрагмент — когда он готов, всё в одном HTTP-ответе. Он даёт данным API то же, что [стриминг](/ru/architecture/rendering/#стриминг) даёт HTML: медленное поле больше не держит весь экран.
- **`@stream`** на списке отправляет сначала первые `initialCount` элементов, а остальные — по мере готовности.

Что для этого нужно в Apollo Client 4:

- **Нужно настроить incremental handler** (обработчик частичной доставки). Без него запрос с `@defer` или `@stream` падает с ошибкой. Формат доставки **пока не стандартизирован**, и обработчик должен соответствовать точной ревизии формата на вашем сервере: например, `Defer20220824Handler` соответствует формату Apollo Router, а `GraphQL17Alpha9Handler` — формату graphql-js 17.0.0-alpha.9. (`@stream` поддерживается с Apollo Client 4.1.)
- **Сервер должен это поддерживать.** Apollo Router поддерживает, но некоторые поля в его плане запроса отложить нельзя, и они вычисляются до отправки первой части, так что одна поддержка не гарантирует, что медленное поле уйдёт с критического пути. Для других серверов проверяйте.
- **Компонент должен справляться с полями, которые ещё не пришли.** В результате `useQuery`, пока части ещё приходят, `dataState` равен `"streaming"`, а `loading` остаётся `true` до последней части. При первой загрузке отложенных полей нет; при перезапросе предыдущие значения могут оставаться и сливаться с новыми частями. Показывайте то, что пришло: если прятать всё, пока `loading` не станет false, выигрыш пропадает.
- **Ничто посередине не должно буферизовать ответ.** Прокси или [CDN](/ru/web-platform/cdn/) (серверы между пользователями и вашим origin), который ждёт весь ответ целиком, снова превращает части в один медленный ответ.

## Что удивляет

- **`@defer` сам по себе ничего переносимого не делает.** Без подходящего обработчика на клиенте и поддержки на сервере он падает или ломается; это не переключатель, который заставляет любой запрос стримиться.
- **Отложенные поля сначала могут быть `undefined`.** Пусть сгенерированные типы TypeScript это отражают (генерация кода для частичной доставки плюс соответствующие переопределения типов Apollo); типы не меняют того, что приходит во время выполнения.
- **Полям с `@client` нужны настройка и источник**: без настроенного `LocalState` операция падает, а без значения в кэше, политики поля или резолвера поле пустое.
- **`@skip` и `@include` не уменьшают операцию.** Пропущенное поле остаётся частью операции, которую получает сервер (текстом или ID при persisted queries); меняется только переменная. Не используйте их, чтобы скрывать данные, которые пользователю видеть нельзя.
- **Директивы — часть операции.** [Persisted queries](/ru/architecture/api-styles/#как-они-сравниваются) (операции, заранее сохранённые на сервере и отправляемые по ID) и списки разрешённых операций включают их, поэтому изменение директивы в серверной части меняет операцию. Клиентские части удаляются перед отправкой, поэтому их изменение операцию не меняет.

## Как это соотносится с концепцией

| Понятие из [стилей API](/ru/architecture/api-styles/) | В Apollo |
| --- | --- |
| Клиент выбирает форму ответа | `@include` и `@skip` позволяют одному документу покрыть несколько вариантов |
| Медленная часть не должна блокировать остальное | `@defer` и `@stream` доставляют ответ частями |
| Развитие контракта без поломки клиентов | `@deprecated` плюс отслеживание использования |
| Одно место для серверных и клиентских данных | Поля с `@client` в том же запросе — рядом с серверными данными в [кэше](/ru/tools/apollo/cache/) или из локального состояния |
