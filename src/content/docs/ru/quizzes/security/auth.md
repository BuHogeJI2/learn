## 1. Чужой счёт

Клиент сообщает, что после замены `/invoices/1042` на `/invoices/1043` в адресной строке он увидел счёт другой компании. Эндпоинт требует входа. В чём ошибка и как предотвратить этот класс ошибок?

<details>
<summary>Ответ</summary>

Сервер проверяет **аутентификацию** (вошёл ли кто-то), но не **авторизацию** для конкретного объекта (принадлежит ли счёт 1043 компании этого пользователя). Это IDOR (небезопасная прямая ссылка на объект), часть broken access control (нарушения контроля доступа) — первого пункта OWASP Top 10. В multi-tenant приложении (много компаний-клиентов, tenant, в одной системе) это ещё и утечка данных между клиентами.

Исправьте этот эндпоинт, а затем сделайте так, чтобы проверку было трудно забыть: общий слой политик, который вызывает каждый обработчик (`can(user, 'read', invoice)`), функции доступа к данным, которые всегда фильтруют по tenant, и тесты, которые вызывают эндпоинты от имени не того пользователя и ожидают `403` или `404`. Случайные ID (UUID) усложняют подбор, но не исправляют ошибку; исправляет проверка.

</details>

## 2. Скрытые кнопки

Пользователи без прав администратора не видят кнопку «Удалить проект». Ревьюер спрашивает, где сервер проверяет роль, и разработчик отвечает: «Нельзя нажать кнопку, которую не видно». Что не так?

<details>
<summary>Ответ</summary>

Скрыть кнопку — это **UX, а не безопасность**. Любой может вызвать эндпоинт напрямую через `curl`, консоль браузера или изменённый запрос. UI только отражает права; сервер должен проверять их на каждом запросе.

Проверяйте право в эндпоинте (и во всех остальных точках входа, которые могут удалить проект: [GraphQL](/ru/architecture/api-styles/)-мутациях, [серверных функциях](/ru/tools/react/server-components/#server-functions-обратное-направление), [фоновых задачах](/ru/architecture/background-jobs/)). Проверку в UI тоже оставьте, чтобы пользователи не видели действий, которые не могут выполнить, но считайте её удобством.

</details>

## 3. Украденный ноутбук

Приложение использует JWT (самодостаточные токены, подписанные сервером, с ID пользователя и сроком действия), которые живут 30 дней и хранятся в cookie. Пользователь сообщает о краже ноутбука и нажимает «Выйти на всех устройствах», но сессия на ноутбуке продолжает работать. Почему и как бы вы это переделали?

<details>
<summary>Ответ</summary>

Самодостаточный токен действует, пока не **истечёт его срок**. Сервер проверяет его подпись и claims, включая срок действия, но не хранит записи о сессии, поэтому удалять ему нечего: «выход» удаляет копию в браузере, а не у вора.

Варианты:

- **Сессии на сервере**: cookie хранит случайный ID сессии, а сервер ищет его на каждом запросе. Отзыв — это удаление записи. Цена — один быстрый поиск на запрос.
- **Короткоживущие access tokens** (токены, которые принимает API; живут минуты) плюс **ротируемые refresh tokens** (долгоживущие токены только для получения новых access tokens, заменяемые при каждом использовании), которые отслеживаются на сервере. Выход на всех устройствах отзывает refresh tokens; access token умирает в течение минут.
- **Список отозванных токенов**, который проверяется на каждом запросе, — это всё равно возвращает поиск.

Для собственного веб-приложения и бэкенда сессии на сервере обычно самый простой выбор, который выполняет требование.

</details>

## 4. «Войти через Google» и корпоративный SSO

Вы делаете B2B-продукт: React-приложение с собственным бэкендом. Маленькие клиенты хотят «Войти через Google», большие — SSO (single sign-on, единый вход) через корпоративный identity provider (сервис, через который входят их сотрудники, например Okta или Entra ID). Как вы спроектируете вход?

<details>
<summary>Ответ</summary>

Используйте **[OpenID Connect](/ru/security/auth/#oauth-2-и-openid-connect)** (OIDC, стандартный протокол входа поверх OAuth; добавьте SAML, более старый корпоративный стандарт, где этого требует клиент) через готовый сервис или зрелую библиотеку, а не пишите сами. Используйте Authorization Code flow с PKCE (проверкой, что вход завершает то же приложение, что его начало), который завершается на **вашем бэкенде**: он проверяет ID token (подписанное провайдером утверждение о том, кто вошёл) и затем создаёт **вашу собственную сессию** с `HttpOnly`-cookie.

Так браузер никогда не держит токены провайдера, любой способ входа заканчивается одинаковой сессией, а отзыв работает одинаково для всех клиентов. Правила авторизации (кто что может делать в аккаунте клиента) остаются в вашем коде: это ваша бизнес-логика, а не identity provider. Компромисс готового сервиса — плата за пользователя и зависимость от поставщика против месяцев критичной для безопасности работы.

</details>

## 5. ID token вместо ключа API

После «Войти через Google» SPA (одностраничное приложение в браузере) отправляет Google **ID token** в ваш API в заголовке `Authorization`, а API принимает любой действительный Google ID token. Что здесь не так?

<details>
<summary>Ответ</summary>

**ID token предназначен для клиента**: он сообщает вашему приложению, кто вошёл. Это не access token для вашего API. Его аудитория — приложение, которое его запросило, поэтому API, принимающий «любой действительный Google ID token», может принять токен, выпущенный для **чужого приложения**, а отозвать его или ограничить то, что он разрешает, API не может.

Проверяйте ID token один раз, на бэкенде, при входе (подпись, издатель, аудитория, срок действия), а затем создавайте свою сессию (или выпускайте свои access tokens). API проверяет ваши учётные данные, а не доказательство личности от Google.

</details>
