Обдумайте каждый сценарий, прежде чем открыть ответ. Единственно верный вариант бывает редко. Хороший ответ называет компромисс.

## 1. «Исправляем» ошибку CORS через `no-cors`

Фронтенд на `https://app.example` вызывает `https://api.partner.example/prices` и получает ошибку CORS (браузер не даёт скрипту прочитать ответ с другого origin — другой схемы, хоста или порта). Разработчик добавляет в `fetch` `mode: 'no-cors'`, ошибка пропадает, но данные пустые. Что произошло и как исправить на самом деле?

<details>
<summary>Ответ</summary>

`no-cors` запрашивает **непрозрачный ответ** (opaque response): запрос отправляется, но скрипту нельзя увидеть статус, заголовки или тело. Ошибка исчезла потому, что код отказался от чтения, а не потому, что доступ разрешили.

[Same-origin policy](/ru/security/browser-boundaries/#ментальная-модель-origin-сайт-и-три-вида-доступа) (правило браузера, которое не даёт скриптам одного origin читать данные другого) блокирует **чтение**, и разрешить его может только владелец ресурса — через [CORS](/ru/security/browser-boundaries/#cors-сервер-сам-разрешает-себя-читать). Исправление на сервере: `api.partner.example` должен отправлять `Access-Control-Allow-Origin: https://app.example` (и отвечать на preflight — запрос разрешения, который браузер отправляет перед некоторыми запросами на другой origin, — если он есть). Если этот сервер вам не подконтролен, вызывайте его со своего бэкенда, который не ограничен CORS, и отдавайте результат со своего origin.

</details>

## 2. «Наш API может вызвать только наш фронтенд»

Команда ограничивает CORS своего API значением `https://app.example` и говорит, что теперь никто другой не может пользоваться API, поэтому [rate limiting](/ru/architecture/reliability/#защита-сервиса-от-перегрузки) (ограничение частоты вызовов клиента) и строгие проверки [авторизации](/ru/security/auth/#авторизация-проверка-того-что-разрешено) не нужны. Они правы?

<details>
<summary>Ответ</summary>

Нет. CORS управляет только тем, что **браузеры** разрешают читать скриптам на других сайтах. `curl`, скрипт на Python или мобильное приложение полностью игнорируют CORS и могут вызвать любой эндпоинт. Даже в браузере простые запросы отправляются и выполняются на сервере; скрыт только ответ.

API по-прежнему нужны аутентификация и авторизация на каждом запросе и rate limiting против злоупотреблений. CORS защищает ваших пользователей внутри их браузера, а не ваш сервер.

</details>

## 3. Настройка CORS, которая доверяет всем

Чтобы поддержать много сайтов-партнёров, сервер копирует заголовок запроса `Origin` в `Access-Control-Allow-Origin` и ещё отправляет `Access-Control-Allow-Credentials: true`. В чём риск?

<details>
<summary>Ответ</summary>

Теперь любой сайт в интернете может читать ответы **с cookies ваших пользователей**. Пользователь, вошедший в ваше приложение, открывает вредоносную страницу; её скрипт вызывает ваш API с `credentials: 'include'`, cookies прикладываются (если это позволяет `SameSite`), и ответ с персональными данными становится доступен атакующему.

Используйте фиксированный **список разрешённых** полных origin и сравнивайте строки точно (не через `endsWith`, который совпадёт и с `evilapp.example`). Не разрешайте `Origin: null`. Отправляйте `Vary: Origin` и убедитесь, что любой кэш перед API хранит отдельную копию для каждого origin (вопрос 6), чтобы разрешение одного origin не отдавалось другому. Если партнёрам нужны данные без cookies пользователей, дайте им отдельный API без учётных данных.

</details>

## 4. Где хранить загрузки пользователей?

Пользователи могут загружать HTML- и SVG-файлы, которые открывают другие люди. Вы планируете отдавать их с `https://files.shop.example`. Хороший ли это выбор?

<details>
<summary>Ответ</summary>

Рискованный. `files.shop.example` — другой **origin**, но тот же **сайт**, что и `shop.example`. Вредоносная загруженная HTML-страница работает с вашим регистрируемым доменом: её запросы к `shop.example` считаются same-site, поэтому `SameSite`-cookies с ними отправляются, а cookie с `Domain=shop.example` для неё общая.

Отдавайте недоверенный контент с **отдельного регистрируемого домена**, например `shop-usercontent.example`. Именно поэтому GitHub Pages использует `github.io`, а Google — `googleusercontent.com`. Кроме того, где возможно, отдавайте загрузки с `Content-Disposition: attachment` или строгой [CSP](/ru/security/web-attacks/#csp-ограничиваем-то-что-может-выполняться) (заголовком, который ограничивает, какие скрипты могут выполняться). Цена — ещё один домен, который нужно купить и настроить.

</details>

## 5. Preflight перед каждым запросом

Приложение живёт на `https://app.shop.example`, а API — на `https://api.shop.example`. Каждый вызов API показывает во вкладке Network два запроса: `OPTIONS`, а затем настоящий. Мобильные пользователи чувствуют задержку. Какие есть варианты?

<details>
<summary>Ответ</summary>

Это **preflight**: два хоста — разные origin (одного сайта недостаточно), а запросы используют JSON-тело или заголовок `Authorization`, поэтому браузер сначала спрашивает разрешения.

Варианты:

- Отдавать API с **того же origin**, например по пути `/api` на `app.shop.example`, с маршрутизацией через [reverse proxy или CDN](/ru/web-platform/cdn/#ментальная-модель-reverse-proxy-перед-всем-остальным). Нет CORS, нет preflight, проще cookies. Обычно это лучший выбор для приложения и его собственного API.
- Оставить разные origin и отправлять `Access-Control-Max-Age`, чтобы браузер кэшировал ответ на preflight.

Заставлять запросы выглядеть «простыми» (например, отправлять JSON как `text/plain`) позволяет избежать preflight, но скрывает настоящий тип содержимого и ослабляет защиту от [CSRF](/ru/security/web-attacks/#csrf-запросы-которых-пользователь-не-хотел) (когда другой сайт заставляет браузер отправлять запросы с cookies пользователя); так делать не надо.

</details>

## 6. Ошибки CORS, которые то появляются, то исчезают

API разрешает два origin, `https://app.example` и `https://admin.example`, и возвращает подходящий в `Access-Control-Allow-Origin`. После того как перед API поставили [CDN](/ru/web-platform/cdn/) (кэширующую сеть серверов рядом с пользователями), админка случайным образом получает ошибки CORS. Почему?

<details>
<summary>Ответ</summary>

CDN закэшировал ответ с `Access-Control-Allow-Origin: https://app.example` и отдал ту же копию на запросы с `admin.example`. Браузер видит заголовок для чужого origin и блокирует чтение.

Когда ответ зависит от заголовка `Origin`, отправляйте **`Vary: Origin`** (см. [`Vary`](/ru/architecture/caching/#http-кэширование-общий-язык)): он говорит кэшам хранить отдельную копию для каждого origin. Затем проверьте сам CDN: некоторые CDN по умолчанию игнорируют `Vary`, поэтому добавьте `Origin` в ключ кэша CDN или не кэшируйте там такие ответы. Проверьте, вызывая API поочерёдно с обоих origin. Компромисс — чуть более низкий hit rate (доля ответов из кэша): по одной копии на каждый разрешённый origin.

</details>
