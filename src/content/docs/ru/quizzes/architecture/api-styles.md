## 1. API для партнёров

Ваша компания открывает данные о заказах партнёрам. Они пишут код на Java, Python, PHP и Go, и с большинством из них вы никогда не встретитесь. Какой стиль API вы выберете?

<details>
<summary>Ответ</summary>

**REST** (ресурсы как URL со стандартными методами HTTP) **с описанием OpenAPI** (машиночитаемым описанием эндпоинтов) — общий знаменатель для неизвестных клиентов: любой язык и инструмент понимает HTTP, статус-коды и JSON, ответы на `GET` работают с HTTP-кэшами, а OpenAPI даёт документацию и сгенерированных клиентов.

GraphQL (один эндпоинт, где клиент просит ровно те поля, которые ему нужны) тоже может подойти партнёрам (GitHub и Shopify его предлагают), но тогда каждому партнёру нужно его изучить, а вам — защищать сервер от дорогих запросов. RPC-стили (вызов серверных функций по имени) подходят хуже: tRPC привязан к TypeScript, а gRPC в браузерах требует дополнительных слоёв. Для публичного API стабильность и документация важнее гибкости, поэтому продумайте версионирование с первого дня.

</details>

## 2. Переименование, которое сломало старые приложения

Бэкенд переименовал поле `price` в `amount` в ответе REST и обновил веб-приложение в том же релизе. На следующий день у пользователей старых версий мобильного приложения пустые цены. Что пошло не так и как нужно было сделать?

<details>
<summary>Ответ</summary>

Переименование поля — это **breaking change** (несовместимое изменение), а команда не контролирует, когда мобильные пользователи обновят приложение. Веб-приложение обновилось вместе с бэкендом; старые мобильные версии — нет.

Используйте **expand and contract** (расширить, затем сузить): добавьте `amount` рядом с `price`, выпустите клиентов, которые читают `amount`, следите, сколько запросов всё ещё идёт от старых версий приложения, и удаляйте `price`, только когда на него не опирается ни одна поддерживаемая версия: после того как старые версии ушли, или после объявленного конца поддержки, или после принудительного обновления. Малое использование — довод для этого решения, а не совместимость; удаление поля раньше всё равно сломает оставшихся пользователей, и бизнес должен принять это осознанно. Проверка контракта в [CI](/ru/delivery/ci-cd/) (автоматических проверках на каждое изменение), которая сравнивает новую схему со старой, поймала бы это до релиза. Цена: оба поля живут в API недели или месяцы.

</details>

## 3. Один запрос уронил сервер

Публичный GraphQL API падает. Логи показывают клиента, который отправляет запрос с вложенностью `friends { friends { friends { … } } }` на десять уровней. Какой защиты не хватало?

<details>
<summary>Ответ</summary>

GraphQL позволяет клиенту выбирать форму ответа, поэтому сервер должен **ограничивать то, что принимает**:

- **Ограничения глубины и стоимости**: отклонять запросы, которые слишком глубокие или затронут слишком много объектов.
- **Persisted queries** (заранее сохранённые запросы): для своих приложений разрешать только запросы, зарегистрированные заранее и отправляемые по ID. Неизвестные запросы отклоняются.
- **Rate limits** для каждого клиента на основе стоимости запроса, а не только числа запросов.
- **Батчинг** (DataLoader) против проблемы N+1 (один запрос за списком, а затем ещё по запросу на каждый его элемент): один запрос к базе данных на уровень, а не на каждый элемент.

Компромисс: ограничения могут блокировать законные сложные запросы, поэтому настраивайте их на реальном трафике. Разрешать только persisted queries — самый сильный вариант, но он работает только для клиентов, которые вы контролируете.

</details>

## 4. «Это вызывает только наш UI»

В приложении на Next.js есть server action `deleteProject(projectId)` (серверная функция, которую UI вызывает как обычную функцию, см. [Server Functions](/ru/tools/react/server-components/#server-functions-обратное-направление)). Она вызывается только кнопкой, которую видят владельцы проекта, поэтому action не проверяет права. Это допустимо?

<details>
<summary>Ответ</summary>

Нет. Server action — это **RPC в маскировке**: фреймворк создаёт для неё публичный `POST`-эндпоинт. Любой, кто найдёт эндпоинт, может вызвать его с любым `projectId`, есть кнопка или нет.

Относитесь к ней как к любому эндпоинту API: проверяйте входные данные, проверяйте, что вызывающий вошёл в систему и может удалить *этот* проект ([авторизация](/ru/security/auth/#авторизация-проверка-того-что-разрешено)), и возвращайте понятную доменную ошибку, если нет. Скрытая кнопка — это UX; проверка внутри action — это безопасность.

</details>

## 5. Двенадцать вызовов на один экран

Мобильному экрану товара нужны данные из 12 REST-эндпоинтов, некоторые из них по цепочке (товар, затем его продавец, затем рейтинги продавца…). В медленной сети экран грузится 4 секунды. Какие есть варианты?

<details>
<summary>Ответ</summary>

API **слишком «разговорчивый»** (chatty): каждый вызов — это round trip (путь запроса до сервера и обратно), а вызовы в цепочке складываются. Варианты:

- **[BFF](/ru/architecture/application-boundaries/#где-здесь-фронтенд-bff-gateway-микрофронтенды)** (тонкий серверный слой для этого приложения), который вызывает 12 эндпоинтов рядом с ними, параллельно, где возможно, и возвращает ровно то, что нужно экрану, одним ответом. Им владеет ваша команда, и он может развиваться вместе с приложением.
- **GraphQL**: один запрос просит товар, продавца и рейтинги вместе. Хорошо, когда многим клиентам нужны данные разной формы, но это большее изменение со своими издержками (ограничения запросов, батчинг против N+1).
- Добавить в REST API несколько **агрегирующих эндпоинтов**. Самое быстрое исправление, но API постепенно наполняется эндпоинтами под конкретные экраны.

</details>
