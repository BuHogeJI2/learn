Обдумайте каждый сценарий, прежде чем открыть ответ. Единственно верный вариант бывает редко. Хороший ответ называет компромисс.

## 1. Три репозитория, одна команда

Одна команда из восьми человек делает веб-приложение, админку и API на TypeScript, каждое в своём репозитории. Общие типы и UI-кит публикуются как приватные пакеты. Почти каждая функция меняет API, типы и одно из приложений, и каждое изменение — это три pull request и два релиза пакетов. Что бы вы предложили?

<details>
<summary>Ответ</summary>

Оптимизируйте под самый частый вид изменений. Здесь изменения постоянно **затрагивают несколько проектов**, поэтому подходит **монорепозиторий** (monorepo — один репозиторий для многих проектов): workspaces (несколько пакетов в одном репозитории, которые пакетный менеджер связывает между собой локально) связывают общие пакеты из исходного кода, а изменение и все его последствия помещаются в один коммит и одно ревью и проверяются вместе.

С самого начала добавьте инструменты: систему сборки (Turborepo, Nx), которая запускает в [CI](/ru/delivery/ci-cd/) (автоматических проверках на каждое изменение) только задачи **затронутых** проектов (изменённых и всех, что от них зависят), с кэшированием, и правила [границ модулей](/ru/architecture/application-boundaries/#модульный-монолит), чтобы пакеты не импортировали друг друга как попало. Деплои оставьте раздельными: переход в один репозиторий не означает, что приложения нужно деплоить вместе.

</details>

## 2. Час CI на каждый pull request

После перехода на монорепозиторий каждый pull request запускает все сборки и все тесты всех приложений. CI идёт час, даже ради опечатки в админке. Чего не хватает?

<details>
<summary>Ответ</summary>

В монорепозитории нет **системы сборки**, которая знает граф зависимостей. С ней (Turborepo, Nx) CI сравнивает изменение с базовым коммитом и запускает задачи только для **затронутых** проектов (изменённые пакеты плюс всё, что от них зависит), а также задачи, которые им нужны сначала (например, сборку неизменённой библиотеки, которую импортирует приложение, или восстановление её результата из кэша), параллельно и в правильном порядке.

Добавьте **удалённый кэш** (remote cache): инструмент вычисляет отпечаток входных данных каждой задачи и сохраняет её результаты, поэтому чистая CI-машина восстанавливает результаты, которые уже получил коллега или предыдущий запуск. Компромисс: и то и другое зависит от правильной настройки. Пропущенная зависимость в графе или неверный базовый коммит молча пропускают проверки.

</details>

## 3. Зелёный CI, сломанный продакшен

CI прошёл и восстановил сборку веб-приложения из удалённого кэша. Но задеплоенное приложение обращается к staging API: переменную `NEXT_PUBLIC_API_URL` вчера поменяли для продакшена. Что произошло?

<details>
<summary>Ответ</summary>

Переменная окружения — входные данные сборки (она встраивается в клиентский бандл), но её **не было в отпечатке кэша**. Инструмент увидел тот же исходный код и ту же конфигурацию, нашёл подходящую запись и восстановил старую сборку со старым значением.

Объявляйте все входные данные, которые меняют результат: переменные окружения, файлы конфигурации, версии инструментов. В большинстве систем сборки есть настройка для переменных окружения, от которых зависит задача. Общий урок: кэш корректен, только если его ключ покрывает всё, что важно, — то же правило, что и для любого [кэша](/ru/architecture/caching/).

</details>

## 4. «Один коммит, значит, атомарно»

В монорепозитории разработчик переименовывает поле в API и обновляет веб-приложение в том же коммите. После слияния веб-приложение деплоится на две минуты раньше API, и эти две минуты приложение сломано. «Но это же был один коммит!» Что он упустил?

<details>
<summary>Ответ</summary>

Один коммит **атомарен в Git, но не на продакшене**. Приложения из этого коммита всё равно собираются и деплоятся отдельно, в разное время, и какое-то время старые и новые версии работают одновременно (а пользователи ещё и держат старые версии приложения открытыми во вкладках).

Изменения между частями, которые деплоятся отдельно, должны оставаться **обратно совместимыми**: добавьте новое поле, задеплойте API, переключите приложение на него, а старое поле удалите позже (expand and contract, см. [развитие API](/ru/architecture/api-styles/#развитие-долгосрочная-цена)). Монорепозиторий делает изменение проще для ревью, но не делает безопасным деплой в любом порядке.

</details>

## 5. Четыре версии UI-кита

Компания держит общий UI-кит в отдельном репозитории и публикует его как пакет. Он меняется почти каждую неделю. Его используют пять приложений, на четырёх разных версиях, а в одном приложении появились странные ошибки React после того, как одна из зависимостей притянула вторую копию React. Какие есть варианты?

<details>
<summary>Ответ</summary>

Библиотека, которая меняется каждую неделю, делает **polyrepo** (по репозиторию на проект с общим кодом через опубликованные версии пакетов) дорогим: у каждого потребителя работа по обновлению, версии расходятся, появляются дублирующиеся зависимости (две копии React ломают хуки и контекст).

Варианты:

- Оставить отдельные репозитории, но автоматизировать: pull request с обновлениями от **Renovate или Dependabot**, React как **peer dependency** UI-кита (React даёт приложение), не включённый в опубликованный бандл кита, и проверка, что приложение и кит используют одну и ту же копию; понятное семантическое версионирование (номера версий, где новая мажорная версия означает несовместимые изменения) и changelog.
- Перенести UI-кит и приложения, которые меняются вместе с ним, в **монорепозиторий**, чтобы все они собирались с последней версией, а несовместимое изменение исправлялось в том же коммите.

Выбор зависит от того, насколько приложения действительно независимы. Если ими владеют разные команды со своими графиками релизов, первый вариант сохраняет их независимость; если их меняет вместе одна организация, второй убирает работу по обновлению.

</details>
