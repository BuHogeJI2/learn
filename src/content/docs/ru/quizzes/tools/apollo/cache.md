Обдумайте каждый сценарий, прежде чем открыть ответ. Единственно верный вариант бывает редко. Хороший ответ называет компромисс.

## 1. Новая задача не появляется

Мутация `createTask` (операция GraphQL, которая меняет данные на сервере) проходит успешно и возвращает новую задачу с её `id`, но список задач на экране не показывает её до перезагрузки. Коллега говорит, что кэш Apollo сломан. Так ли это?

<details>
<summary>Ответ</summary>

Нет. Кэш **слил новый объект задачи** (он хранится под своим cache ID — тип плюс `id`, например `Task:91`; см. [как хранятся данные](/ru/tools/apollo/cache/#как-хранятся-данные)), но не может знать, какие **списки** должны его содержать, на какой позиции и подходит ли он под фильтр. Членство в списке — ваше решение.

Варианты:

- **функция `update`** у мутации, которая добавляет задачу в закэшированный список (`cache.modify` или `cache.updateQuery`): без лишнего запроса, но вы должны правильно поддерживать логику для каждого списка, фильтра и порядка сортировки;
- **`refetchQueries`** для затронутого запроса списка: просто и правильно, ценой ещё одного запроса и короткой задержки.

С удалением то же самое: уберите объект через `cache.evict` и почистите через `cache.gc`.

</details>

## 2. Переименовали, но не везде

Мутация `renameProject` возвращает `{ success: true }`. После неё ни страница проекта, ни боковая панель не показывают новое имя. Версия другой команды возвращает проект, но в их приложении боковая панель всё ещё держит старое имя, а страница проекта обновляется. Что происходит в каждом случае?

<details>
<summary>Ответ</summary>

- **Первый случай**: в ответе нет проекта, поэтому сливать нечего. Возвращайте изменённый объект с полем идентичности (`id`) и изменёнными полями, и каждый запрос, который читает `Project:12` из кэша, обновится сам.
- **Второй случай**: запрос боковой панели, скорее всего, не запрашивает `id` проекта (или тип определяется другим полем без `keyFields`). Без идентичности эта копия хранится **внутри своего родителя**, а не нормализуется, поэтому это отдельная копия, которую результат мутации не трогает. Запрашивайте поля идентичности в каждом запросе и настраивайте `keyFields` для типов с собственными ID.

</details>

## 3. Два фильтра, один перемешанный список

Список товаров использует пагинацию по смещению (страницы запрашиваются по позиции: элементы 0–19, 20–39…) с `offsetLimitPagination()` и аргументом `category`. После переключения с «Лампы» на «Стулья» список показывает лампы и стулья вперемешку. Почему?

<details>
<summary>Ответ</summary>

`offsetLimitPagination()` не использует **ключевых аргументов**, если их не передать, поэтому каждый вызов этого поля, какой бы ни была категория, хранится как **один список**, а его функция `merge` присоединяет к нему страницы.

Объявите, какие аргументы делают список *другим*: `offsetLimitPagination(['category'])`, что задаёт `keyArgs`. Смещение и лимит страницы — не ключевые аргументы (они выбирают страницу того же списка), а фильтры, категории и порядок сортировки — ключевые. То же касается помощников для курсорной пагинации и собственных функций `merge`.

</details>

## 4. Данные предыдущего пользователя

На общем офисном компьютере один сотрудник выходит из системы, а другой входит без перезагрузки страницы. Несколько секунд второй сотрудник видит уведомления и имя первого. Почему и как это предотвратить?

<details>
<summary>Ответ</summary>

Кэш принадлежит **экземпляру клиента, а не пользователю**. С `cache-first` (fetch policy по умолчанию: отвечать из кэша, когда можно) запросы отвечают из того, что закэшировано, поэтому следующему пользователю отдаются данные предыдущего, пока что-нибудь их не заменит.

При выходе, входе или смене аккаунта **очищайте кэш**: `clearStore` (очищает) или `resetStore` (очищает и перезапрашивает активные запросы), и следите, чтобы UI не рендерил закэшированные данные, пока это не закончится. Ещё лучше — полная перезагрузка страницы при выходе. В multi-tenant приложениях (одно приложение на много организаций-клиентов, tenant), где ID могут повторяться между tenant, включайте tenant в идентичность кэша.

</details>

## 5. Чужая корзина в HTML с сервера

В приложении на Next.js `ApolloClient` создаётся один раз на уровне модуля и используется ещё и для [рендеринга на сервере](/ru/architecture/rendering/). Под нагрузкой некоторые пользователи видят в первом HTML корзину другого пользователя. Что не так?

<details>
<summary>Ответ</summary>

На сервере клиент уровня модуля **общий для всех запросов** этого процесса, поэтому его кэш наполняется данными многих пользователей и отвечает на запрос одного пользователя закэшированным результатом другого. Это ошибка [scope](/ru/architecture/caching/#ментальная-модель-четыре-вопроса-к-любому-кэшу) (кто видит данные): персональные данные в общем кэше.

Создавайте на сервере **новый клиент и кэш на каждый запрос** и передавайте кэш в браузер для [гидратации](/ru/architecture/rendering/#гидратация-цена-html-который-выглядит-готовым). Пакеты интеграции Apollo для Next.js и React Router делают это за вас. В браузере один клиент на вкладку — нормально, если очищать его при выходе (вопрос 4).

</details>

## 6. Старые данные после чужого изменения

Страница проекта использует fetch policy по умолчанию. Алиса открывает проект, уходит на другую страницу и возвращается через десять минут. За это время Боб переименовал проект со своего компьютера. Алиса видит старое имя, а во вкладке Network нет ни одного запроса. Почему и какие есть варианты?

<details>
<summary>Ответ</summary>

**Fetch policy** по умолчанию (правило выбора между кэшем и сетью) — `cache-first`: если всё, что нужно запросу, уже есть в кэше, Apollo отвечает из кэша и не спрашивает сервер. Нормализованный кэш поддерживает правильность собственных мутаций Алисы, но у него **нет правила свежести** для изменений, сделанных в другом месте.

Варианты, для каждого запроса:

- **`cache-and-network`**: сразу показать закэшированный результат и одновременно спросить сервер, затем обновить. Быстро и вскоре свежо, ценой запроса при каждом визите.
- **`network-only`**: всегда сначала спрашивать сервер. Всегда свежо, но каждый визит ждёт сети.
- **Явные обновления**: `pollInterval` для часто меняющихся данных, `refetch` при фокусе окна или по событию из [канала реального времени](/ru/architecture/real-time/).

Выбирайте по тому, насколько дорого обходятся устаревшие данные на этом экране, и оставляйте `cache-first` там, где это не важно.

</details>
