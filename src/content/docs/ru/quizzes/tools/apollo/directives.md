Обдумайте каждый сценарий, прежде чем открыть ответ. Единственно верный вариант бывает редко. Хороший ответ называет компромисс.

## 1. Добавили `@defer` — и запрос сломался

Чтобы ускорить страницу товара, разработчик добавляет в [GraphQL](/ru/architecture/api-styles/)-запрос `... @defer { recommendations { … } }` (фрагмент — переиспользуемый набор полей, — отмеченный для доставки позже). В приложении на Apollo Client 4 запрос теперь падает вместо того, чтобы грузиться быстрее. Что нужно, чтобы `@defer` работал?

<details>
<summary>Ответ</summary>

`@defer` (отправить отмеченный фрагмент позже, в том же ответе) обрабатывают **обе стороны**, поэтому обе должны быть готовы:

- **Клиенту** нужен настроенный **обработчик частичной доставки** (incremental handler), и он должен соответствовать точной версии формата доставки на сервере, который пока не стандартизирован (например, `Defer20220824Handler` для формата Apollo Router — GraphQL-шлюза от Apollo). Без него Apollo Client 4 отклоняет такие запросы.
- **Сервер** должен поддерживать частичную доставку. Apollo Router поддерживает; для других серверов проверьте. Даже при поддержке некоторые поля нельзя отложить в плане запроса роутера, и они вычисляются до отправки первой части.

Это не переключатель, который заставляет любой запрос стримиться; это договорённость между конкретной настройкой клиента и конкретным сервером.

</details>

## 2. `@defer` работает, но страница не стала быстрее

Теперь `@defer` настроен с обеих сторон, и при локальной разработке вкладка Network показывает, что часть с товаром приходит первой, а часть с рекомендациями — позже. На продакшене пользователи всё равно ждут всё целиком. Компонент показывает спиннер, пока `loading` равно `true`. Что может быть не так?

<details>
<summary>Ответ</summary>

Две частые причины:

- **Компонент ждёт последнюю часть.** Пока приходят части, `loading` остаётся `true` (а `dataState` равно `"streaming"`) до последней из них. Если прятать всё, пока `loading` не станет false, выигрыш пропадает. Рендерьте то, что уже пришло, и показывайте плейсхолдер только для отложенных полей, которые сначала могут быть `undefined`.
- **Что-то посередине буферизует ответ.** Прокси или [CDN](/ru/web-platform/cdn/) (серверы между пользователями и приложением) на продакшене, который ждёт весь ответ, прежде чем передать его дальше, снова превращает части в один медленный ответ. При локальной разработке такого слоя нет. Настройте его так, чтобы он пропускал стримящиеся ответы.

</details>

## 3. Прячем зарплаты через `@skip`

Чтобы не показывать зарплаты сотрудников не-администраторам, запрос использует `salary @skip(if: $isNotAdmin)`, а `$isNotAdmin` фронтенд выставляет по роли пользователя. Это безопасный способ защитить данные?

<details>
<summary>Ответ</summary>

Нет. `@skip` и `@include` выбирают поля по **переменным, которые отправляет клиент**. Любой может изменить переменную (или отправить свой запрос) и получить поле. Это способ переиспользовать один запрос для нескольких вариантов UI, **а не контроль доступа**.

Защищайте поле **на сервере**: резолвер (серверный код, который выдаёт значение поля) проверяет роль вызывающего и отказывает или возвращает `null` не-администраторам ([авторизация](/ru/security/auth/#авторизация-проверка-того-что-разрешено)). `@skip` в UI можно оставить, если он помогает не запрашивать то, что не будет показано, но считайте его удобством.

</details>

## 4. `@nonreactive` — и список перестал обновляться

Список из 2000 элементов полностью перерисовывался при изменении одного элемента, поэтому разработчик добавил `@nonreactive` к фрагменту элемента в запросе списка. Теперь изменения элемента вообще не появляются в списке. Чего не хватало?

<details>
<summary>Ответ</summary>

`@nonreactive` говорит родительскому запросу **игнорировать** изменения внутри этого фрагмента. Это только половина паттерна: каждый **компонент элемента** должен читать свои данные из кэша через **`useFragment`** (по cache ID элемента — типу плюс `id`; см. [кэш Apollo](/ru/tools/apollo/cache/#как-хранятся-данные)), чтобы при изменении его данных перерисовывался этот элемент, и только он.

Без второй части за элементами больше никто не следит, поэтому список показывает устаревшие данные. С обеими частями список перерисовывается, только когда элементы добавляются, удаляются или меняют порядок, а каждое изменение перерисовывает одну строку.

</details>
