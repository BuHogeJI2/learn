Обдумайте каждый сценарий, прежде чем открыть ответ. Единственно верный вариант бывает редко. Хороший ответ называет компромисс.

## 1. Переключатель темы удвоил бандл

Чтобы добавить переключатель тёмной темы, разработчик поставил `'use client'` в начало корневого `layout.tsx`, который импортирует шапку, навигацию и секции страницы. JavaScript, который уходит в браузер, вырос вдвое. Почему и как нужно было сделать?

<details>
<summary>Ответ</summary>

`'use client'` помечает **этот модуль и всё, что он импортирует**, как клиентский код: он работает по графу импортов, а не по дереву рендеринга. Layout импортирует большую часть приложения, поэтому большая часть приложения стала Client Components (кодом, который уходит в браузер и гидратируется, то есть привязывает интерактивность к HTML с сервера, см. [гидратацию](/ru/architecture/rendering/#гидратация-цена-html-который-выглядит-готовым)) вместо Server Components (кода, который выполняется только на сервере и не отправляет JavaScript).

Опустите границу ниже: вынесите переключатель в маленький `ThemeToggle.tsx` с `'use client'`, а layout оставьте Server Component, который его рендерит. Если клиентская обёртка должна окружать серверный контент (например, провайдер темы), передавайте этот контент как `children`: Server Components, переданные так, по-прежнему рендерятся на сервере.

</details>

## 2. Хэш пароля в исходном коде страницы

Server Component загружает текущего пользователя из базы данных и передаёт всю запись в Client Component `<ProfileMenu user={user} />`, который показывает только имя и аватар. Проверка безопасности находит email, роль и хэш пароля пользователя в RSC payload страницы (сериализованном UI, который сервер отправляет в браузер). Как так вышло?

<details>
<summary>Ответ</summary>

**Всё, что передано в Client Component, отправляется в браузер.** Пропсы, пересекающие границу, сериализуются в payload, рендерит их компонент или нет. То, что поле не показано, не делает его секретным.

Передавайте только поля, которые нужны компоненту (`name`, `avatarUrl`), собранные небольшой серверной функцией, которая строит безопасный объект. Модули, которые никогда не должны попасть на клиент, защищайте пакетом `server-only`, чтобы их импорт из клиентского кода ломал сборку.

</details>

## 3. Сохранено, а список старый

Server Function (функция с `'use server'`, которую клиент вызывает как обычную функцию) переименовывает проект в базе данных. Вызов проходит успешно, но список проектов на той же странице, отрендеренный Server Component, показывает старое имя, пока пользователь не перезагрузит страницу. Почему?

<details>
<summary>Ответ</summary>

Server Components определяют, **где выполняется код**, а не **когда обновляется его результат**. Список был отрендерен до мутации и, возможно, [закэширован](/ru/architecture/caching/). Ничто автоматически не перерендеривает его и не помечает его данные устаревшими после того, как Server Function вернула результат.

После мутации ваш код должен сообщить фреймворку, что изменилось. В Next.js вызовите `updateTag` внутри Server Action для тегов (меток, которые объединяют записи кэша) данных проекта: записи сразу истекают, а фреймворк возвращает обновлённый UI в том же ответе, поэтому пользователь видит своё изменение. `revalidateTag(tag, 'max')` здесь был бы неправильным выбором: это stale-while-revalidate, поэтому обновлённая страница ещё могла бы прочитать старую запись ([кэширование в Next.js](/ru/tools/nextjs/caching/)). В других фреймворках свои API, но идея та же: устаревание кэшированных данных и обновление UI не происходят сами. А поскольку Server Function — публичный эндпоинт, она ещё и должна проверять, что вызывающий может переименовать этот проект ([авторизация](/ru/security/auth/#авторизация-проверка-того-что-разрешено)).

</details>

## 4. «window is not defined» в клиентском компоненте

Client Component (помеченный `'use client'`) во время рендера читает `window.innerWidth`, чтобы выбрать раскладку. Страница падает на сервере с `window is not defined`. «Но это же клиентский компонент!» Почему он выполняется на сервере?

<details>
<summary>Ответ</summary>

`'use client'` не значит «только в браузере». Client Components обычно сначала **рендерятся в HTML на сервере** (SSR, рендеринг на сервере), чтобы первая загрузка была готовым HTML, а затем гидратируются в браузере. Во время этого серверного рендера `window` нет.

Читайте браузерные API **в эффектах** (они выполняются только в браузере), а сначала рендерьте безопасное значение по умолчанию; или используйте CSS (media queries) вместо измерений в JavaScript. Следите, чтобы первый рендер в браузере совпадал с HTML с сервера, иначе гидратация сообщит о несовпадении.

</details>

## 5. Медленная страница из await

Страница заказов собрана из вложенных Server Components: страница ждёт пользователя (200 мс), затем рендерит `<Orders>`, который ждёт заказы пользователя (300 мс), затем рендерит `<Recommendations>`, который ждёт сервис рекомендаций (400 мс). Почти секунда проходит, прежде чем что-либо отправлено. Что можно сделать?

<details>
<summary>Ответ</summary>

Это **серверный waterfall**: каждый компонент начинает загрузку только после того, как закончил родитель, поэтому время складывается.

- Запускайте **независимые загрузки параллельно**: если заказам и рекомендациям нужен только ID пользователя, запустите обе сразу (или запустите их на уровне страницы и передайте Promise вниз).
- Поместите медленные необязательные части внутрь **границ [Suspense](/ru/tools/react/suspense/)** и читайте Promise через `use` там, чтобы оболочка страницы и заказы пришли [стримингом](/ru/architecture/rendering/#стриминг) первыми, а рекомендации — позже.
- Кэшируйте то, что можно кэшировать между запросами, и используйте `cache()` из React, который убирает повторные вызовы только в пределах одного запроса, чтобы несколько компонентов, которым в одном запросе нужны одни и те же данные, делили один запрос.

</details>
