Обдумайте каждый сценарий, прежде чем открыть ответ. Единственно верный вариант бывает редко. Хороший ответ называет компромисс.

## 1. Fallback (заглушка загрузки) никогда не показывается

Разработчик оборачивает `UserCard` в `<Suspense fallback={<Spinner />}>`. `UserCard` загружает данные в `useEffect` и хранит их в состоянии. Пока данные грузятся, карточка рендерится пустой, а спиннер так и не появляется. Почему?

<details>
<summary>Ответ</summary>

`<Suspense>` (граница, которая показывает fallback, пока что-то внутри не готово) замечает только то, чего React умеет ждать: код, загруженный через `lazy`, Promise, прочитанный через `use`, данные из библиотеки или фреймворка с поддержкой Suspense и HTML, который ещё стримится с сервера. Загрузка в `useEffect` — ничто из этого: компонент уже отрендерился, пустым, ещё до запуска эффекта.

Либо оставьте компоненту собственное состояние загрузки, либо перейдите на источник данных для Suspense: `useSuspenseQuery` в TanStack Query или [Apollo Client](/ru/tools/apollo/cache/), данные, переданные как Promise из [Server Component](/ru/tools/react/server-components/) (компонента, который выполняется на сервере) или загрузчика роутера и прочитанные через `use`. Второй вариант ещё и позволяет начать загрузку раньше, вне компонента.

</details>

## 2. Цикл перезапросов с `use`

Чтобы попробовать Suspense, разработчик пишет внутри компонента `const user = use(fetch('/api/me').then(r => r.json()))`. Страница постоянно мигает, а вкладка Network показывает бесконечные запросы к `/api/me`. Что не так?

<details>
<summary>Ответ</summary>

Каждый рендер создаёт **новый Promise**. React приостанавливается на нём; когда он выполняется, React рендерит снова, рендер создаёт ещё один новый Promise и запускает ещё один запрос, и React снова приостанавливается.

Promise должен сохранять **ту же идентичность** для тех же данных между рендерами: создавайте его до рендера (в загрузчике роутера или в Server Component, передавая вниз как проп) или берите из кэша библиотеки, который возвращает тот же Promise для того же ключа.

</details>

## 3. Один спиннер на всю страницу

У дашборда есть шапка, боковая панель, основной график и медленная панель «последние действия». В версии A одна граница вокруг всей страницы: пользователи две секунды смотрят на спиннер во весь экран. В версии B каждый из двенадцати виджетов обёрнут в свою границу: контент выскакивает по кусочку, а макет прыгает. Где бы вы поставили границы?

<details>
<summary>Ответ</summary>

Место границы — это **то, что пользователь видит во время ожидания**. Спроектируйте последовательность загрузки вместо обеих крайностей:

- шапка и боковая панель рендерятся сразу (граница не нужна, если их данные быстрые или статические);
- одна граница вокруг **основного контента**, чтобы график и виджеты, которые грузятся вместе, появлялись вместе;
- отдельная граница для **медленной панели**, чтобы она не задерживала остальное.

Делайте каждый fallback того же размера, что и контент, который он заменяет, чтобы ничего не прыгало ([CLS](/ru/observability/web-vitals/#cls-насколько-стабилен-макет), оценка неожиданных сдвигов макета). React к тому же ограничивает частоту показа контента, поэтому границы, которые стали готовы почти одновременно, часто появляются вместе.

</details>

## 4. Результаты пропадают при каждой смене фильтра

На странице поиска результаты читаются через Suspense. Каждый раз, когда пользователь меняет фильтр, видимые результаты заменяются спиннером fallback, пока не придут новые, и это ощущается как шаг назад. Как сохранить старые результаты на экране?

<details>
<summary>Ответ</summary>

Контент, который **уже виден** и снова приостанавливается, заменяется fallback, если обновление не помечено как несрочное:

- оберните смену фильтра в **`startTransition`** (или используйте `useTransition`): React продолжает показывать старые результаты, пока грузятся новые, а флаг `isPending` из `useTransition` позволяет показать небольшой индикатор, например приглушённые результаты;
- или используйте **`useDeferredValue`** для запроса, от которого зависят результаты, чтобы список отставал, а элемент фильтра обновлялся сразу.

Само поле ввода оставьте срочным; ждать должен только дорогой UI, который от него зависит. Роутеры, созданные для Suspense, уже оборачивают переходы в transition.

</details>

## 5. Один сломанный виджет — сломанная страница

Виджет «погода» на главной иногда не может загрузить данные, и тогда вся страница показывает экран ошибки. Виджет находится внутри своей границы `<Suspense>`. Почему это не помогает?

<details>
<summary>Ответ</summary>

Suspense обрабатывает **«ещё не готово»**, а не **«не получилось»**. Неудачная загрузка (например, отклонённый Promise, прочитанный через `use`) выбрасывается как ошибка и поднимается до ближайшего **error boundary** (границы ошибок). Если ближайший находится на уровне страницы, ошибку показывает вся страница.

Поставьте error boundary вокруг виджета со своим небольшим fallback («Погода недоступна») и кнопкой «попробовать снова», которая сбрасывает границу и загружает данные заново. Оборачивайте те части UI, которые должны отказывать независимо; действительно критичные сбои пусть поднимаются до страницы.

</details>
