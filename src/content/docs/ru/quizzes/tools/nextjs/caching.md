Обдумайте каждый сценарий, прежде чем открыть ответ. Единственно верный вариант бывает редко. Хороший ответ называет компромисс. Если не сказано иное, сценарии предполагают Next.js 16 с включёнными Cache Components.

## 1. «Я сохранил, но вижу старое имя»

Страница профиля читает отображаемое имя пользователя через функцию с `'use cache'` и тегом `user:42`. Форма «Сохранить» вызывает Server Action (серверную функцию, которую форма вызывает напрямую), которая обновляет базу данных, затем вызывает `revalidateTag('user:42', 'max')` и перенаправляет обратно на профиль. Сразу после сохранения пользователь видит старое имя; перезагрузка через мгновение показывает новое. Почему и что должна вызывать action?

<details>
<summary>Ответ</summary>

`revalidateTag(tag, 'max')` работает как **[stale-while-revalidate](/ru/architecture/caching/#стратегии-свежести)**: следующий запрос всё ещё получает старую запись, пока в фоне генерируется свежая. Хорошо для поста в блоге или каталога, но неправильно для человека, который только что внёс изменение.

В Server Action вызывайте **`updateTag('user:42')`**: она сразу помечает запись истёкшей, поэтому страница после перенаправления ждёт свежих данных и пользователь видит своё изменение ([read-your-own-writes](/ru/data/consistency/#копии-и-модели-согласованности), «вижу свои изменения»). `revalidateTag` оставьте для изменений, которые приходят извне, например от webhook из [CMS](/ru/data/cms/) в Route Handler (API-эндпоинте внутри директории `app`), где `updateTag` недоступна.

</details>

## 2. `cookies()` внутри кэшируемой функции

Разработчик добавляет `'use cache'` в `getRecommendations()`, которая вызывает `cookies()`, чтобы прочитать регион пользователя. Сборка падает с ошибкой о данных запроса внутри кэшируемой функции. Какие есть варианты?

<details>
<summary>Ответ</summary>

Записи `'use cache'` **общие для всех пользователей**, поэтому они не могут читать данные запроса вроде `cookies()` или `headers()`, в том числе во вспомогательных функциях, которые вызывают.

Варианты:

- **Прочитать cookie снаружи** кэшируемой функции и передать регион как **аргумент**: он станет частью ключа кэша, и все пользователи одного региона будут делить одну запись. Обычно лучший выбор, когда у значения мало вариантов.
- **`'use cache: private'`**: может читать cookies и заголовки напрямую, но её результаты живут только в браузере этого пользователя, а не в общем серверном кэше.
- Без кэширования: читать во время запроса внутри границы [`<Suspense>`](/ru/tools/react/suspense/), чтобы эта часть пришла стримингом после static shell.

</details>

## 3. Кэш, в который никогда не попадаешь

На [serverless](/ru/delivery/deployment-models/#модели-деплоя)-платформе (инстансы запускаются на запрос и вскоре останавливаются) медленный запрос товара, обёрнутый в `'use cache'` с динамическим ID товара, похоже, выполняется почти на каждом запросе. Логи большую часть времени показывают промахи кэша. Почему и что можно сделать?

<details>
<summary>Ответ</summary>

Записи, вычисленные во время запроса, по умолчанию хранятся **в памяти, отдельно для каждого инстанса**. На serverless-платформах инстансы живут недолго и многие работают параллельно, поэтому запись, сделанная одним инстансом, редко оказывается на месте для следующего запроса.

Варианты:

- **`'use cache: remote'`**: общий долговременный обработчик кэша (например, Redis или KV платформы). Записи переживают смену инстансов ценой сетевого запроса на каждую проверку и платы платформе, поэтому это окупается только при высоком hit rate (доле попаданий).
- **Пререндерить** то, что можно: известные ID товаров из `generateStaticParams` становятся частью статического результата, а не слишком короткое время жизни позволяет записям войти в static shell (пререндеренную часть страницы, которая отдаётся мгновенно).
- Сделать сам запрос дешевле (индекс, меньше данных).

Помните, что каждый деплой начинается с холодного кэша: build ID входит в каждый ключ.

</details>

## 4. Публикация из CMS

Страницы товаров показывают данные из headless CMS (которая отдаёт контент только через API) через функции с `'use cache'` и `cacheLife('days')`. Редакторы хотят, чтобы опубликованное изменение появлялось в течение минуты. Как связать CMS с кэшем?

<details>
<summary>Ответ</summary>

Помечайте каждую кэшируемую функцию тегами записей, которые она показывает (`cacheTag('product:42')` плюс теги общих вещей вроде `category:lamps`). Пусть CMS вызывает **webhook публикации** (HTTP-запрос, который CMS отправляет при публикации): Route Handler, который проверяет подпись webhook и вызывает `revalidateTag(tag, { expire: 0 })` для тегов изменённой записи. `updateTag` недоступна вне Server Actions, а рекомендуемый профиль `'max'` ещё раз отдал бы старую страницу, пока она перегенерируется; с `{ expire: 0 }` следующий запрос ждёт свежих данных. Страницы перегенерируются по мере посещения, а долгое время жизни держит всё остальное в кэше.

Минута должна выдерживаться и в браузере, и при сбое webhook:

- **Браузеры** хранят закэшированные результаты в течение `stale` профиля — 5 минут для `days` (минимум 30 секунд), поэтому посетитель, у которого страница уже открыта, может видеть старую версию столько же. Если это важно, используйте собственный профиль с более коротким `stale`.
- **Потерянный webhook** оставляет старые данные, пока профиль `days` их не обновит: до суток. Логируйте и алертите неудачные доставки и раз в минуту запускайте задачу сверки (которая спрашивает у CMS, что недавно опубликовано, и перепроверяет эти теги); или примите, что при сбое минута — цель, а не гарантия ([публикация из CMS](/ru/data/cms/#черновики-превью-и-публикация)). Для превью черновиков используйте **Draft Mode** (режим, который включается cookie для редакторов и рендерит неопубликованный контент), который обходит все записи `'use cache'`.

</details>

## 5. Обновление, которое утроило нагрузку на базу

Старое приложение без Cache Components обновляют с Next.js 14 до 15. В коде ничего не меняли, но нагрузка на базу данных и API выросла примерно втрое, а некоторые страницы стали медленнее. Что изменилось?

<details>
<summary>Ответ</summary>

В Next.js 15 изменились **значения по умолчанию** предыдущей модели кэширования: запросы `fetch` и `GET` Route Handlers **больше не кэшируются по умолчанию**, а клиентский роутер перестал переиспользовать сегменты страниц при обычных переходах по ссылкам (кнопки «назад» и «вперёд» по-прежнему их переиспользуют). Приложение полагалось на то, что Next.js 14 кэширует это неявно, поэтому теперь каждый рендер снова вызывает API.

В краткосрочной перспективе: осознанно, для каждого источника данных, верните кэширование нужным запросам (например, `cache: 'force-cache'` у `fetch` или настройки сегментов). В долгосрочной: перейдите на Cache Components, где асинхронные данные кэшируются, только когда вы явно включаете это через `'use cache'`, а явный `cacheLife` делает понятным их время жизни, так что кэширование видно в коде, а не задано значением по умолчанию версии.

</details>
