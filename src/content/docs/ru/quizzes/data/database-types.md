Обдумайте каждый сценарий, прежде чем открыть ответ. Единственно верный вариант бывает редко. Хороший ответ называет компромисс.

## 1. «MongoDB, потому что она масштабируется»

В новом SaaS-продукте есть пользователи, команды, подписки, счета и платежи. Клиентов несколько сотен. Коллега предлагает MongoDB, «потому что она лучше масштабируется». Что вы порекомендуете?

<details>
<summary>Ответ</summary>

Выбирайте по **паттернам доступа и связям**, а не по масштабу, которого у вас нет. Эти данные сильно связаны (пользователи принадлежат командам, счета — подпискам), вы будете запрашивать их способами, которых пока не знаете (отчёты, инструменты поддержки), а платежам нужны [транзакции](/ru/data/consistency/) по принципу «всё или ничего» и ограничения. Это родная территория **реляционной** базы данных.

Управляемый PostgreSQL подходит под такую нагрузку с большим запасом для роста: машина помощнее и реплики для чтения (копии базы, которые обслуживают чтение). MongoDB тоже умеет join (объединение записей из нескольких коллекций в одном запросе) и транзакции между документами, но её естественная модель — самодостаточные документы; для настолько связанных данных вы бы тратили силы на то, чтобы ссылки и копии между документами оставались согласованными. Измеряйте реальную нагрузку по мере роста, а не выбирайте заранее под масштаб.

</details>

## 2. Поиск с опечатками

Поиск товаров использует `WHERE name ILIKE '%lamp%'`. На 2 миллионах товаров он медленный, ничего не находит по опечатке «lmap», выдаёт результаты без полезного порядка, а продукт хочет фасеты (счётчики для фильтров по бренду и цене). Какие есть варианты?

<details>
<summary>Ответ</summary>

`LIKE` с подстановочным символом `%` в начале не может использовать обычный [индекс](/ru/data/database-types/#ментальная-модель-структура-данных-на-диске-плюс-гарантии) (упорядоченную структуру, которая ускоряет поиск), поэтому просматривает каждую строку, и он ничего не знает об опечатках, словоформах и релевантности.

Варианты:

- **Встроенный полнотекстовый поиск базы данных** (`tsvector` в PostgreSQL с GIN-индексом, плюс `pg_trgm` для опечаток). Новой системы не нужно; для многих продуктов этого достаточно.
- **Поисковый движок** (Elasticsearch, OpenSearch, Meilisearch, Typesense, Algolia): **инвертированный индекс** (соответствие «слово → документы, где оно есть»), созданный для релевантности, опечаток и фасетов. Его наполняют из основной базы, и он от неё отстаёт, поэтому источником истины остаётся база данных.

Начните со встроенного варианта, если он покрывает требования; добавляйте поисковый движок, когда релевантность и фасеты важны настолько, что стоит платить за ещё одну систему и её синхронизацию.

</details>

## 3. Список заказов стал медленным

Страница «Мои заказы» была быстрой при запуске. Через год она грузится 3 секунды. Запрос: `SELECT * FROM orders WHERE user_id = ? ORDER BY created_at DESC LIMIT 20`. Сервер базы данных не загружен. Какая вероятная причина?

<details>
<summary>Ответ</summary>

**Нет индекса**. Без индекса по `user_id` (а лучше — по `(user_id, created_at)`) база данных читает всю растущую таблицу, чтобы найти заказы одного пользователя, а потом сортирует их. Пока таблица была маленькой, это было быстро.

Проверьте план запроса (`EXPLAIN`). С составным индексом по `(user_id, created_at)` база данных сразу переходит к строкам этого пользователя, уже упорядоченным, и читает только 20. Цена: каждая вставка обновляет и индекс, и он занимает место на диске. Большинство проблем «база данных тормозит» — это именно оно, а не марка базы данных.

</details>

## 4. «Too many connections»

API на [serverless-функциях](/ru/delivery/deployment-models/) работает нормально, но во время всплесков трафика PostgreSQL отклоняет запросы с ошибкой «too many connections». CPU базы данных почти не загружен. Что происходит?

<details>
<summary>Ответ</summary>

Каждый инстанс функции открывает своё соединение с базой данных, а всплеск запускает сотни или тысячи инстансов. SQL-база данных поддерживает ограниченное число соединений, и каждое стоит памяти, даже если почти всё время простаивает.

Исправления: поставить **пул соединений** (connection pooler — прокси, через который много клиентов делят небольшое число соединений с базой) между функциями и базой данных (PgBouncer или встроенный пул управляемых провайдеров, таких как Supabase и Neon), использовать **драйвер поверх HTTP**, который предлагает провайдер, или ограничить параллельность функций. Компромисс пула в режиме транзакций: некоторые возможности сессии (prepared statements — заранее подготовленные запросы, настройки сессии) ведут себя иначе, поэтому проверьте, что ваш ORM (библиотека, которая отображает таблицы на объекты в коде) это поддерживает.

</details>

## 5. Аналитика замедляет оформление заказа

Бизнес-команда запускает отчёты вроде «выручка по странам по месяцам» на основной базе данных. Когда они работают, оформление заказа тормозит. Что вы сделаете?

<details>
<summary>Ответ</summary>

Это **OLAP**-запросы (просматривают миллионы строк), которые выполняются на **OLTP**-базе (много маленьких чтений и записей). Они конкурируют за одни и те же CPU, память и диск.

Варианты, от маленьких к большим:

- Запускать отчёты на **реплике для чтения**, чтобы они не трогали основную базу. Дёшево, но строчное хранение всё равно медленное для больших сканирований, а реплика немного отстаёт.
- Копировать данные в **аналитическое (колоночное) хранилище**, такое как ClickHouse, BigQuery или Snowflake, которое создано для агрегаций по миллиардам строк. Больше движущихся частей и пайплайн синхронизации, но отчёты становятся быстрыми, а база приложения остаётся в покое.

</details>

## 6. Страницы из блоков

Конструктор страниц в духе [CMS](/ru/data/cms/) (инструмент, где редакторы собирают страницы из готовых блоков) хранит страницы из блоков (hero, текст, галерея, форма), у каждого свои поля, и каждый месяц появляются новые типы блоков. Остальное приложение использует PostgreSQL. Нужна ли документная база данных?

<details>
<summary>Ответ</summary>

Скорее всего, нет. Страница — **самодостаточный объект**, который читают и пишут целиком и форма которого меняется, а это сильная сторона документной модели. Но PostgreSQL может хранить её в колонке `JSONB` (JSON в двоичном виде, который можно индексировать и запрашивать) с индексами по полям, по которым вы делаете запросы, рядом с реляционными данными (авторы, права, статус публикации), которым полезны join и транзакции.

Одной базой данных проще управлять и проще держать её согласованной. Отдельное документное хранилище стоит рассматривать, только если большая часть приложения станет документной. В любом случае схема не исчезает: ваш код всё равно должен обрабатывать старые формы блоков, поэтому версионируйте их.

</details>
