Обдумайте каждый сценарий, прежде чем открыть ответ. Единственно верный вариант бывает редко. Хороший ответ называет компромисс.

## 1. Edge сделал медленнее

Команда перенесла обработчик страницы товара с сервера в us-east в edge-функцию (код, который выполняется на серверах CDN рядом с пользователями), «чтобы быть ближе к пользователям». Для пользователей в Токио страница стала медленнее. Обработчик делает три запроса подряд к базе данных в us-east. Что произошло?

<details>
<summary>Ответ</summary>

Функция теперь близко к **пользователю**, но далеко от **данных**. Раньше Токио платил за один долгий round trip (путь запроса туда и обратно) до us-east, а три запроса выполнялись рядом с базой данных. Теперь каждый из трёх запросов пересекает Тихий океан: три долгих round trip вместо одного.

Правило: запускайте код рядом с данными, к которым он обращается чаще всего. Варианты: вернуть обработчик в регион базы данных (CDN всё равно завершает соединения рядом с пользователем, так что быстрым он останется), объединить запросы в один или читать из реплики (копии данных только для чтения) рядом с edge. Оставьте edge-функциям работу, которой не нужны данные с origin (вашего собственного сервера): редиректы, распределение по группам A/B-теста, изменение заголовков, первую проверку подписанного токена.

</details>

## 2. CDN, который почти ничего не отдаёт

Вы поставили CDN перед маркетинговым сайтом. Дашборд показывает hit rate (долю запросов, на которые CDN отвечает из кэша) 5%, а нагрузка на origin не снизилась. Ответы кэшируемые, а логи CDN показывают много разных URL для одних и тех же нескольких страниц: письма и реклама добавляют `?utm_source=...&utm_campaign=...&utm_content=...` с разным значением для каждой кампании и каждого получателя. Что не так?

<details>
<summary>Ответ</summary>

**[Ключ кэша](/ru/architecture/caching/#ментальная-модель-четыре-вопроса-к-любому-кэшу)** (то, по чему CDN решает, «одинаковые» ли два запроса) включает всю строку запроса. При таком количестве уникальных комбинаций большинство визитов приходит с ключом, которым ещё никто не пользовался, поэтому они промахиваются. Cookies или заголовки в ключе (например, `Vary: Cookie`) дают тот же эффект. Если бы разных URL было мало, сначала стоило бы искать другие причины: `Cache-Control: private` или `no-store`, `Set-Cookie` в каждом ответе или правило обхода кэша.

Исправления: убрать параметры отслеживания из ключа кэша (большинство CDN позволяют игнорировать параметры запроса или задать список разрешённых), не включать cookies в ключ для публичных страниц и избегать `Vary` по заголовкам с множеством значений. Проверяйте результат по заголовку статуса кэша (`x-cache`, `cf-cache-status`) и `Age`. Компромисс: если параметр действительно меняет содержимое, его игнорирование отдаст не ту страницу, поэтому составьте список нужных параметров, а не отбрасывайте все вслепую.

</details>

## 3. DDoS прошёл мимо CDN

Ваш сайт стоит за CDN с защитой от DDoS (заваливания сайта трафиком с множества машин), но атака всё равно роняет origin. Логи показывают, что трафик идёт не с адресов CDN. Как это случилось и как это предотвратить?

<details>
<summary>Ответ</summary>

Origin **доступен публично**. Атакующие нашли его адрес (старые DNS-записи, логи сертификатов, поддомен не за CDN) и отправили трафик прямо на него. CDN защищает только тот трафик, который через него проходит.

Сделайте так, чтобы origin принимал трафик **только от CDN**: разрешите только диапазоны IP CDN, требуйте секретный заголовок, который добавляет CDN, или используйте аутентифицированное соединение (mutual TLS или туннель, который предлагает CDN). После этого смените IP origin, если он утёк.

</details>

## 4. «Наш API персональный, CDN бесполезен»

Каждый ответ API персональный, поэтому кэшировать нечего. Коллега говорит, что CDN ничего не даёт. Вы согласны?

<details>
<summary>Ответ</summary>

Не полностью. Даже без всякого кэширования CDN:

- **завершает TCP и TLS рядом с пользователем** и переиспользует тёплые соединения с origin, что убирает несколько долгих round trip из каждого нового соединения;
- бесплатно даёт **HTTP/2, HTTP/3 и современный TLS**;
- добавляет **защиту**: поглощение DDoS, правила WAF (web application firewall — межсетевой экран, который блокирует вредоносные запросы, см. [что делает CDN](/ru/web-platform/cdn/#что-cdn-делает-помимо-кэширования)), [rate limiting](/ru/architecture/reliability/#защита-сервиса-от-перегрузки).

Это менее важно для внутреннего инструмента, которым пользуются из того же региона, где стоит origin. И есть цена: нужно следить, чтобы персональные ответы были помечены `private` или `no-store` и CDN их никогда не сохранял.

</details>

## 5. Персонализация на edge

Продукт хочет, чтобы главная страница приветствовала каждого вошедшего пользователя по имени, а страница кэшируется на CDN. Разработчик предлагает добавить cookie с id пользователя в ключ кэша. Что произойдёт и что бы вы сделали вместо этого?

<details>
<summary>Ответ</summary>

С id пользователя в ключе у каждого пользователя своя запись в кэше. Записи больше не общие: первый визит каждого пользователя — промах, и попадать могут только его собственные повторные визиты в пределах времени жизни кэша, так что большая часть пользы от кэширования этой страницы пропадает. А если ключ когда-нибудь настроят неправильно, страница одного пользователя может попасть к другому.

Лучше: оставить страницу **публичной** и закэшированной, а персональную часть (приветствие, корзину) загружать отдельным некэшируемым запросом или рендерить на клиенте. Используйте персонализацию на edge только для **нескольких** вариантов (страна, группа A/B-теста, вошёл пользователь или нет), потому что каждый вариант делит кэш.

</details>
