Обдумайте каждый сценарий, прежде чем открыть ответ. Единственно верный вариант бывает редко. Хороший ответ называет компромисс.

## 1. Аватары пропадают после деплоя

Пользователи загружают аватары, и приложение сохраняет их в папку `uploads/` на сервере. Неделями всё работает. После переезда на контейнерную платформу (которая запускает приложение как [контейнеры](/ru/delivery/containers/)) с двумя инстансами (запущенными копиями приложения) часть аватаров отображается сломанными, а после каждого деплоя пропадают все. Почему?

<details>
<summary>Ответ</summary>

Файлы лежат на **локальном диске инстанса**. Этот диск не общий для инстансов, поэтому запрос, который обслуживает другой инстанс, файл не находит, и он не переживает замену инстанса, а её делает каждый деплой.

Считайте каждый инстанс **одноразовым**: храните загрузки в **объектном хранилище** (сервисе для файлов, например S3 или R2), в базе данных — только их метаданные, и отдавайте их через [CDN](/ru/web-platform/cdn/). То же правило касается [сессий](/ru/security/auth/#сессии-на-практике-жизненный-цикл), кэшей в памяти, которые должны быть общими, и таймеров: всё, что должно пережить процесс, уходит во внешний сервис ([что переживает перезапуск](/ru/delivery/deployment-models/#состояние-что-переживает-перезапуск)).

</details>

## 2. `ChunkLoadError` после каждого релиза

После каждого релиза [отслеживание ошибок](/ru/observability/error-tracking/) показывает всплеск `ChunkLoadError` и неудачных вызовов API, в основном у пользователей, у которых приложение было открыто до деплоя. Перезагрузка помогает. Что происходит и что можно сделать?

<details>
<summary>Ответ</summary>

**Version skew** (расхождение версий): открытые вкладки всё ещё выполняют старый JavaScript. Когда пользователь переходит по страницам, старый код запрашивает чанки, которые новый деплой удалил, или вызывает изменившийся API.

Варианты, часто вместе:

- **Держать старые статические файлы доступными** какое-то время после деплоя (имена файлов с хэшем содержимого это упрощают).
- Держать API **обратно совместимыми** хотя бы столько, сколько живут старые вкладки.
- **Перезагружать страницу**, когда чанк не загрузился, лучше при следующем переходе, а не посреди работы пользователя.
- Использовать **skew protection**, если платформа её предлагает: запросы старых клиентов направляются в старый деплой.

</details>

## 3. Артефакт со staging ходит в staging API

Команда хочет проверять одну сборку на staging (окружении, похожем на продакшен, для проверок), а затем продвигать **тот же артефакт** (результат сборки) на продакшен. После продвижения страницы продакшена обращаются к staging API. URL API задан как `VITE_API_URL` в настройках каждого окружения. Что пошло не так?

<details>
<summary>Ответ</summary>

Переменные с публичным префиксом (`VITE_`, `NEXT_PUBLIC_`) читаются во время **сборки** и копируются в JavaScript-бандл. Артефакт собран со значениями staging; изменение переменной на продакшене позже ничего не меняет в уже собранных файлах.

Варианты: загружать такие значения **во время выполнения** (небольшой эндпоинт конфигурации или скрипт, который сервер вставляет в страницу), чтобы один артефакт работал в любом окружении; или согласиться на **отдельную сборку для каждого окружения**, понимая, что тогда staging проверяет немного другой артефакт. Помните, что всё в бандле публично: никогда не кладите туда секреты.

</details>

## 4. Откат, который не помог

Релиз миграцией переименовал колонку базы данных `name` в `full_name` и обновил код. Появилась не связанная с этим ошибка, и команда откатилась на предыдущую версию. Откат сделал только хуже: теперь падает каждая страница, которая читает пользователей. Почему?

<details>
<summary>Ответ</summary>

Откат переключает **код, а не данные**. Старый код ожидает колонку `name`, а миграция её уже переименовала. Кроме того, во время rolling-деплоя (инстансы заменяются по несколько за раз, см. [релизы](/ru/delivery/deployment-models/#релизы-от-коммита-до-пользователей)) старый и новый код одновременно работали с одной и той же схемой, так что ошибки, скорее всего, появились ещё до отката.

Меняйте схему **совместимыми шагами** (expand, migrate, contract — расширить, перенести, сузить): добавьте `full_name`, пишите в обе колонки, заполните старые данные, переключите чтение, задеплойте и только позже, когда `name` не нужна ни одной версии, на которую вы можете откатиться, удалите её. Каждый шаг работает и с предыдущей, и со следующей версией кода.

</details>

## 5. Kubernetes для маленькой команды?

Команда из четырёх человек делает приложение на Next.js с неравномерным трафиком: большую часть дня тихо, а во время вечерних акций в десять раз больше. Один разработчик предлагает запускать его в [Kubernetes](/ru/delivery/kubernetes/), «чтобы быть готовыми к масштабу». Что вы порекомендуете?

<details>
<summary>Ответ</summary>

Для маленькой команды с неравномерным трафиком обычно лучше **платформа**: такая, которая превращает приложение в статические файлы и serverless-функции (код, который платформа запускает по требованию: Vercel, Netlify), или serverless-сервис для контейнеров (Cloud Run). Они масштабируются автоматически, почти до нуля в простое, и никому не нужно обслуживать кластер.

Kubernetes окупается, когда организация запускает много сервисов и у неё есть люди для его эксплуатации; для четырёх разработчиков он добавляет много работы без явной выгоды. Вместо этого следите за ограничениями платформы: длительностью функций, cold start (задержкой запуска нового инстанса), соединениями с базой данных от множества инстансов и стоимостью при высоком постоянном трафике. Если это станет проблемой, следующий шаг — долгоживущие контейнеры на управляемом сервисе.

</details>
