## Какую проблему решает

Два разных вопроса, которые всегда задаются отдельно:

- **Аутентификация** (authN): *кто* делает этот запрос?
- **Авторизация** (authZ): может ли *этот* пользователь выполнить *это* действие над *этим* объектом?

HTTP [не хранит состояние](/ru/web-platform/http/#ментальная-модель-сообщение-из-трёх-частей): сервер не помнит, что вы вошли минуту назад. Поэтому вход должен выдать **учётные данные** (доказательство личности), и каждый следующий запрос должен их нести.

Смешение этих двух вопросов порождает самую частую ошибку безопасности в вебе: сервер проверяет, что пользователь вошёл, но не проверяет, что заказ `/orders/43` принадлежит ему.

## Ментальная модель: учётные данные, которые проверяются на каждом запросе

```
1. Login         the user proves who they are       → the server issues a credential
                 (password, passkey, Google…)
2. Each request  the browser sends the credential   → server: who is it?           (authN)
                 (cookie or header)
3. Each action   the server applies the rules for   → allow, or 403                 (authZ)
                 this user and this object
4. End           logout, expiry, revocation          → the credential stops working
```

Учётные данные бывают двух видов:

- **Ссылка (ID сессии)**: длинная случайная строка. Настоящие данные (ID пользователя, срок действия) сервер хранит в **хранилище сессий** и ищет их на каждом запросе. Отозвать легко: удалить запись. Цена — один поиск на запрос, что дёшево с быстрым хранилищем вроде Redis.
- **Самодостаточный токен**, обычно **JWT** (JSON Web Token: JSON с ID пользователя, сроком действия и другими **claims** (утверждениями о пользователе), подписанный выпустившей стороной). Сервер проверяет подпись, и поиск не нужен. Но токен действует до истечения срока, поэтому отозвать его трудно. Обычный ответ — короткий срок жизни плюс **refresh token** (долгоживущие учётные данные, которые используются только для получения новых короткоживущих токенов) или список отозванных токенов, который возвращает поиск.

Как учётные данные передаются — **отдельное решение**: cookie или заголовок `Authorization`. JWT может лежать в cookie; ID сессии можно отправлять в заголовке. «Сессии или JWT» и «cookie или `localStorage`» — два разных вопроса, которые часто путают.

| | В cookie с `HttpOnly` | В заголовке `Authorization` (хранит ваш код) |
| --- | --- | --- |
| **ID сессии** | Классическое веб-приложение: просто, легко отозвать | Мобильные приложения, API-клиенты |
| **JWT** | Работает; следите за размером cookie; защита от CSRF всё равно нужна | Типичное SPA, вызывающее API; сторонние API |

## Как пользователи доказывают, кто они

- **Пароли.** Сервер хранит только медленный хэш с солью (Argon2id, bcrypt), ограничивает число попыток входа и отклоняет известные утёкшие пароли. Задача фронтенда — не мешать менеджерам паролей (правильные атрибуты `autocomplete`, вставка не запрещена).
- **MFA** (multi-factor authentication — многофакторная аутентификация: второе доказательство из того, что у пользователя есть ещё): коды из приложения-аутентификатора, аппаратные ключи, подтверждение push-уведомлением. SMS-коды — самый слабый вариант, потому что номер телефона можно перехватить.
- **Passkeys** (ключи доступа, построены на WebAuthn): устройство или менеджер паролей хранит приватный ключ, а сервер — только публичный. Они устойчивы к фишингу, потому что браузер использует passkey только на том домене, для которого он создан. Индустрия движется в эту сторону.
- **Magic links и одноразовые коды**, отправленные по email.
- **Вход через другой аккаунт** («Войти через Google») и **корпоративный SSO** (single sign-on — единый вход во много приложений): через OpenID Connect или более старый SAML, описанные ниже.

## Сессии на практике: жизненный цикл

У учётных данных есть жизнь, и на каждом этапе свои правила:

- **Создание.** Выдавайте **новый** ID сессии при входе, никогда не переиспользуйте тот, что был до входа. Иначе атакующий, подсунувший заранее известный ID (session fixation — фиксация сессии), тоже окажется залогинен.
- **Передача.** Cookie с `HttpOnly`, `Secure`, `SameSite=Lax` и префиксом `__Host-` (см. [cookies и границы](/ru/security/browser-boundaries/#когда-браузер-отправляет-cookies)).
- **Истечение.** Таймаут бездействия (нет активности N минут) плюс абсолютный предел (войти заново через N дней).
- **Отзыв.** Выход удаляет сессию **на сервере**, а не только cookie. «Выйти на всех устройствах» и смена пароля завершают остальные сессии.
- **Повторная проверка.** Чувствительные действия (смена email, платёж) снова требуют пароль или passkey.

Токены проходят те же этапы: короткоживущие access tokens (токены, которые API принимает в каждом запросе; живут минуты) и refresh tokens, которые **ротируются** при каждом использовании, чтобы украденный и уже использованный refresh token был обнаружен.

## Где браузер хранит учётные данные

| Место | Переживает перезагрузку | Может прочитать внедрённый скрипт | Отправляется автоматически | Заметки |
| --- | --- | --- | --- | --- |
| **Cookie с `HttpOnly`** | Да | Нет (но внедрённый код всё равно может *использовать* её, пока страница открыта) | Да | Нужна [защита от CSRF](/ru/security/web-attacks/#csrf-запросы-которых-пользователь-не-хотел). Сервер видит её в запросе страницы, поэтому [рендеринг на сервере](/ru/architecture/rendering/) знает пользователя. |
| **`localStorage` / `sessionStorage`** | Да / в пределах вкладки | **Да**: XSS или сторонний скрипт может скопировать токен и использовать его откуда угодно до истечения срока | Нет | CSRF нет, но украсть токен легко |
| **Память** (переменная JavaScript) | Нет | Скопировать сложнее, но внедрённый код может использовать её на странице | Нет | Нужен способ получить новый токен после перезагрузки, например через эндпоинт вашего собственного бэкенда, который хранит refresh token или сессию в cookie с `HttpOnly` |
| **На сервере, за BFF** | — | Браузер никогда не видит токены | Только cookie сессии | Самый безопасный вариант для браузерных приложений; см. ниже |

**BFF** (backend for frontend — серверный слой, которым владеет фронтенд; см. [границы приложения](/ru/architecture/application-boundaries/#где-здесь-фронтенд-bff-gateway-микрофронтенды)): браузер общается только с вашим собственным сервером через cookie сессии. Сервер хранит OAuth-токены и вызывает API. RFC 10017, рекомендации IETF для браузерных приложений, настоятельно рекомендует этот паттерн для бизнес-приложений и приложений, которые работают с персональными данными.

Для собственного веб-приложения с собственным бэкендом разумный вариант по умолчанию — **cookie сессии с `HttpOnly` к бэкенду на том же origin** (схема + хост + порт). Токены, которые держит JavaScript, имеют смысл в основном для прямых вызовов сторонних API и для клиентов вне браузера.

## Авторизация: проверка того, что разрешено

- **На сервере, на каждом запросе, для конкретного объекта.** «Может ли этот пользователь редактировать *этот* документ?», а не только «вошёл ли он?».
- **UI только отражает права.** Спрятанная кнопка — это UX, а не безопасность; эндпоинт за ней должен проверять снова.
- **Проверяет каждая точка входа**: REST-эндпоинты, резолверы GraphQL (поле за полем, см. [Стили API](/ru/architecture/api-styles/#как-они-сравниваются)), серверные функции фреймворка, webhooks, фоновые задачи.

У пропущенной проверки объекта есть название: **IDOR** (insecure direct object reference — небезопасная прямая ссылка на объект). Нарушение контроля доступа (broken access control), категория, к которой он относится, — первый пункт OWASP Top 10.

Распространённые модели для записи правил:

| Модель | Правило выглядит так | Подходит для |
| --- | --- | --- |
| **RBAC** (role-based — на основе ролей) | «Редакторы могут публиковать» | Простых продуктов, админок |
| **ABAC** (attribute-based — на основе атрибутов, или политик) | «Пользователи могут редактировать документы своего отдела в рабочее время» | Правил, которые зависят от данных |
| **ReBAC** (relationship-based — на основе связей) | «Может смотреть, если состоит в команде, которой принадлежит папка с этим файлом» | Совместного доступа, как в Google Drive или GitHub |

В multi-tenant приложениях (много компаний-клиентов в одной системе) каждый запрос ещё и должен ограничиваться tenant (компанией-клиентом) пользователя. Один забытый фильтр — и утекают данные другой компании.

Где живут правила: в каждом обработчике, в общем слое политик приложения или в отдельном сервисе авторизации. [API gateway](/ru/architecture/application-boundaries/#где-здесь-фронтенд-bff-gateway-микрофронтенды) (общая точка входа перед сервисами) может для всех проверить «есть ли валидные учётные данные?», но правилам уровня объекта нужны данные, поэтому они остаются рядом с данными.

## OAuth 2 и OpenID Connect

- **OAuth 2.0** позволяет приложению получить **доступ к API от имени пользователя** без его пароля: «разрешить этому приложению читать мои репозитории на GitHub». Результат — **access token**. OAuth — это про делегированный доступ, а не про вход.
- **OpenID Connect** (OIDC) добавляет поверх OAuth **личность**: **ID token** (JWT, который говорит, кто пользователь). Именно его используют «Войти через Google» и большинство корпоративных SSO.

Участники: **пользователь**, **клиент** (ваше приложение), **authorization server** (сервер авторизации) или **identity provider** (провайдер идентификации: Google, Okta, Auth0, Keycloak) и **resource server** (сервер ресурсов, то есть API).

Рекомендуемый поток — **Authorization Code с PKCE**:

```
App ── redirect ──────────────────► Identity provider: login + consent
App ◄── redirect back with ?code=… ─ (short-lived, single-use code)
App backend ── code + PKCE verifier ──► token endpoint
App backend ◄── ID token (who) + access token (what it may call) + refresh token
App backend checks the callback belongs to this login, validates the ID token
App backend creates its OWN session → cookie to the browser
```

- **Прежде чем доверять результату**, приложение проверяет, что callback (возврат от провайдера в приложение) относится к начатому им входу (PKCE, а также `state` или `nonce`, если они используются), и проверяет ID token: подпись, издателя, аудиторию и срок действия. Хорошая библиотека делает это сама; никогда не пропускайте этот шаг.
- **PKCE** (Proof Key for Code Exchange — ключ-доказательство для обмена кода) доказывает, что поток завершает то же приложение, которое его начало, поэтому украденный код бесполезен. Он рекомендован для всех клиентов и обязателен для приложений, которые не могут хранить секрет (SPA, мобильные приложения).
- Старый **implicit flow** (неявный поток), который клал токены прямо в URL, устарел.
- Большинство приложений используют OIDC только чтобы **узнать, кто пользователь**, а затем создают свою сессию. Токены провайдера в качестве сессии они не используют.
- **ID token — для клиента**, чтобы узнать, кто вошёл. **Access token — для API**. Не отправляйте ID token в API как доказательство доступа.

## Типичные проблемы

- **Аутентификация без авторизации**: любой вошедший пользователь может прочитать любой объект, поменяв ID.
- **Авторизация только в UI.**
- **Долгоживущие JWT без возможности отзыва** и «выход», который удаляет только копию в браузере.
- **Ошибки проверки JWT**: принимать `alg: none`, не проверять срок действия, издателя и аудиторию или считать JWT секретным. Подписанный JWT не зашифрован; payload может раскодировать кто угодно.
- **Токены в `localStorage`** на сайте с множеством сторонних скриптов.
- **ID сессии не обновляется при входе**, или сессии никогда не истекают.
- **Разные правила в разных сервисах**, каждое реализовано чуть иначе.
- **Самодельное хранение паролей или криптография** вместо проверенных библиотек или провайдеров.
- **Вход и сброс пароля без rate limiting** (ограничения частоты запросов), что открывает дорогу credential stuffing (перебору паролей, утёкших с других сайтов), и сообщения, которые выдают, существует ли аккаунт.

## Как выбирать

- **Своё веб-приложение и свой бэкенд:** серверные сессии с cookie `HttpOnly`. Просто, и отозвать легко.
- **Вход через существующие аккаунты или корпоративный SSO:** OIDC через провайдера или библиотеку, затем своя сессия.
- **SPA плюс API на другом домене:** лучше BFF или API на том же origin с cookie. Иначе — короткоживущие access tokens в памяти. Обновлять их можно двумя способами: эндпоинт вашего собственного бэкенда хранит refresh token в cookie с `HttpOnly` и выдаёт новые access tokens (token-mediating backend — бэкенд-посредник для токенов; этому эндпоинту всё равно нужна защита от CSRF), или SPA работает как чистый OAuth-клиент и сам обрабатывает ротируемые refresh tokens — это наименее защищённый вариант.
- **Мобильные приложения, CLI, сервер-сервер:** токены в заголовке `Authorization` (сервер-сервер: OAuth-поток client credentials или взаимный TLS).
- **Приложения других разработчиков, действующие от имени ваших пользователей:** вы становитесь OAuth-провайдером; используйте готовую проверенную реализацию.
- **Писать самим или покупать:** аутентификация критична для безопасности и полна деталей. Хостинговые провайдеры и зрелые библиотеки — вариант по умолчанию; правила авторизации пишите сами, потому что это ваша бизнес-логика.

## Ландшафт

- **Хостинговая идентификация:** Auth0 (Okta), Clerk, Firebase Authentication, Supabase Auth, Amazon Cognito, Microsoft Entra ID, WorkOS (корпоративный SSO). Self-hosted: Keycloak, Ory, Authentik, Zitadel.
- **Библиотеки:** Auth.js, Better Auth, Passport.js, встроенная аутентификация в Rails, Django, Laravel и ASP.NET; SimpleWebAuthn для passkeys.
- **Авторизация:** CASL, Casbin, Open Policy Agent, Cerbos; OpenFGA и SpiceDB для правил на основе связей (в стиле Zanzibar от Google).
- **Стандарты:** OAuth 2.0 и готовящийся OAuth 2.1, OpenID Connect, SAML, WebAuthn и passkeys, JWT (RFC 7519), SCIM (синхронизация пользователей из корпоративного каталога).
