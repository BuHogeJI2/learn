## Какую проблему решает

Вы вошли в свой банк в одной вкладке и открыли случайный сайт в другой. Браузер хранит cookies банка. Если бы правил не было, JavaScript случайного сайта мог бы вызвать `fetch("https://bank.example/account")`, браузер приложил бы ваши cookies, и скрипт прочитал бы ваш баланс.

Браузер — одна программа, которая выполняет код множества сторон, не доверяющих друг другу. Его границы безопасности решают, что код из одного места может **читать** или **делать** с другим местом.

Одну вещь стоит держать в голове с самого начала: эти правила защищают **пользователя внутри браузера**. Ваш сервер они не защищают. `curl`, скрипт или мобильное приложение игнорируют их все. Сервер всё равно должен проверять, кто к нему обращается ([аутентификация и авторизация](/ru/security/auth/)).

## Ментальная модель: origin, сайт и три вида доступа

**Origin** (источник) = схема + хост + порт. Два URL имеют один origin, только если совпадают все три части.

**Сайт** (site) = схема + регистрируемый домен (та часть, которую вы покупаете у регистратора, например `shop.example`; для `api.shop.example` сайт всё равно `shop.example`). Некоторые домены внесены в **Public Suffix List** (список публичных суффиксов, например `github.io`), поэтому `alice.github.io` и `bob.github.io` — разные сайты.

В сравнении с `https://shop.example`:

| URL | Тот же origin? | Тот же сайт? | Почему |
| --- | --- | --- | --- |
| `https://shop.example/cart` | Да | Да | Отличается только путь |
| `http://shop.example` | Нет | Нет | Другая схема |
| `https://shop.example:8443` | Нет | Да | Другой порт |
| `https://api.shop.example` | Нет | Да | Другой хост, тот же регистрируемый домен |
| `https://other.example` | Нет | Нет | Другой регистрируемый домен |

Разные правила используют разные единицы: **same-origin policy** (политика одного источника) и хранилища работают с origin; cookies с `SameSite` и разделение cookies — с сайтом. Cookies старше same-origin policy и следуют своим правилам области действия (`Domain`, `Path`), а не origin.

**Same-origin policy** делит взаимодействия между разными origin на три вида:

```
Page on https://app.example
  │
  ├─ <img src="https://cdn.other/x.png">       embed:  allowed
  ├─ <form action="https://bank.example/pay">   send:   allowed (cookies depend on SameSite)
  └─ fetch("https://api.other/data")            send:   allowed
                                                read:   only if api.other allows it (CORS)
```

- **Запись** (ссылки, редиректы, отправка форм) на другой origin разрешена.
- **Встраивание** (`<img>`, `<script>`, стили, `<iframe>`, медиа) разрешено, если другой сервер не запретил его заголовками.
- **Чтение** по умолчанию заблокировано: JavaScript не видит ответ с другого origin, DOM iframe с другого origin и пиксели картинки с другого origin, нарисованной на canvas.

Главное: **политика запрещает читать, а не отправлять**. Запрос на другой origin часто доходит до сервера и выполняется там; браузер просто не отдаёт ответ скрипту. Именно этим разрывом пользуются атаки [CSRF](/ru/security/web-attacks/#csrf-запросы-которых-пользователь-не-хотел).

## CORS: сервер сам разрешает себя читать

**CORS** (Cross-Origin Resource Sharing — совместное использование ресурсов между разными источниками) позволяет серверу ослабить same-origin policy для своих ответов. Это разрешение от **владельца ресурса**, а соблюдает его браузер.

**Простые запросы** (`GET`, `HEAD` или `POST` только с базовыми заголовками и типом содержимого как у формы: `application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain`) отправляются сразу, с заголовком `Origin`. Если в ответе нет подходящего `Access-Control-Allow-Origin`, скрипт получает ошибку. Но запрос **уже дошёл до сервера и выполнился**.

**Остальные запросы** (`PUT`, `DELETE`, тело в JSON, свои заголовки вроде `Authorization`) сначала получают **preflight** (автоматический запрос `OPTIONS`, который спрашивает разрешения):

```
Browser (app.example)                          api.example
  │── OPTIONS /orders/42                      ──►│
  │   Origin: https://app.example                │
  │   Access-Control-Request-Method: PUT         │
  │◄── 204                                     ──│
  │   Access-Control-Allow-Origin: https://app.example
  │   Access-Control-Allow-Methods: PUT
  │   Access-Control-Max-Age: 600
  │── PUT /orders/42  (the real request)      ──►│
  │◄── 200 + Access-Control-Allow-Origin        ──│  → the script can read it
```

`Access-Control-Max-Age` позволяет браузеру закэшировать ответ на preflight, чтобы не каждый запрос стоил лишнего round trip (пути до сервера и обратно).

**Учётные данные.** По умолчанию `fetch` на другой origin **не** отправляет cookies. С `credentials: 'include'` браузер может их отправить, но только те cookies, которые всё ещё разрешены их собственными правилами (`SameSite`, `Domain`, `Secure`, блокировка сторонних cookies); `include` эти правила не отменяет. Чтобы скрипт смог прочитать ответ, тот должен содержать `Access-Control-Allow-Credentials: true` и **конкретный** origin, а не `*`.

Что из этого следует:

- **Ошибка CORS исправляется на сервере**, а не в опциях `fetch`. `mode: 'no-cors'` даёт непрозрачный ответ, который скрипт не может прочитать; он прячет ошибку, а не исправляет её.
- **CORS — не контроль доступа к вашему API.** Он управляет только тем, что браузеры разрешают читать скриптам. Клиенты вне браузера его игнорируют.
- **Тот же сайт всё равно требует CORS.** `app.shop.example`, который вызывает `api.shop.example`, делает запрос на другой origin.
- **Самый дешёвый CORS — его отсутствие.** Если отдавать API с того же origin (`/api` на том же домене, маршрутизация через [reverse proxy или CDN](/ru/web-platform/cdn/#ментальная-модель-reverse-proxy-перед-всем-остальным)), preflight исчезают, а cookies остаются простыми.

## Когда браузер отправляет cookies

Основы cookies описаны на [странице про HTTP](/ru/web-platform/http/#cookies-на-уровне-протокола). Для безопасности важнее всего два атрибута:

| `SameSite` | Отправляется в запросах внутри сайта | Отправляется при переходе верхнего уровня с другого сайта (клик по ссылке) | Отправляется в других запросах с других сайтов (`fetch`, формы с `POST`, iframe, картинки) |
| --- | --- | --- | --- |
| `Strict` | Да | Нет | Нет |
| `Lax` | Да | Да, для безопасных методов вроде `GET` | Нет |
| `None` (требует `Secure`) | Да | Да | Да, если браузер не блокирует сторонние cookies. **Разделённая** (partitioned) cookie отправляется только в пределах того же сайта верхнего уровня, где её установили |

И область действия:

- Cookie **без `Domain`** привязана к хосту: отправляется только на тот хост, который её установил.
- `Domain=shop.example` отправляет её ещё и на **все поддомены**.
- Префикс имени `__Host-` требует `Secure`, `Path=/` и отсутствия `Domain`. Cookie закреплена за одним хостом, и поддомены не могут её перезаписать.

Помните, что `SameSite` работает с **сайтами**: `blog.shop.example` и `shop.example` — один сайт. Поддомен с пользовательским контентом или забытая маркетинговая страница могут отправлять запросы внутри сайта с cookies ваших пользователей.

## Другие границы, которые стоит знать

- **Хранилища** (`localStorage`, IndexedDB) разделены по origin. Сторонние iframe получают **разделённое** хранилище: отдельную копию для каждого сайта верхнего уровня.
- **Iframe и окна.** Iframe с другого origin не может трогать DOM родителя. Они общаются через `postMessage`; получатель должен проверять `event.origin`, а отправитель — указывать целевой origin вместо `'*'`.
- **Кто может встраивать вашу страницу во фрейм**, управляет директива `frame-ancestors` в CSP (см. [clickjacking](/ru/security/web-attacks/#clickjacking-и-другие-атаки-через-ui)).
- **Изоляция процессов.** Браузеры запускают разные сайты в разных процессах, чтобы баг вроде Spectre (чтение памяти через тайминги процессора) не дотянулся до данных другого сайта. Страницы, которым нужны мощные возможности вроде `SharedArrayBuffer`, должны явно включить **cross-origin isolation** (изоляцию между origin) заголовками `Cross-Origin-Opener-Policy` и `Cross-Origin-Embedder-Policy`.

## Типичные проблемы

- **Отражение любого `Origin` с `Allow-Credentials: true`.** Сервер копирует в `Access-Control-Allow-Origin` любой origin, который спросил. Теперь любой сайт в интернете может читать данные ваших залогиненных пользователей.
- **Слабая проверка списка разрешённых.** `origin.endsWith("shop.example")` совпадает и с `evilshop.example`. Сравнивайте полные origin с фиксированным списком.
- **Разрешение origin `null`.** Iframe в песочнице и локальные файлы отправляют `Origin: null`, и атакующий может получить его намеренно.
- **Забытый `Vary: Origin`**, когда разрешённый origin меняется от запроса к запросу. CDN кэширует заголовок для первого origin и отдаёт его всем ([`Vary`](/ru/architecture/caching/#http-кэширование-общий-язык)). Некоторые CDN без настройки игнорируют `Vary`, поэтому проверьте ещё и то, что ключ кэша CDN включает `Origin`.
- **CORS как защита.** «Только наш фронтенд может вызвать этот API» — неправда; вне браузера его может вызвать кто угодно.
- **Cookie с широким `Domain`**, общая для всех поддоменов, включая те, которыми управляют третьи стороны.
- **`postMessage` без проверки origin** или отправка секретов с целью `'*'`.
- **Preflight на каждый запрос**, потому что нет `Max-Age` или API без причины живёт на другом origin.

## Проектирование с учётом границ

- **Один origin для приложения и его API**, когда это возможно. Нет CORS, нет preflight, cookies с `SameSite=Lax` просто работают.
- **Отдельный origin для API** (публичный API, много клиентских приложений): явный список разрешённых origin, учётные данные только при необходимости, `Max-Age` для preflight, `Vary: Origin`.
- **Публичные данные только для чтения** (шрифты, публичный JSON, открытые API без cookies): `Access-Control-Allow-Origin: *` подходит.
- **Недоверенный контент** (загрузки пользователей, пользовательские сайты, песочницы): отдавайте его с **отдельного регистрируемого домена**, а не с поддомена основного сайта. Поэтому GitHub Pages использует `github.io`, а Google отдаёт файлы пользователей с `googleusercontent.com`.

## Ландшафт

- **Инструменты браузера:** Console показывает ошибки CORS с причиной; вкладка Network показывает preflight-запросы `OPTIONS`; панель Application показывает у каждой cookie `SameSite`, `Domain` и раздел.
- **Сервер:** CORS-middleware в каждом фреймворке (пакет `cors` для Express, встроенные опции в Fastify, Hono, NestJS, Django, Rails), правила CDN и API gateway, которые добавляют CORS-заголовки.
- **Стандарты:** Fetch Standard (определяет CORS и режимы запросов), HTML Standard (origin, `postMessage`), RFC 6265bis (cookies), Public Suffix List.
