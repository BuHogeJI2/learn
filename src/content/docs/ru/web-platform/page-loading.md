## Какую проблему решает

Между нажатием Enter и появлением страницы происходит около десятка шагов, и любой из них может оказаться медленным. Если вы знаете последовательность, медленная страница перестаёт быть загадкой: можно прочитать вкладку Network, найти шаг, который отнимает время, и выбрать правильное исправление. Без этого знания люди уменьшают бандл, когда проблема в сервере, или ускоряют сервер, когда рендеринг блокирует скрипт.

## Путь

```
 URL entered
   │
 1 ├─ Can we skip the network?  HTTP cache, service worker, back/forward cache, prerender
 2 ├─ DNS lookup                name → IP address
 3 ├─ Connection                TCP + TLS handshakes (or QUIC for HTTP/3)
 4 ├─ Request → server works    first byte of HTML arrives (TTFB)
 5 ├─ HTML is parsed as it streams in → DOM
 │     ├─ CSS found     → download, build CSSOM      (blocks rendering)
 │     ├─ <script> found → download, maybe run        (may block the parser)
 │     └─ images, fonts  → download in parallel
 6 ├─ Style → Layout → Paint → Composite              first pixels (FCP), main content (LCP)
 7 └─ JavaScript runs, handlers attach                 page responds to input (INP)
```

**1. Обойтись без сети.** Самый быстрый запрос — тот, который не отправлен. Браузер проверяет свой HTTP-кэш (см. [Кэширование](/ru/architecture/caching/)), может ответить service worker, back/forward cache (кэш для кнопок «назад» и «вперёд») может мгновенно восстановить всю страницу, а страница, заранее **отрендеренная** (prerender, через Speculation Rules API), появляется сразу.

**2. DNS.** Доменное имя превращается в IP-адрес. Ответы кэшируются браузером и операционной системой, поэтому время тратится в основном при первом визите: от нескольких миллисекунд до более чем 100 мс.

**3. Соединение.** Для HTTP/1.1 и HTTP/2 браузер открывает TCP-соединение (один round trip), а затем выполняет TLS handshake (ещё один round trip с TLS 1.3). HTTP/3 работает поверх QUIC, который совмещает оба шага в один round trip. Каждый **round trip** (RTT — время, за которое пакет доходит до сервера и обратно) — это единица, которая имеет значение: в мобильной сети он может быть 100 мс и больше, так что три round trip до первого запроса — уже заметная задержка. Это главная причина, почему [CDN](/ru/web-platform/cdn/) помогает даже для контента, который нельзя закэшировать: handshake выполняются с ближайшим сервером. См. [версии HTTP](/ru/web-platform/http/#версии-http-смысл-тот-же-транспорт-разный).

**4. Запрос и работа сервера.** Браузер отправляет запрос и ждёт. **TTFB** (Time To First Byte, время до первого байта) для страницы измеряется от начала навигации до первого байта HTML. Он включает редиректы, DNS, соединение и всё, что делает сервер (запросы к базе данных, рендеринг). Каждый редирект добавляет ещё один полный запрос. Фаза «Waiting (TTFB)» в DevTools уже: только время после отправки запроса.

**5. Парсинг.** Браузер не ждёт весь HTML-файл; он разбирает его по мере поступления и строит **DOM** (дерево элементов). По ходу дела:

- **CSS блокирует рендеринг.** Браузер не будет рисовать, пока не получит найденный CSS, чтобы не показывать контент без стилей. Он строит **CSSOM** (дерево стилей).
- **Классический `<script>` блокирует парсер.** Парсер останавливается, загружает скрипт, выполняет его и только потом продолжает, потому что скрипт может изменить документ. `defer` и `type="module"` (по умолчанию отложенный) загружаются параллельно и выполняются после парсинга, по порядку: блокировки нет. `async` загружается параллельно, но выполняется сразу, как только пришёл, в любом порядке; пока он выполняется, парсер всё равно стоит.
- **Preload scanner** (сканер предзагрузки) — второй, облегчённый парсер, который заглядывает вперёд в исходный HTML и начинает загружать ресурсы рано, даже пока основной парсер заблокирован. Он видит только то, что написано в HTML. Ресурсы, которые он **не видит**, находятся поздно: фоновые картинки в CSS, скрипты и картинки, добавленные из JavaScript, шрифты, на которые ссылается CSS, и `@import` внутри CSS.

**6. Рендеринг.** Браузер вычисляет стили, выполняет **layout** (размер и положение каждого блока), **paint** (рисует пиксели) и **composite** (собирает слои на GPU). Когда позже меняется DOM или размеры, layout выполняется снова; контент, который сдвигается после того, как его уже показали, — это **layout shift** (сдвиг макета).

**7. Интерактивность.** JavaScript выполняется в **главном потоке** (main thread) — том же, который обрабатывает ввод и рендеринг. Пока работает длинный скрипт, клики ждут. У страниц, отрендеренных на сервере, HTML может быть виден задолго до того, как готов их JavaScript; см. [гидратацию](/ru/architecture/rendering/#гидратация-цена-html-который-выглядит-готовым).

### Как шаги соотносятся с метриками

| Метрика | Что измеряет | В основном зависит от шагов |
| --- | --- | --- |
| TTFB | Первый байт HTML | 2–4: DNS, соединение, сервер |
| FCP (First Contentful Paint) | Первый текст или картинка на экране | 4–6 |
| **LCP** (Largest Contentful Paint) | Основной контент, например главная картинка или заголовок | 4–6, особенно позднее обнаружение ресурсов |
| **CLS** (Cumulative Layout Shift) | Насколько сильно прыгает контент | 6 |
| **INP** (Interaction to Next Paint) | Как быстро страница реагирует на ввод | 7 |

Три выделенные метрики — это **Core Web Vitals**, по которым Google оценивает опыт реальных пользователей.

## Читаем вкладку Network

Вкладка Network в DevTools браузера показывает каждый запрос на временной шкале (**waterfall**, «водопад»). Колонки, которые отвечают на большинство вопросов:

- **Initiator**: кто запросил этот файл. Показывает **цепочки**: HTML → CSS → шрифт или JS → JS → JSON.
- **Size**: переданный размер, или `(memory cache)`, `(disk cache)`, `(ServiceWorker)`, когда сеть не использовалась.
- **Protocol** (включается правым кликом по заголовку таблицы): `h2`, `h3`.
- **Priority**: насколько важным браузер считает запрос.

Кликните по запросу и откройте **Timing**, чтобы увидеть его фазы:

| Фаза | Что означает |
| --- | --- |
| Queueing, Stalled | Ожидание старта: более низкий приоритет или лимит в шесть соединений у HTTP/1.1 |
| DNS Lookup | Разрешение имени |
| Initial connection, SSL | TCP и TLS handshake |
| Request sent | Отправка запроса |
| Waiting (TTFB) | Один round trip плюс время сервера |
| Content Download | Получение тела ответа |

### Паттерны и что они означают

| Что вы видите | Вероятная причина | Направление исправления |
| --- | --- | --- |
| Долгое «Waiting» у HTML-документа | Медленный или далёкий сервер | Кэширование, CDN, стриминг HTML |
| Лесенка: каждый файл начинается только после окончания другого | Цепочка запросов из-за позднего обнаружения | Ресурсы прямо в HTML, `preload`, плоские импорты |
| Много запросов в «Queueing» или «Stalled» | Лимит HTTP/1.1 или низкий приоритет | HTTP/2, меньше запросов, приоритеты |
| Долгий «Content Download» | Большие файлы | Сжатие, картинки поменьше, code splitting |
| Пауза между HTML и запросом LCP-картинки | LCP-картинка найдена поздно (фон в CSS, рендер из JS) | Картинка прямо в HTML, `fetchpriority="high"` |
| Сеть молчит, а страница медленно реагирует | JavaScript в главном потоке | Смотреть вкладку Performance, а не Network |

Полезные переключатели: **Disable cache** (чтобы увидеть первый визит), **throttling** (чтобы имитировать медленную сеть) и **Preserve log** (чтобы сохранять запросы при редиректах).

## Рычаги: что можно изменить

| Цель | Рычаги |
| --- | --- |
| Меньше round trip | CDN рядом с пользователями; без цепочек редиректов; HTTP/3; `preconnect` к важным сторонним origin |
| Раньше обнаружить ресурсы | Ресурсы прямо в HTML; `<link rel="preload">`; `103 Early Hints` |
| Правильный приоритет | `fetchpriority="high"` для LCP-картинки, `"low"` для менее важных файлов; без `loading="lazy"` на LCP-картинке |
| Меньше байтов | Сжатие Brotli или Zstandard; картинки AVIF и WebP; code splitting |
| Меньше блокировок | Скрипты с `defer` / `async`; небольшой критический CSS; `font-display` для веб-шрифтов |
| Быстрее сервер | Кэширование; [стриминг HTML](/ru/architecture/rendering/#стриминг), чтобы браузер начал работу раньше |
| Совсем без сети | Заголовки HTTP-кэша; back/forward cache; service worker; prerender вероятных следующих страниц |

## Типичные проблемы

- **Оптимизация не того шага.** Уменьшение бандла не поможет, если TTFB — две секунды. Сначала посмотрите на waterfall.
- **Сторонние скрипты, блокирующие рендеринг.** Менеджер тегов или виджет чата как классический скрипт в `<head>` задерживают всё.
- **Ленивая загрузка главной картинки.** `loading="lazy"` на LCP-картинке задерживает самый важный элемент.
- **Цепочки редиректов.** `http://` → `https://` → `www.` → `/en/`: каждый шаг — полный round trip до какого-либо контента.
- **Картинки и встраиваемые блоки без зарезервированного места.** Без `width`/`height` или соотношения сторон контент прыгает, когда они загружаются (CLS).
- **Тестирование только на быстром ноутбуке с быстрым Wi-Fi.** Лабораторные тесты полезны для отладки, но результат определяют реальные пользователи на телефонах среднего уровня. Сравнивайте с **полевыми данными** (field data) от реальных пользователей.

## Когда это знание окупается

- Любое расследование производительности: оно говорит, какой шаг измерять.
- Выбор [стратегии рендеринга](/ru/architecture/rendering/): каждая стратегия переносит работу между шагами 4, 5 и 7.
- Ревью сторонних скриптов, шрифтов и картинок до того, как их добавят.
- Чтение отчётов Lighthouse или PageSpeed: каждый аудит соответствует одному из шагов выше.

## Ландшафт

- **Инструменты браузера:** панели Network и Performance в DevTools, Lighthouse.
- **Лабораторное тестирование:** WebPageTest (filmstrip, waterfall, реальные устройства и локации), PageSpeed Insights.
- **Полевые данные:** Chrome UX Report (CrUX) и инструменты мониторинга реальных пользователей (RUM), например Vercel Speed Insights, Sentry, SpeedCurve, или библиотека `web-vitals`, отправляющая данные в вашу аналитику.
