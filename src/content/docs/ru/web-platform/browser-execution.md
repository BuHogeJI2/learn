## Какую проблему решает

[Как браузер загружает страницу](/ru/web-platform/page-loading/) заканчивается словами «JavaScript выполняется в главном потоке, и пока он работает, клики ждут». Затем [Web Vitals](/ru/observability/web-vitals/#inp-как-быстро-страница-реагирует) советует разбивать длинные задачи, уступать браузеру или использовать worker (фоновый поток). Эта страница объясняет, почему всё это работает.

Без этой модели возвращаются одни и те же ошибки: страница, которая зависает во время вычисления, спиннер, который не появляется, потому что браузер так и не получил шанс его нарисовать, и «но это же `async`!» про код, который по-прежнему блокирует каждое нажатие.

## Ментальная модель: один работник, одна очередь дел

Для каждой страницы почти всё делает один поток: выполняет ваш JavaScript, обрабатывает события ввода, вычисляет стили и раскладку и рисует. Это **главный поток** (main thread). Он делает что-то одно за раз.

**Event loop** (цикл событий) — это способ, которым он выбирает, что делать дальше:

```
        ┌─────────────────────────────────────────────────────┐
        │ 1. take one task from a queue                       │
        │    (click, timer, network response, script)         │
        │ 2. run it to the end  ◄── nothing else can happen   │
        │ 3. run all microtasks (promise callbacks)           │
        │ 4. maybe render: rAF → style → layout → paint       │
        └──────────────────────── repeat ─────────────────────┘
```

Большую часть поведения объясняют три правила:

- **Задача выполняется до конца.** Когда задача началась, её ничто не прервёт: ни нажатие, ни отрисовка. Нажатие во время 2-секундной задачи ждёт 2 секунды.
- **Рендеринг происходит между задачами.** Браузер может рисовать, только когда текущая задача и её микрозадачи закончились. Рисует он не после каждой задачи: он старается совпасть с частотой обновления экрана, обычно 60 раз в секунду, то есть примерно 16 мс на кадр.
- **Изменения DOM видны не сразу.** Ваш код обновляет DOM мгновенно, но пользователь видит изменение только при следующей отрисовке. Если одна задача показывает спиннер, считает и прячет спиннер, пользователь его не увидит.

## Задачи, микрозадачи и кадры

| Вид | Откуда берётся | Когда выполняется |
| --- | --- | --- |
| **Задача** (task) | События, `setTimeout`, сетевые колбэки, `postMessage`, скрипты страницы | По одной за оборот цикла; между задачами может быть рендеринг |
| **Микрозадача** (microtask) | `Promise.then`, код после `await`, `queueMicrotask` | Все сразу, сразу после текущей задачи, до любого рендеринга |
| **Кадр анимации** | `requestAnimationFrame` (rAF) | Прямо перед следующей отрисовкой |

Важное различие: **браузер не может рисовать между микрозадачами**. Если микрозадача планирует другую микрозадачу, цепочка продолжается до конца, и длинная цепочка блокирует страницу точно так же, как одна длинная задача. Поэтому `await` на уже завершённом Promise не даёт браузеру шанса отрисовать кадр.

`setTimeout(fn, 0)` ставит в очередь новую задачу, поэтому если текущий код затем завершится, браузер сможет нарисовать кадр или обработать ввод до запуска `fn`. Код, который продолжается после вызова, всё равно блокирует: отложенная работа должна быть внутри `fn` или после `await` Promise, который разрешает таймер. На самом деле это не ноль: вложенные таймеры ограничиваются примерно 4 мс, а фоновые вкладки притормаживаются гораздо сильнее.

## Async — не значит параллельно

`async`, `await` и Promise — про **ожидание**, а не про одновременную работу.

```
await fetch(url)        the network work happens outside the main thread;
                        the thread is free to do other things while waiting
await heavyCalculation()  the calculation still runs on the main thread;
                          marking it async moves nothing
```

- **Ожидание ввода-вывода** (сеть, диск, таймеры) не блокирует. Браузер делает это в другом месте, а ваш код продолжается, когда приходит результат, и в это время выполняются другие задачи. Поэтому один поток справляется со страницей с пятьюдесятью параллельными запросами.
- **Работа CPU** (фильтрация, сортировка, разбор, рендеринг большого дерева компонентов) блокирует, какой бы синтаксис её ни окружал. Главный поток должен сделать вычисление сам.

Асинхронный код ещё и может чередоваться. Пока `await` действительно ждёт, выполняются другие задачи, поэтому состояние может измениться посреди вашей функции. Отсюда берутся [race condition](/ru/architecture/state/#типичные-проблемы) (гонки) во фронтенд-коде.

## Long tasks и что чувствуют пользователи

**Long task** (длинная задача) — задача, которая занимает главный поток дольше 50 мс. Это число — определение для диагностики, а не бюджет: для плавной анимации на кадр остаётся около 16 мс. Всё время длинной задачи ввод ждёт, анимации на JavaScript стоят и ничего не рисуется. Обычные источники:

- выполнение и разбор больших бандлов JavaScript;
- [гидратация](/ru/architecture/rendering/#гидратация-цена-html-который-выглядит-готовым) и большие перерисовки;
- сторонние скрипты;
- **принудительная раскладка** (forced layout): чтение значения геометрии, например `offsetHeight`, сразу после изменения DOM заставляет браузер немедленно вычислить раскладку. В цикле это называется **layout thrashing** (постоянный пересчёт раскладки).

Long tasks — частая причина плохого [INP](/ru/observability/web-vitals/#inp-как-быстро-страница-реагирует) (насколько быстро страница реагирует на ввод), но измеряет он не их: в INP входят ещё ваши обработчики событий и время отрисовки следующего кадра, и он может быть плохим без единой задачи дольше 50 мс.

CSS-анимации `transform` и `opacity` обычно могут выполняться на **компоновщике** (compositor — отдельном потоке, который двигает уже нарисованные слои), поэтому остаются плавными, пока главный поток занят. Анимациям `top` или `height` нужен главный поток.

## Варианты: что делать с тяжёлой работой

| Вариант | Как помогает | Цена |
| --- | --- | --- |
| **Делать меньше** | Отправлять меньше кода, меньше рендерить, кэшировать результаты | Нужна настоящая работа, зато это единственный вариант, который экономит ещё и батарею и байты |
| **Уступать** (yield): разбить работу и дать браузеру очередь | Между частями могут пройти ввод и отрисовка | Всё вместе занимает немного дольше; между частями могут выполняться другие задачи, поэтому состояние может измениться |
| **Приоритизация** во фреймворке | [Transitions](/ru/tools/react/suspense/#обновления-transitions-сохраняют-то-что-уже-показано) в React позволяют срочным обновлениям прерывать работу рендеринга | Помогает только рендерингу, а не вашему синхронному коду |
| **Web worker** | Работа идёт в другом потоке, а главный остаётся свободным | Нет доступа к DOM; данные копируются через `postMessage`; больше настройки |
| **Сервер** | Работа вообще не доходит до телефона | Сетевой round trip и стоимость сервера |

**Уступить** значит завершить текущую задачу и продолжить в новой. `await scheduler.yield()` делает именно это и ставит продолжение впереди другой работы того же приоритета, поэтому срочный ввод всё равно может пройти первым. Он работает в Chrome и Firefox, но не в Safari, поэтому сначала проверяйте наличие и в запасном варианте ждите Promise, который разрешает `setTimeout`; завершённый Promise запасным вариантом не годится, потому что не уступает. Обычно хватает небольшого помощника, который в длинном цикле уступает примерно каждые 50 мс.

**Web worker** запускает отдельный event loop в отдельном потоке. Они подходят для чистых вычислений: разбор большого файла, обработка картинок, поиск по большому списку, WebAssembly. Со страницей они общаются сообщениями, а данные копируются (**structured clone**, структурное клонирование), что для больших объектов само занимает время. `ArrayBuffer` можно **передать** без копирования, а `SharedArrayBuffer` делит память, но требует [cross-origin isolation](/ru/security/browser-boundaries/#другие-границы-которые-стоит-знать). Worker не может трогать DOM, поэтому результат всё равно применяет главный поток. [Service worker](/ru/web-platform/offline-and-storage/#service-worker-прокси-в-браузере) — другое: он обрабатывает сетевые запросы, а не ваши вычисления.

## Чтение записи Performance

Вкладка Network показывает, что загрузилось. **Панель Performance** в Chrome DevTools показывает, что делал главный поток.

1. Включите **замедление CPU** (4× или 6×), потому что ваш ноутбук намного быстрее обычного телефона.
2. Запишите, пока делаете медленное действие: нажимаете кнопку, вводите в поле.
3. Посмотрите на дорожку **Main**. Каждый блок — задача, а блоки внутри — функции, которые она вызвала. Задачи дольше 50 мс отмечены красным уголком.
4. Найдите самый широкий блок и спуститесь до функции, которая занимает время.

| Что вы видите | Вероятная причина | Направление исправления |
| --- | --- | --- |
| Один широкий блок скрипта после нажатия | Медленный обработчик события или большая перерисовка | Сначала показать отклик, разбить работу, меньше рендерить |
| Фиолетовые блоки «Layout», повторяющиеся в цикле | Layout thrashing | Сначала читать, потом писать; группировать изменения DOM |
| Длинный блок при старте сразу после загрузки скрипта | Разбор и выполнение большого бандла, гидратация | Разделение кода, меньше JavaScript, меньше гидратации |
| Блоки со сторонних доменов | Tag manager, виджеты | Загружать позже или убрать |
| Зелёный «Paint» занимает много времени | Огромные или сложные области перерисовки | Упростить рисуемую область |

Для полевых данных **Long Animation Frames API** сообщает о медленных кадрах у реальных пользователей вместе со скриптами, которые их вызвали. Он есть только в браузерах на Chromium, поэтому считайте его дополнительной диагностикой. Эти данные отвечают на те же вопросы, что и [real-user monitoring](/ru/observability/web-vitals/#лабораторные-и-полевые-данные) (измерения в браузерах пользователей).

## Типичные проблемы

- **Спиннер, который не появляется**: его добавляют и убирают в той же задаче, что и тяжёлую работу, поэтому отрисовки между ними нет.
- **`async` на работе CPU** в ожидании, что она пойдёт в фоне.
- **Длинная цепочка микрозадач**, которая не даёт рендерингу выполниться.
- **`await` в цикле по тысячам элементов**, который на самом деле никогда не уступает.
- **Layout thrashing**: чтение `offsetHeight` после каждой записи в цикле.
- **Уступка без защиты**: пока работа на паузе, пользователь меняет ввод, и старый результат перезаписывает новый. Отменяйте устаревшую работу.
- **Перенос работы с DOM в worker**: рендеринг всё равно происходит в главном потоке.
- **Worker, который копирует огромный объект туда и обратно** и тратит на копирование больше времени, чем экономит.
- **Проверка только на быстром ноутбуке**, где ничто не выглядит длинным.

## Когда это знание окупается

- Страница ощущается зависшей или INP плохой, а сеть выглядит нормально.
- Выбор между worker, сервером и разбиением работы для тяжёлой функции.
- Оценка стороннего скрипта или большой зависимости.
- Понимание, зачем фреймворк предлагает transitions, отложенные значения или ленивую гидратацию.

## Ландшафт

- **Измерение:** панель Performance в Chrome DevTools, API Long Tasks и Long Animation Frames, сборка attribution библиотеки `web-vitals`, Lighthouse.
- **Планирование:** `scheduler.yield()` и `scheduler.postTask()`, `requestIdleCallback`, `requestAnimationFrame`, transitions в React.
- **Вне главного потока:** Web Workers, включая WebAssembly, запущенный внутри worker (сам по себе WebAssembly работает в главном потоке); библиотека Comlink для более удобных сообщений worker; Partytown для переноса сторонних скриптов в worker.
