## Какую проблему решает

Некоторые данные должны оставаться на устройстве: неотправленный черновик, выбранная тема, большой набор данных, который не стоит скачивать дважды, оболочка (app shell — базовый UI и файлы, нужные для открытия приложения) инструмента, который открывают в поезде. А сеть есть не всегда. По умолчанию веб-приложение без соединения показывает страницу ошибки браузера.

Браузер предлагает несколько хранилищ и один программируемый сетевой слой. Сложность не в API. Сложность в том, чтобы решить, **кто владеет данными**, **как долго они могут жить** и **что происходит, когда устройство и сервер расходятся**.

Данные в браузере — это [копия на чужом диске](/ru/architecture/state/#ментальная-модель-решает-владелец): пользователь может их удалить, браузер может их вытеснить, а скрипты на вашем [origin](/ru/security/browser-boundaries/#ментальная-модель-origin-сайт-и-три-вида-доступа) (схема + хост + порт) могут прочитать большую их часть. Считайте их кэшем, если нет причин считать иначе.

## Ментальная модель: хранилища на origin и прокси перед сетью

```
page ──┬── localStorage        small strings, synchronous
       ├── IndexedDB           structured data, queries, large
       ├── Cache API           request → response pairs
       ├── OPFS                files
       │
       └── fetch ──► service worker ──► cache or network
                     (a proxy your code controls)
```

Все эти хранилища относятся к одному origin, а сторонние iframe получают отдельную, разделённую копию. IndexedDB, Cache API и OPFS делят одну квоту и удаляются вместе; у `localStorage` и `sessionStorage` свой небольшой лимит, а у cookies свои правила.

## Варианты хранения

| Хранилище | Что хранит | API | Для чего подходит | Ограничения |
| --- | --- | --- | --- | --- |
| **Cookies** | Маленькие строки, отправляются на сервер | Заголовок, `document.cookie` | Идентификация сессии ([аутентификация](/ru/security/auth/#где-браузер-хранит-учётные-данные)) | Около 4 КБ на штуку; отправляются с каждым подходящим запросом |
| **`localStorage`** | Строки | Синхронный | Небольшие настройки | Около 5 МиБ на origin; блокирует главный поток |
| **`sessionStorage`** | Строки | Синхронный | Состояние одной вкладки, например форма из нескольких шагов | То же; заканчивается вместе с вкладкой |
| **IndexedDB** | Объекты, файлы, с индексами и транзакциями | Асинхронный, события (обычно через библиотеку) | Офлайн-данные, большие клиентские кэши | Делит квоту origin |
| **Cache API** | Пары HTTP-запрос и ответ | Асинхронный, Promise | Оболочка приложения, файлы, ответы API; используется из service worker | Делит квоту origin |
| **OPFS** (origin private file system) | Файлы, невидимые пользователю | Асинхронный; быстрый синхронный доступ из worker | SQLite в браузере, редакторы, большие файлы | Делит квоту origin |

**`localStorage` синхронный**: чтение блокирует [главный поток](/ru/web-platform/browser-execution/#ментальная-модель-один-работник-одна-очередь-дел). Держите его маленьким. Никогда не храните [токены и другие секреты](/ru/security/auth/#где-браузер-хранит-учётные-данные) в хранилище, которое может читать JavaScript: их может скопировать любой скрипт на origin. Сессионная cookie с `HttpOnly` — другое дело: скрипты страницы её прочитать не могут.

## Как долго живут данные

По умолчанию хранилище браузера работает как **best-effort** (без гарантий): данные остаются, пока есть место, и браузер может их удалить.

- **Квота.** Для IndexedDB, Cache API и OPFS каждый origin получает долю диска, которая зависит от браузера. Запись сверх квоты завершается ошибкой `QuotaExceededError`, поэтому оборачивайте её в `try/catch`. `navigator.storage.estimate()` даёт приблизительное использование и квоту.
- **Вытеснение при нехватке места.** Когда на устройстве заканчивается место, браузер удаляет данные тех origin, которыми дольше всего не пользовались. Все данные origin уходят разом, поэтому приложение должно обрабатывать состояние «всё пропало».
- **Семидневное правило Safari.** При включённой защите от межсайтового отслеживания origin, с которым пользователь не взаимодействовал последние семь дней использования браузера, теряет данные, созданные его скриптами. Это не срок жизни каждой записи, а веб-приложения на домашнем экране от этого правила освобождены, хотя и не от других причин потери данных.
- **Постоянное хранилище.** `navigator.storage.persist()` просит браузер хранить данные, пока их не удалит пользователь. Это запрос, Promise которого разрешается в `true` или `false`: Firefox спрашивает пользователя; Chromium и Safari решают по тому, как пользователь взаимодействовал с сайтом.
- **Пользователь** может очистить данные сайта в любой момент, а приватные окна их отбрасывают.

Поэтому проектируйте с расчётом на потерю: всё, что хранится только на устройстве, может исчезнуть. Синхронизируйте важные данные с сервером и считайте отсутствие локальной копии нормальным состоянием.

## Service worker: прокси в браузере

**Service worker** — скрипт, который браузер запускает в фоне, отдельно от всех страниц. Когда он управляет страницей, каждый `fetch` с неё проходит через него, и он решает, что ответить. Он работает только по [HTTPS](/ru/web-platform/http/#https-что-добавляет-tls) (или на `localhost`), у него нет DOM, и браузер останавливает его в простое, поэтому хранить состояние в памяти он не может.

**Его жизненный цикл защищает работающие страницы от смешения версий:**

```
register ──► install ──► waiting ──► activate ──► controls pages
             (pre-cache   (old worker  (clean old
              files)       still runs   caches)
                           open tabs)
```

- **Новая версия ждёт**, пока не закроется каждая вкладка, которой управляет старая. Перезагрузки недостаточно, если открыта другая вкладка.
- `skipWaiting()` сразу активирует новый worker, а `clients.claim()` берёт под управление открытые страницы. Оба полезны, и оба создают **[version skew](/ru/delivery/deployment-models/#релизы-от-коммита-до-пользователей)** (расхождение версий): страница, загруженная со старым JavaScript, теперь общается с новым worker и его новыми закэшированными файлами.
- **Браузер проверяет новую версию** скрипта worker при навигации и по умолчанию обходит HTTP-кэш для основного скрипта, но не для скриптов, которые тот импортирует. Версионируйте их, иначе исправление может не дойти до пользователей.

**Service worker — это программируемый [кэш](/ru/architecture/caching/#стратегии-свежести).** Стратегия выбирается для каждого вида запросов:

| Стратегия | Поведение | Для чего подходит |
| --- | --- | --- |
| **Cache first** | Отвечать из кэша, идти в сеть только при промахе | Файлы с хэшем содержимого в имени |
| **Network first** | Пробовать сеть, при отсутствии связи брать из кэша | HTML, данные API, которые должны быть свежими |
| **Stale-while-revalidate** | Отвечать из кэша, обновлять его в фоне | Аватары, данные, которые могут немного устареть |
| **Network only** | Не использовать кэш worker | Платежи, всё личное или чувствительное; им нужны ещё и правильные [заголовки HTTP-кэша](/ru/architecture/caching/#http-кэширование-общий-язык), потому что HTTP-кэш отдельный |

В отличие от HTTP-кэша, у этого кэша нет собственного срока жизни: записи остаются, пока их не удалит ваш код. Забытое правило cache first для HTML может **привязать пользователей к старой версии приложения**, и обычная перезагрузка не поможет, потому что worker продолжает отвечать.

## Офлайн-запись: дорогая часть

Чтение офлайн — в основном задача кэширования. **Запись офлайн превращает клиент в маленькую распределённую систему.**

Типичная схема: сохранить изменение локально, сразу его показать и отправить позже из **outbox** (локальной очереди неотправленных изменений). Записывайте изменение и его запись в outbox в одной транзакции IndexedDB, чтобы падение не оставило локальную правку, которая никогда не будет отправлена.

```
user action ──► local store + outbox ──► UI updates at once
                       │ when online
                       ▼
                    server ──► accepted / rejected / conflict
```

Здесь возникают те же вопросы, что в [надёжности](/ru/architecture/reliability/) и [согласованности](/ru/data/consistency/), только теперь на телефоне:

- **Дубликаты.** Запрос может пройти, а ответ потеряться, и клиент повторит запрос. Дайте каждому изменению [idempotency key](/ru/architecture/reliability/#идемпотентность-делаем-ещё-раз-безопасным) (ключ идемпотентности), созданный один раз и хранящийся вместе с изменением в очереди.
- **Конфликты.** Два устройства изменили одну запись, пока были офлайн. Выбирайте: last write wins (побеждает последняя запись; просто, но молча теряет данные), [проверка версии](/ru/architecture/state/#одновременные-изменения) с показом конфликта пользователю или слияние через CRDT (типы данных, которые сливаются автоматически).
- **Отказ.** Сервер отклоняет изменение, которое пользователь несколько часов назад видел выполненным: товар распродан, права отозваны. В UI нужно место, чтобы это показать.
- **Порядок.** Зависимые изменения нужно отправлять по порядку; одно неудачное изменение может заблокировать те, что за ним.
- **Права и личность.** Пока устройство офлайн, пользователь может выйти из аккаунта или лишиться доступа, а локальные данные предыдущего пользователя не должны остаться для следующего. То же с очередью: привязывайте каждое изменение в ней к пользователю и tenant (организации-клиенту), которые его сделали, иначе правки пользователя A уйдут с учётными данными пользователя B. Сервер всё равно проверяет права на каждое изменение.
- **Схема.** Локальные данные переживают версии приложения. У IndexedDB свои [миграции](/ru/data/schema-evolution/), которые выполняются на устройстве каждого пользователя.
- **Отправка.** API **Background Sync** может отправить outbox после закрытия страницы, но работает только в браузерах на Chromium. Всегда отправляйте ещё и тогда, когда приложение открыто и связь вернулась.

«Сохранено локально» — не то же самое, что «принято сервером», поэтому показывайте в UI ожидающие и неудавшиеся изменения. С `navigator.onLine` будьте осторожны: `true` значит, что есть сетевой интерфейс, а не что ваш сервер доступен. Сигналом считайте настоящие неудачи запросов.

## Типичные проблемы

- **Секреты или токены в `localStorage`.** Одна ошибка [XSS](/ru/security/web-attacks/#xss-данные-которые-становятся-кодом) раскрывает их.
- **Большой JSON в `localStorage`**, который разбирается в главном потоке при каждом запуске.
- **Нет обработки `QuotaExceededError`** или пропажи данных.
- **Персональные данные, оставшиеся на общем устройстве** после выхода.
- **Service worker, кэширующий HTML по принципу cache first**, из-за чего пользователи остаются на старой версии после деплоя.
- **Нет способа убрать сломанный service worker.** Держите план: новый worker, который отменяет свою регистрацию, по тому же URL.
- **Кэширование ответов для вошедших пользователей** в Cache API, откуда их может получить следующий пользователь устройства.
- **Неограниченные кэши**, которые растут, пока браузер не вытеснит всё.
- **Непрозрачные ответы** (opaque responses) с других origin в Cache API: приложение не может прочитать их статус, поэтому может закэшировать ошибку, а браузеры считают их намного больше, чем они есть.
- **Оптимистичные офлайн-записи без плана на отказ**: UI заявляет о том, чего не было.
- **Ожидание офлайн-поддержки от [web app manifest](/ru/web-platform/site-files/#установка-и-идентичность-приложения-web-app-manifest).** Он её не даёт; её даёт service worker.

## Когда что использовать

- **Настройка или небольшой флаг:** `localStorage` или cookie, если сервер должен видеть значение при рендеринге.
- **Неотправленный черновик:** IndexedDB (или `localStorage` для короткого текста) с синхронизацией на сервер.
- **Более быстрые повторные визиты:** сначала HTTP-кэш с [правильными заголовками](/ru/architecture/caching/#http-кэширование-общий-язык). Кода он не требует.
- **Приложение, которое должно открываться без сети:** service worker с заранее закэшированной оболочкой приложения.
- **Чтение офлайн:** оболочка приложения плюс закэшированный набор данных.
- **Редактирование офлайн с несколькими устройствами или пользователями:** sync engine (движок синхронизации) или local-first библиотека (локальная копия — рабочий источник, а изменения синхронизируются позже). Написать это самим — отдельный проект.
- **Большинство контентных сайтов и дашбордов:** ничего из этого не нужно. Service worker добавляет новый способ сломать сайт, поэтому нужна настоящая причина.

## Ландшафт

- **Обёртки над IndexedDB:** idb, Dexie.
- **Инструменты для service worker:** Workbox, Serwist.
- **Базы данных в браузере:** официальная сборка SQLite на WebAssembly поверх OPFS, wa-sqlite; PGlite для PostgreSQL.
- **Sync engines и local-first:** Replicache и Zero, ElectricSQL, PowerSync, Yjs, Automerge.
- **Просмотр:** панель Application в DevTools показывает все хранилища, service worker и его состояние, а также умеет имитировать офлайн и очищать данные сайта.
