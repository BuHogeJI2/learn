## Какую проблему решает

Много пользователей и серверов работают с одними и теми же данными одновременно. Операции обрываются на полпути. Данные копируются в реплики, кэши и поисковые индексы. Без гарантий деньги пропадают, два человека бронируют последнее место, а пользователь сохраняет изменение и потом его не видит.

Фронтенд видит симптомы: два заказа после двойного клика, старые данные сразу после сохранения, счётчик, который немного врёт, «конфликт», который никто не обработал.

## Ментальная модель: три источника проблем

| Проблема | Пример | Гарантия, которая на неё отвечает |
| --- | --- | --- |
| **Частичный сбой** | Деньги ушли с одного счёта, а сервер упал раньше, чем они дошли до другого | **Атомарность**: все шаги или ни одного |
| **Параллельность** | Два запроса читают «осталось 1 место» и оба его бронируют | **Изоляция**: сколько параллельные операции видят друг от друга |
| **Копии** | Реплика или кэш всё ещё хранит старое значение | **Модели согласованности**: что может вернуть чтение |

Первые две решаются внутри одной базы данных **транзакциями**. Третья появляется, как только данные живут больше чем в одном месте.

## Транзакции и ACID

**Транзакция** объединяет несколько чтений и записей в одну единицу. Гарантии транзакций базы данных описывают как **ACID**:

- **Atomicity** (атомарность): применяются все изменения или ни одного. Перевод списывает и зачисляет вместе.
- **Consistency** (согласованность): ваши правила (ограничения вроде «баланс ≥ 0», уникальный email, внешние ключи) выполняются после каждой транзакции. Здесь «согласованность» означает *ваши правила соблюдены*; это другой смысл, чем у «согласованности» в распределённых системах ниже.
- **Isolation** (изоляция): параллельные транзакции не видят незавершённую работу друг друга — в той мере, которую задаёт **уровень изоляции**.
- **Durability** (долговечность): после коммита изменение переживает сбой.

Транзакция живёт **внутри одной базы данных**. У процесса, который пишет в вашу базу, списывает деньги с карты через Stripe и отправляет email, общей транзакции нет; см. [между сервисами](#между-сервисами-общей-транзакции-нет).

## Параллельные записи и изоляция

Классические проблемы:

- **Потерянное обновление** (lost update). Два запроса читают `stock = 5`, оба записывают `stock = 4`. Одна продажа потеряна.
- **Write skew** (перекос записи). Два дежурных врача каждый проверяют «дежурит ли кто-то ещё?», видят «да», и оба уходят с дежурства. Каждое чтение было верным; общий результат нарушает правило.
- **Неповторяющееся чтение** (non-repeatable read). Один и тот же запрос внутри одной операции возвращает разные результаты, потому что кто-то закоммитил изменения между ними.

Уровни изоляции (названия из стандарта SQL; детали отличаются между базами):

| Уровень | Что видит транзакция | Типичный уровень по умолчанию в | Всё ещё возможно |
| --- | --- | --- | --- |
| **Read committed** | Только закоммиченные данные, но каждый оператор может видеть более новые | PostgreSQL | Потерянные обновления в коде «прочитать, затем записать»; write skew |
| **Repeatable read / snapshot** | Один снимок на всю транзакцию | MySQL (InnoDB) | Write skew; в некоторых базах и потерянные обновления |
| **Serializable** | Как будто транзакции выполнялись одна за другой | — | Ничего из перечисленного, но база может прервать транзакцию, и код должен её повторить |

На практике большинство приложений остаётся на уровне по умолчанию и явно защищает несколько критичных мест:

- **Атомарные обновления**: пусть база посчитает всё одним оператором: `UPDATE products SET stock = stock - 1 WHERE id = 3 AND stock > 0`. Если ни одна строка не изменилась, товар закончился.
- **Ограничения**: уникальный индекс делает невозможными два аккаунта с одним email, как бы ни совпало время. Заставить базу соблюдать правило — самый надёжный инструмент.
- **Пессимистичная блокировка**: заблокировать строку, пока вы с ней работаете (`SELECT … FOR UPDATE`). Безопасно, но другие запросы ждут, а небрежный порядок блокировок приводит к deadlock (взаимной блокировке).
- **Оптимистичная блокировка**: хранить номер версии и одним обновлением менять данные и повышать версию: `UPDATE documents SET title = 'New', version = 8 WHERE id = 3 AND version = 7`. Если ни одна строка не изменилась, кто-то успел раньше: повторите или покажите конфликт. Это та же идея, что `ETag` с `If-Match` в HTTP ([одновременные изменения](/ru/architecture/state/#одновременные-изменения)).
- **Serializable** для небольшой части системы, где правила охватывают несколько строк (бронирования, балансы), с автоматическими повторами.

## Копии и модели согласованности

Как только данные скопированы, чтение может вернуть более старую версию:

```
write ──► Primary ──(replication lag: usually ms to seconds, sometimes more)──► Replica ◄── read
                                                     a read here may return the old value
```

Два края шкалы:

- **Строгая согласованность** (линеаризуемость, linearizability): каждое чтение видит последнюю закоммиченную запись, как будто копия одна. Чтение с текущего primary (основной базы) избавляет от отставания реплик, но полной гарантией становится, только если чтение не обслуживается из более старого снимка, а переключение на другой сервер (failover) никогда не теряет уже подтверждённые записи.
- **Eventual consistency** (согласованность в конечном счёте): если записи прекратятся, все копии в итоге станут одинаковыми. Когда именно — не обещается. Кэши, поисковые индексы, CDN и DNS согласованы в конечном счёте.

Между ними находятся **сессионные гарантии**: обещания о том, что видит один пользователь. Они независимы, и система может давать одну без другой:

- **Read-your-own-writes** («вижу свои изменения»): пользователь всегда видит свои изменения, даже если другие увидят их чуть позже. Надёжные способы: держать чтения этого пользователя на primary или читать с реплики только после проверки, что она уже применила запись пользователя (некоторые базы возвращают для этого позицию или токен версии). Отправлять чтения на primary фиксированное время после записи — частый упрощённый приём, но он ломается, когда отставание длиннее этого времени. Сторона UI описана в [Клиентском и серверном состоянии](/ru/architecture/state/#одновременные-изменения).
- **Монотонное чтение** (monotonic reads): пользователь никогда не видит, как время идёт назад. Без этой гарантии два чтения, попавшие на реплики с разным отставанием, могут показать новое значение, а потом старое. Частое решение — держать каждого пользователя на одной и той же реплике.

**CAP** коротко. Когда сеть разделяет копии данных (сетевое разделение, partition), система должна выбрать: отказывать в части запросов, чтобы остаться согласованной, или продолжать отвечать, рискуя отдать устаревшие или конфликтующие данные. Это всё, что говорит CAP, и относится это только к моменту разделения. В обычной работе повседневный компромисс — **задержка против согласованности**: чтобы копии оставались согласованными, нужна координация (ожидание других копий или обращение к единственному месту, которому принадлежат данные), и это замедляет операции. Не используйте CAP, чтобы раскладывать базы данных по коробкам; проверяйте, какую гарантию получает каждая операция.

## Между сервисами: общей транзакции нет

Процесс заказа часто затрагивает вашу базу, платёжного провайдера, сервис склада и сервис email. Транзакции, охватывающей их всех, нет. Двухфазный коммит (протокол, который блокирует всех участников, пока все не согласятся) существует, но в вебе встречается редко. Вместо этого:

- **Делайте каждый шаг идемпотентным и пригодным для повтора** с [idempotency key](/ru/architecture/api-styles/#границы-ошибок) (ключом идемпотентности), чтобы повтор никогда не списал деньги дважды.
- **Саги**: последовательность локальных транзакций, у каждой из которых есть **компенсирующее действие**, отменяющее её в бизнес-смысле. Если резерв товара не удался после оплаты, компенсация — возврат денег. Промежуточные состояния («оплата получена, товар в ожидании») видны, и их нужно проектировать.
- **Проблема двойной записи** (dual write): «сохранить заказ, затем опубликовать сообщение „заказ создан“» ломается, если процесс упадёт между двумя шагами; заказ существует, но о нём никто не узнает. Паттерн **transactional outbox** (таблица исходящих сообщений внутри транзакции) записывает сообщение в ту же транзакцию базы, что и заказ, а отдельный процесс публикует его позже ([фоновые задачи](/ru/architecture/background-jobs/#как-надёжно-отправлять-сообщения)).
- **Показывайте промежуточные состояния в UI**: «Обрабатывается», «Ожидает подтверждения». Если делать вид, что многошаговый процесс мгновенный, позже появятся непонятные ошибки.

## Типичные проблемы

- **«Прочитать, изменить, записать» в коде приложения** без блокировки или атомарного обновления: счётчики, остатки, балансы.
- **«Проверить, затем вставить»** без уникального ограничения: дублирующиеся аккаунты, двойные бронирования.
- **Двойная отправка создаёт два заказа.** Отключённая кнопка помогает пользователю, но ничего не гарантирует. Idempotency key гарантирует, если клиент создаёт **один ключ на одну задуманную операцию** (например, когда открывается форма оформления заказа), использует его для каждого клика и повтора, а сервер отклоняет повторы уже виденного ключа.
- **Чтение с реплики сразу после записи**: «моё изменение пропало».
- **Длинные транзакции**, которые держат блокировки, пока вызывают другие сервисы по HTTP.
- **Игнорирование ошибок сериализации и deadlock** вместо их повтора.
- **Побочные эффекты внутри транзакции**: email отправлен, а транзакция откатилась.
- **Упорядочивание событий по времени с разных машин.** Их часы расходятся (clock skew), поэтому «позже» может оказаться неправдой.
- **Предположение, что кэш или поисковый индекс актуальны.**

## Как выбирать

Начните с вопроса: **сколько стоит неверный ответ и сколько стоит медленный или отказанный?**

- **По умолчанию:** реляционная база с транзакциями на уровне по умолчанию, плюс ограничения, атомарные обновления для счётчиков и остатков и оптимистичные версии для записей, которые редактируют пользователи.
- **Деньги, склад, бронирования:** serializable-транзакции или явные блокировки для критичной части и idempotency keys в API.
- **Ленты, лайки, счётчики просмотров, результаты поиска:** eventual consistency подходит; приблизительные числа допустимы.
- **Сразу после собственного изменения пользователя:** read-your-own-writes.
- **Процессы между сервисами:** саги, идемпотентность и outbox, с промежуточными состояниями в UI.

## Ландшафт

- **Транзакционные базы на одном узле:** PostgreSQL, MySQL, SQLite, SQL Server.
- **Распределённый SQL с сильными гарантиями:** Google Spanner, CockroachDB, YugabyteDB, TiDB.
- **Настраиваемая или eventual consistency:** Cassandra (согласованность выбирается для каждого запроса), DynamoDB (по умолчанию чтения согласованы в конечном счёте; строгие чтения и транзакции — как опции), MongoDB (read и write concerns, транзакции по нескольким документам).
- **Движки workflow для саг и надёжных многошаговых процессов:** Temporal, AWS Step Functions, Inngest, Restate.
- **Change data capture** (CDC — поток изменений базы в другие системы, часто используется для outbox): Debezium.
- **Проверка гарантий:** опубликованные анализы реальных баз данных от Jepsen.
