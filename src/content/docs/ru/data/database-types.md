## Какую проблему решает

Любое приложение хранит данные, и база данных определяет, какие вопросы задавать легко, какие гарантии вы получаете, как система растёт и сколько стоит её эксплуатация. Это одно из самых трудных для отмены решений: код переписывают, а данные остаются, и их приходится мигрировать.

Для фронтенд-разработчика это проявляется так: как API может делать пагинацию и фильтрацию, возможен ли поиск, бывают ли баги «моё изменение пропало», а в full-stack фреймворках и на serverless-платформах (код, который платформа запускает по запросу, без постоянно работающего сервера) — какую базу выбрать для своего проекта.

## Ментальная модель: структура данных на диске плюс гарантии

Любая база данных — это сочетание четырёх вещей:

1. **Модель данных**: таблицы, документы, пары ключ-значение, графы.
2. **Индексы**: какие поиски быстрые.
3. **Гарантии**: транзакции и согласованность (см. [Согласованность данных](/ru/data/consistency/)).
4. **Модель масштабирования**: одна машина, копии или данные, разделённые между многими машинами.

Поэтому выбирают по **паттернам доступа**: что вы читаете и записываете, как часто и по какому ключу или условию.

**Индексы** определяют скорость сильнее, чем бренд базы. Без индекса найти строки — значит прочитать их все. Индекс (обычно B-tree, сортированное дерево) — это отсортированная копия некоторых колонок с указателями на строки, поэтому поиск и диапазоны по этим колонкам быстрые. Цена: каждая запись обновляет ещё и индексы, и они занимают место. Большинство проблем «база тормозит» — это отсутствующий индекс или запрос, который не может его использовать.

Второе разделение — по нагрузке:

- **OLTP** (online transaction processing — обработка транзакций): много мелких чтений и записей, например «загрузить этот заказ» или «добавить в корзину». Это основная база приложения.
- **OLAP** (online analytical processing — аналитическая обработка): немного больших запросов, которые сканируют миллионы строк, например «выручка по странам по месяцам». Обычно отдельная система, которая хранит данные по колонкам.

## Типы баз данных

| Тип | Модель данных | Сильна в | Слаба в | Примеры |
| --- | --- | --- | --- | --- |
| **Реляционная** (SQL) | Таблицы с фиксированной схемой (объявленные колонки и их типы); связи через ключи; join (соединение таблиц в запросе) | Гибкие запросы, ограничения, транзакции, вопросы, которые вы не планировали | Масштабирование записи на много машин; изменения схемы требуют миграций | PostgreSQL, MySQL, SQLite, SQL Server |
| **Документная** | JSON-подобные документы, вложенные; гибкая форма | Чтение и запись целого объекта за раз; данные разной формы | Связи между документами; join | MongoDB, Firestore, Couchbase |
| **Key-value** (ключ-значение) | Значение под ключом | Очень быстрый простой доступ: [кэши](/ru/architecture/caching/), сессии, счётчики, rate limits (ограничения частоты запросов) | Любые запросы не по ключу | Redis, Valkey, Memcached, Cloudflare KV, DynamoDB (и документы) |
| **Wide-column** (широкие колонки) | Строки, сгруппированные по ключу партиции и распределённые по многим машинам | Огромные объёмы записи с доступом по известным ключам | Произвольные запросы; таблицы проектируются под каждый запрос | Cassandra, ScyllaDB, Bigtable, HBase |
| **Поисковый движок** | **Инвертированный индекс** (слово → документы, где оно встречается) | Полнотекстовый поиск, ранжирование по релевантности, опечатки, фильтры со счётчиками (фасеты) | Роль источника истины; обновления появляются с задержкой | Elasticsearch, OpenSearch, Meilisearch, Typesense, Algolia |
| **Графовая** | Узлы и рёбра | Запросы через много шагов: друзья друзей, рекомендации, мошеннические схемы | Простые чтения и записи в большом объёме | Neo4j, Amazon Neptune |
| **Time-series** (временные ряды) | Измерения во времени | Интенсивная запись метрик и событий; временные окна; прореживание | Данные общего назначения | TimescaleDB, InfluxDB, Prometheus |
| **Аналитическая** (колоночная) | Данные хранятся по колонкам | Агрегации по миллиардам строк | Много мелких записей; получение отдельных строк | ClickHouse, BigQuery, Snowflake, DuckDB |
| **Векторная** | Embeddings (списки чисел, которые передают смысл) | Поиск по сходству: семантический поиск, поиск для AI | Точные запросы | pgvector, Pinecone, Qdrant, Weaviate |

Файлам (картинки, видео, загрузки) место в **объектном хранилище** (Amazon S3, Cloudflare R2), а в базе данных — только их метаданные.

## Реляционная или документная: решение, которое важнее всего

**Реляционная** подходит, когда у данных много связей, вы будете запрашивать их способами, которые пока не знаете, и важна корректность: пользователи, заказы, платежи, складские остатки.

**Документная** подходит, когда данные — это естественно **самодостаточный объект**, который читается и записывается целиком и форма которого меняется: страница CMS из блоков, товар со множеством атрибутов вариантов, данные событий.

Заказ с позициями, обоими способами:

```
Relational                                Document
orders(id, user_id, created_at)           {
order_items(order_id, product_id,           "_id": 42, "userId": 7,
            qty, price)                     "items": [
products(id, name, price)                     { "productId": 3, "name": "Lamp",
→ join the tables to show an order              "qty": 1, "price": 49 } ] }
                                          → one read shows the whole order
```

Здесь виден главный компромисс:

- **Нормализация**: хранить каждый факт один раз и соединять при чтении. Запись простая, и ничего не рассинхронизируется.
- **Денормализация**: копировать данные туда, где их читают. Чтение быстрое, но копии нужно поддерживать в согласии. (Для заказов копировать название и цену как раз правильно: заказ должен хранить цену на момент покупки.)

Граница размылась: в PostgreSQL есть колонки `JSONB` с индексами, а в MongoDB — транзакции по нескольким документам и join. Разница в настройках по умолчанию и в том, что естественно, а не в том, что возможно.

«Без схемы» (schemaless) — миф. Схема переезжает из базы данных в ваш код, и старые формы данных всё равно придётся обрабатывать, только позже и в приложении.

## Одна основная база, специализированные помощники

Типичная схема:

```
            ┌─► Redis            cache, sessions, rate limits, queues
App ──► PostgreSQL (source of truth)
            ├─► Search engine    fed from the primary, for full-text search
            ├─► Object storage   files
            └─► Warehouse        copies for analytics
```

Каждое дополнительное хранилище — ещё одна копия, которая может устареть ([согласованность](/ru/data/consistency/#копии-и-модели-согласованности)), и ещё одна система, которую надо эксплуатировать. Начните с одной базы: один только PostgreSQL умеет JSON-документы, полнотекстовый поиск, простые очереди и векторы. Добавляйте специализированное хранилище, когда потребность измерена.

## Масштабирование коротко

- **Вертикальное**: машина помощнее. Это работает дольше, чем ожидает большинство.
- **Реплики для чтения**: копии, которые обслуживают чтение. Они отстают от основной базы, и из-за этого чтения бывают устаревшими.
- **Партиционирование**: разделение большой таблицы на части по ключу (например, по месяцам) внутри одной базы. Большими таблицами становится проще управлять, а некоторые запросы ускоряются, но машин не добавляется.
- **Шардинг**: разделение данных по ключу между несколькими машинами, каждая хранит свою часть. Запросы и транзакции между шардами становятся трудными, а ключ трудно поменять.
- **Лимиты соединений**: serverless-функции могут открыть тысячи соединений и исчерпать SQL-базу. Используйте пулер соединений или драйвер поверх HTTP.
- **Распределённый SQL** (Spanner, CockroachDB, YugabyteDB, TiDB): SQL и транзакции, распределённые по многим машинам, ценой большей задержки и стоимости.

## Типичные проблемы

- **Выбор под масштаб, которого у вас нет**: распределённая база для приложения с тысячей пользователей.
- **Отсутствующие индексы** и N+1-запросы из ORM (библиотеки, которая связывает таблицы с объектами в коде), которая загружает связанные строки по одной ([N+1](/ru/architecture/api-styles/#как-они-сравниваются)).
- **Кэш или поисковый индекс в роли источника истины**, а потом потеря данных при перезапуске или переиндексации.
- **Документная база для сильно связанных данных**: join в коде приложения и копии, которые расходятся.
- **Документы, растущие без предела**, например все комментарии внутри документа поста.
- **Исчерпание соединений** serverless-функциями.
- **Файлы, сохранённые как blob в базе данных.**
- **Структура таблиц, выставленная наружу как API**, из-за чего базу уже никогда не поменять.

## Как выбирать

Спросите:

1. Какие основные чтения и записи? По ключу, по диапазону, по множеству фильтров, по тексту?
2. Насколько связаны данные? Нужны ли join и ограничения?
3. Какие операции должны выполняться целиком или не выполняться вовсе?
4. Сколько данных и сколько записей в секунду, сейчас и через два года?
5. Что знает команда и будет ли базой управлять провайдер?

Разумный вариант по умолчанию для большинства приложений: **управляемая реляционная база как основное хранилище**. Добавьте key-value хранилище для кэширования и недолговечных данных, поисковый движок, когда встроенного поиска базы недостаточно, и хранилище для аналитики, когда аналитические запросы начинают замедлять основную базу.

## Ландшафт

- **Управляемые реляционные:** Supabase, Neon, Amazon RDS и Aurora, Google Cloud SQL, PlanetScale. SQLite на edge: Turso, Cloudflare D1.
- **Документные:** MongoDB Atlas, Firestore, Couchbase.
- **Key-value:** Redis, Valkey (open-source форк Redis), Upstash, DynamoDB, Memcached.
- **Поиск:** Elasticsearch, OpenSearch, Meilisearch, Typesense, Algolia.
- **Аналитика:** ClickHouse, BigQuery, Snowflake, DuckDB.
- **Слои доступа:** ORM и query builders (Prisma, Drizzle, TypeORM, Kysely). Они меняют то, как вы пишете запросы, а не то, что умеет база.
