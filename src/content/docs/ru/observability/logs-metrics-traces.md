## Какую проблему решает

Production ломается так, как никто не предсказал, и подключить к нему отладчик нельзя. Когда что-то идёт не так, ответы нужны быстро:

- Сломано ли? У кого?
- С какого момента? После какого [деплоя](/ru/delivery/deployment-models/#релизы-от-коммита-до-пользователей)?
- Где: какая страница, какой сервис, какой регион?
- Почему?

**Мониторинг** следит за показателями, выбранными заранее. **Observability** (способность понять, что происходит внутри системы, по данным, которые она отдаёт) — более широкая возможность отвечать на *новые* вопросы о работающей системе по данным, которые она испускает. И то и другое строится на одних и тех же сигналах.

Для фронтенд-разработчика сложность в том, что большинство проблем случается там, где их не видно: ошибки JavaScript в браузерах пользователей, медленные страницы на дешёвых телефонах и один клик, который проходит через браузер, [CDN](/ru/web-platform/cdn/) (серверы рядом с пользователями), [BFF](/ru/architecture/application-boundaries/#где-здесь-фронтенд-bff-gateway-микрофронтенды) (серверный слой для одного фронтенда) и несколько сервисов.

## Ментальная модель: три сигнала, три вопроса

| Сигнал | Что это | Отвечает на вопрос | Компромиссы |
| --- | --- | --- | --- |
| **Метрики** | Числа, агрегированные во времени, с несколькими метками: запросы в секунду, доля ошибок, перцентили задержки, CPU | «Что-то не так? Насколько? С какого момента?» | Дёшево хранить и запрашивать; выбираются заранее; нет деталей об отдельных запросах |
| **Логи** | Записи о событиях с временной меткой, в идеале **структурированные** (поля, например JSON, вместо свободного текста) | «Что именно произошло в этом случае?» | Богатые детали; дороги при большом объёме; трудно агрегировать, если не структурированы |
| **Трейсы** | Путь одного запроса через систему в виде дерева **спанов** (span — один спан на операцию) со временем | «Куда ушло время? Какая часть упала?» | Необходимы при нескольких сервисах; обычно **сэмплируются** (сохраняется только доля запросов) |

На их основе строятся специализированные сигналы:

- **[Отслеживание ошибок](/ru/observability/error-tracking/)**: исключения, сгруппированные по причине, со стектрейсами, релизом и затронутыми пользователями.
- **RUM** (real-user monitoring — мониторинг реальных пользователей): производительность и ошибки, измеренные в браузерах реальных пользователей.
- **Профили**: какие функции расходуют CPU и память.

Трейс делает видимым «где»:

```
trace 4bf92f…  GET /checkout                     820 ms
├─ BFF: render page                              790 ms
│  ├─ orders-service:  GET /cart                  40 ms
│  ├─ pricing-service: POST /quote               650 ms   ← the slow part
│  │  └─ db: SELECT … FROM prices                610 ms
│  └─ users-service:   GET /me                    30 ms
```

Обычное расследование движется от широкого к узкому: **алерт** по метрике → **[дашборд](/ru/observability/dashboards-alerting/)** сужает поиск (какой эндпоинт, регион, релиз) → **трейс** медленного или упавшего запроса → **логи** виноватого спана.

## Как связать сигналы

Сигналы полезны только вместе, поэтому у них должны быть общие идентификаторы:

- **Контекст трейса.** Первый компонент, который видит запрос, создаёт **trace ID**. Каждая операция записывает **спан** со своим span ID и указателем на **родительский** спан. Когда один сервис вызывает другой, он отправляет trace ID и ID текущего спана в заголовке (заголовок W3C `traceparent`), поэтому спаны вызванного сервиса встраиваются в то же дерево под правильным родителем.
- **Trace ID и span ID в каждой строке лога, записанной во время запроса.** Тогда можно перейти от трейса к его логам, а от ошибки — к её трейсу. Логи вне запроса (запуск, работа по расписанию) вместо этого несут сервис, релиз и идентификатор задачи.
- **Общие атрибуты** у каждого сигнала: имя сервиса, версия или релиз, окружение, регион. Они позволяют спросить: «ошибки начались с релиза 1.42?»
- **Из браузера.** Фронтенд-SDK могут начинать трейс и отправлять `traceparent` вместе с вызовами API, так что медленный клик связывается со спанами бэкенда. Если API на другом origin (схема + хост + порт), он должен разрешить этот заголовок в [CORS](/ru/security/browser-boundaries/#cors-сервер-сам-разрешает-себя-читать).

Одна ловушка со стоимостью — **кардинальность**, число уникальных временных рядов. Каждое уникальное сочетание имени метрики и значений всех её меток — отдельный ряд, поэтому значения перемножаются между метками: 50 эндпоинтов × 10 статус-кодов × 20 регионов — это уже 10 000 рядов. Метка с неограниченным числом значений (ID пользователя, ID запроса, URL с ID внутри) заставляет это число взорваться. Держите такие значения в логах и трейсах, а не в метках метрик.

## Что измерять

Для сервисов, обрабатывающих запросы, классические наборы такие:

- **RED**: **R**ate (запросы в секунду), **E**rrors (неудачные запросы), **D**uration (задержка).
- **Четыре золотых сигнала Google**: задержка, трафик, ошибки и **saturation** (насыщение: насколько заполнен ресурс — CPU, память, пул соединений с базой, длина очереди).

Измеряйте задержку **перцентилями**, а не средними:

- **p50** (медиана) — типичный запрос; **p95** и **p99** показывают медленный хвост. «p99 = 1,2 с» значит, что 1% запросов медленнее 1,2 секунды.
- Средние скрывают хвост, а хвост важен: один просмотр страницы может делать десятки запросов, поэтому медленный 1% встречается многим пользователям.
- Перцентили нельзя усреднять между серверами. Системы хранят **гистограммы** (количество запросов в каждом диапазоне задержки) и вычисляют перцентили из них.
- Измеряйте ошибки отдельно: быстрый падающий запрос может улучшить картину задержки.

Для фронтенда добавьте [Core Web Vitals](/ru/observability/web-vitals/) от реальных пользователей ([метрики](/ru/web-platform/page-loading/#как-шаги-соотносятся-с-метриками)), долю ошибок JavaScript и сбои API так, как их видит клиент. Если сервер вернул `200 OK`, это ещё не значит, что страница сработала.

## SLI, SLO, SLA и error budget

Они превращают измерения в решения:

- **SLI** (service level indicator — показатель уровня сервиса): измеренная доля хороших событий, например «доля запросов оформления заказа, которые успешны и быстрее 300 мс». Измеряйте его как можно ближе к пользователю: на [балансировщике нагрузки](/ru/architecture/scaling/#балансировка-нагрузки), в CDN или в клиенте. Считайте его по полным счётчикам или гистограммам всех запросов, а не по сэмплированным трейсам: выборка, которая сохраняет каждую ошибку, но лишь часть успешных запросов, делает долю ошибок хуже, чем она есть.
- **SLO** (service level objective — цель уровня сервиса): цель для SLI за временное окно, например «99,9% за 28 дней». Это внутренняя цель.
- **SLA** (service level agreement — соглашение об уровне сервиса): договор с клиентами с последствиями (возвраты, компенсации), если он нарушен. Обычно он мягче SLO, чтобы вы заметили проблемы раньше, чем начнёте платить.
- **Error budget** (бюджет ошибок): 100% минус SLO. Объём сбоев, который вам разрешён. Пока бюджет остаётся, выпускайте свободно; когда он израсходован, замедлите рискованные релизы и займитесь надёжностью. Это превращает вопрос «скорость или стабильность?» в число.

Для наглядности — что позволяет **временна́я** цель доступности за 30-дневный месяц, если во время сбоя сервис полностью не работает. SLO на основе запросов считает вместо этого плохие запросы: сбой в пик трафика расходует больше бюджета, чем ночью, а медленные запросы тоже расходуют бюджет.

| SLO | Допустимый полный простой |
| --- | --- |
| 99% | около 7 часов 12 минут |
| 99,9% | около 43 минут |
| 99,99% | около 4 минут |

100% — неправильная цель. Сети и устройства пользователей и так отказывают чаще, а каждая следующая девятка стоит гораздо дороже предыдущей.

## Алерты, на которые реагируют

- **Алертьте по симптомам, которые чувствуют пользователи** (доля ошибок, задержка относительно SLO), а не по каждой возможной причине («CPU на 80%»). Причинам место на дашбордах, куда смотрят во время расследования. Исключение — причина, которая предсказывает реальный ущерб и требует действия, например диск, который заполнится через четыре часа ([алерты](/ru/observability/dashboards-alerting/#алерты-правила-маршрутизация-тишина)).
- **Алерты по burn rate** (скорости расходования бюджета). Поднимайте дежурного, когда бюджет ошибок сгорает быстро (например, 2% месячного бюджета за час), и заводите тикет, когда медленно. Проверяйте короткое окно вместе с длинным, чтобы алерт прекращался, как только проблема закончилась. В сервисах с малым трафиком один неудачный запрос может выглядеть как огромное сгорание; используйте там синтетические проверки (скриптовые запросы, отправляемые по расписанию) или более мягкие пороги.
- **Каждый вызов дежурного должен быть срочным, требовать действия и иметь runbook** (описание шагов для диагностики и исправления). Если правильная реакция на алерт — «игнорировать», удалите алерт.
- **Alert fatigue** (усталость от алертов) — реальный сценарий сбоя: слишком много шумных алертов, и важный пропускают.

## Типичные проблемы

- **Неструктурированные логи без ID запроса или трейса.** Ничего нельзя связать между сервисами.
- **Секреты и персональные данные в логах**: токены, пароли, email, полные тела запросов. Утечка и проблема с требованиями регуляторов.
- **Метки метрик с высокой кардинальностью** и счёт за мониторинг, который растёт быстрее трафика.
- **Только средние**, из-за чего медленный хвост остаётся невидимым.
- **Мониторинг только на сервере.** Сервер отвечает `200`, а страница ломается в браузерах из-за ошибки JavaScript, сломанного файла в CDN или заблокированного стороннего скрипта.
- **Ошибки без тегов релиза и source maps** (файлов, которые сопоставляют минифицированный код с исходным), из-за чего регрессию нельзя связать с деплоем, а стектрейсы указывают в минифицированный код.
- **Сэмплирование, которое выбрасывает редкие сбои.** **Head sampling** (сэмплирование в начале) решает в начале запроса, когда ещё никто не знает, чем он закончится, поэтому может выбросить единственный упавший трейс. **Tail sampling** (сэмплирование в конце) решает после завершения трейса и может сохранить все ошибки и медленные запросы, но сначала должно буферизовать спаны и имеет собственные лимиты мощности.
- **Трейсы, которые обрываются на [очереди](/ru/architecture/background-jobs/) или вызове сторонней системы**, потому что контекст трейса не передали дальше.
- **Алерты на всё подряд.**

## С чего начать

Разумный минимум для приложения в production:

1. **Отслеживание ошибок** во фронтенде и бэкенде, с тегами релиза и source maps.
2. **Структурированные логи** с ID запроса или трейса в каждой строке, записанной во время запроса.
3. **RED-метрики** для каждого эндпоинта, насыщение для баз данных и очередей и Web Vitals от реальных пользователей.
4. **Один-два SLO** для самых важных пользовательских сценариев (вход, оформление заказа) с алертами на них.
5. **Распределённый трейсинг**, как только запрос проходит больше чем через один сервис, включая BFF, который вызывает API.

Где можете, инструментируйте через **[OpenTelemetry](/ru/observability/opentelemetry/)**: один открытый стандарт сбора всех трёх сигналов с отправкой в любой бэкенд, так что смена вендора не требует менять код.

## Ландшафт

- **Стандарты:** OpenTelemetry (SDK, Collector, семантические соглашения), W3C Trace Context.
- **Платформы «всё в одном»:** Datadog, New Relic, Dynatrace, Honeycomb, Grafana Cloud, Elastic Observability, Sentry (ошибки, трейсинг, запись сессий).
- **Open-source компоненты:** Prometheus (метрики), Grafana (дашборды), Loki (логи), Tempo и Jaeger (трейсы), Pyroscope (профили); стеки на основе ClickHouse, например SigNoz и HyperDX.
- **Фронтенд и реальные пользователи:** Sentry, Datadog RUM, LogRocket, Vercel Speed Insights, библиотека `web-vitals`.
- **Дежурства и инциденты:** PagerDuty, incident.io, Rootly; страницы статуса, например Atlassian Statuspage и Better Stack.
